# 연구: 여러 쪽 문서 추출에서 행이 빠지는 원인

브랜치 `claude/multipage-bundle-extraction`

> **질문.** 여러 쪽짜리 서류(거래내역서, 인보이스·패킹리스트, 재무제표, 등기부등본, 주민등록등본)를 VLM에 넣어 목록을 뽑으면
> 행이 빠진다. **왜 빠지는가?** 해상도, 출력 길이, 이미지 수, 쪽 사이 의존 등 후보 원인을 하나씩 떼어 내 측정하고,
> 밝혀진 원인에 맞는 처방을 검증한다.

## 1. 왜 이 질문인가

- 지금 2부 방식은 묶음의 모든 쪽을 한 질문에 넣는다(이미지 합 12,000토큰 → 13쪽이면 쪽당 약 920토큰, 원래의 1/4).
  답은 중앙값 약 8,600토큰, 길면 13,500토큰이다(생성 데이터 실측).
- 쪽이 많을수록 VLM 추출 점수가 무너진다는 보고는 있다(ExtractBench 2607.29677: 50쪽 넘으면 87.9 → 27.9, 행 누락).
  그러나 **무엇 때문에** 빠지는지는 분리해서 밝혀진 적이 없다. 실제 서류에서는 원인들이 늘 같이 움직이기 때문이다
  (쪽이 많으면 해상도도 떨어지고, 이미지도 늘고, 답도 길어진다).
- 이 저장소의 생성기(docgen)는 **같은 내용**을 해상도·쪽 나눔·머리글 유무만 바꿔 다시 만들 수 있고, 모든 행의 정답과
  위치(쪽, 박스)를 안다. 그래서 원인을 하나씩 떼어 볼 수 있다. 이것이 이 연구만 할 수 있는 부분이다.
- 원인을 알아야 처방이 정해진다. 출력 길이가 원인이면 해상도는 그대로 두고 출력만 끊으면 되고, 해상도가 원인이면
  원래 해상도로 한 장씩 읽어야 하며, 쪽 사이 의존이 원인일 때 비로소 "앞 쪽에서 무엇을 넘길까"가 의미 있는 질문이 된다.

## 2. 후보 원인

| 단계 | 후보 | 내용 | 확인 방법 |
|---|---|---|---|
| 읽기 | 해상도 | 쪽당 이미지 토큰이 적어 글자를 못 읽음 | 통제 A |
| | 글자 높이 대 토큰 크기 | 이 모델은 이미지 토큰 하나가 32×32px. 글자·행 간격이 토큰보다 작으면 행이 섞임 | 관찰(글자·행 간격을 토큰 단위로), 통제 A |
| | 표 모양, 촬영 품질, 쪽 안 위치 | 괘선 없는 표, 스캔·팩스, 쪽 맨 아래 행 | 관찰 |
| 출력 | 출력 길이 | 답이 길어질수록 중간 행을 건너뛰거나 상한에 잘림 | 통제 B, 관찰(출력 속 위치) |
| | 비슷한 행 반복 | "카드결제 / 같은 금액"이 연달아 나오면 반복을 피하다 건너뜀 | 관찰(이웃 행과 같은 칸 비율) |
| | 스스로 일찍 끝냄 | 상한 전에 모델이 멈춤 | 관찰(`finish_reason`) |
| 여러 쪽 | 이미지 수 | 이미지가 많으면 어느 행이 어디 있는지 놓침 | 통제 C |
| | 머리글 없는 다음 쪽 | 다음 쪽에 표 머리글이 없어 무슨 표인지 모름 | 통제 D, 관찰 |
| | 쪽 경계 | 경계 바로 앞뒤 행이 빠지거나 겹침 | 관찰 |
| 채점 착시 | 잘못 읽음, 다른 곳에 넣음 | 행은 냈지만 값이 틀려 짝이 안 지어지거나 다른 목록·문서에 넣음 | 누락 분류에서 따로 셈 |

## 3. 방법

### 1단계 — 관찰: 실제로 어디서 빠지는가

묶음을 지금 방식(한 번에 넣기)과 비교용 쪽 단위(원래 해상도, 쪽마다 따로)로 돌리고, **정답 행 하나하나**에 대해
결과와 특징을 기록한다(`rows.jsonl`). 그다음 어떤 특징이 누락과 묶이는지 본다(`analysis.md`).

**행 결과 분류** (`mpx/rows.py`). 정답 행과 예측 행을 순서를 지키며 맞춘 뒤(칸 절반 이상 같으면 짝),
짝이 없는 정답 행은 앞뒤 짝 사이의 빈자리를 보고 나눈다.

| 결과 | 뜻 | 누락으로 셈 |
|---|---|---|
| `exact` | 모든 칸 맞음 | |
| `partial` | 짝은 지어졌으나 일부 칸 틀림 | |
| `misread` | 그 자리에 예측 행이 있으나 절반 이상 틀림 (행은 냈음) | |
| `misplaced` | 다른 목록이나 다른 문서에 들어감 | |
| `skipped` | 앞뒤 행은 냈는데 이 행만 없음 (그 뒤에도 출력이 이어짐) | ● |
| `cut_length` | 출력이 길이 상한에 잘려 이 행부터 끝까지 없음 | ● |
| `cut_stop` | 상한이 아닌데 모델이 이 행 앞에서 출력을 끝냄 | ● |
| `doc_missing` | 문서 자체를 못 찾았고 위 어디에도 해당하지 않음 | ● |

잘린 출력은 그냥 버리지 않고 닫히지 않은 괄호를 메워 잘리기 전까지의 행을 살린다(`mpx/parse.py`). 그래야 "잘려서 뒤가 없음"과
"처음부터 못 읽음"이 갈린다.

**행 특징.** 글자 높이·행 간격(모델 입력 기준 토큰 단위), 쪽 이미지 토큰, 쪽 안 세로 위치, 요청에 든 이미지 수,
출력에서 이 행 앞에 나올 행 수(추정), 목록 안 위치·목록 길이, 이웃 행과 같은 칸 비율, 칸 수·글자 수,
쪽 경계 행 여부, 이어지는 쪽 여부, 머리글 없는 쪽 여부, 증강(스캔·촬영·팩스) 여부.

**분석.** 방법별 결과 분포, 특징 구간별 누락률, 그리고 누락 여부를 특징들로 설명하는 로지스틱 회귀(특징은 표준화,
계수 = 1 표준편차당 로그 오즈). 한 번에 넣기에서는 쪽 수가 늘면 해상도·이미지 수·출력 길이가 함께 변해
(공선성) 관찰만으로는 원인을 가를 수 없다. 관찰은 **용의자 순위**를 내는 단계이고, 판정은 2단계에서 한다.

### 2단계 — 통제 실험: 한 가지만 바꾼다

같은 쪽, 같은 행을 두고 조건 하나만 바꿔 **그 쪽 행의 누락률**을 비교한다(`mpx/probe.py`). 모든 조건에서 목록 이름과 칸 이름은
질문에 알려 준다(키 이름을 맞히는 능력이 아니라 누락을 재기 위해).

| 실험 | 바꾸는 것 | 고정하는 것 |
|---|---|---|
| A `resolution` | 쪽 이미지 토큰 460 / 920 / 1,800 / 원래(약 3,600) | 그 쪽 한 장만, 그 쪽 행만 묻기 |
| B `scope` | 문서 전체 행을 묻기 vs 그 쪽 행만 묻기 (출력 길이) | 입력 이미지(문서 전 쪽, 쪽당 920토큰)와 해상도 |
| C `images` | 대상 쪽 + 같은 묶음의 다른 쪽 0 / 2 / 4 / 8장 | 쪽당 920토큰, 대상 쪽 행만 묻기 |
| D `header` | 같은 내용을 머리글 반복 있게/없게 렌더링한 두 판의 이어지는 쪽 | 그 쪽 한 장만, 원래 해상도 |

같은 쪽을 조건만 바꿔 묻기 때문에 조건 간 차이는 짝지은 비교(같은 행의 결과 변화)로 본다.
관찰에서 상위에 오른 다른 후보(비슷한 행 반복 등)는 생성기 조절 기능을 더해 같은 방식으로 실험을 늘린다.

### 3단계 — 처방 검증

밝혀진 원인에 맞는 처방을 시나리오 묶음과 실제 서류에서 확인한다.

| 원인 | 처방 | 이미 있는 것 |
|---|---|---|
| 출력 길이 | 쪽·구간 단위로 끊어 출력 (해상도는 유지 가능) | `run --method pagewise` |
| 해상도 | 원래 해상도로 한 장씩 | `run --method pagewise` |
| 이미지 수 | 문서 나누기 후 문서마다 따로 | — |
| 쪽 사이 의존 | 앞 쪽에서 얻은 것을 넘김(상태)과 그 학습 | `run --state doc/tail/context`, `sft` |

실제 서류는 정답이 없으므로 예측 값이 그 쪽 사내 OCR 글자에 있는 비율, 잔액 흐름, 품목 합계로 본다(`check`).

## 4. 데이터

- **생성 묶음** (`gen`). 평가는 벤치마크(docgen.bench) 업무 시나리오 묶음을 그대로 쓴다(고객 한 명이 한 업무로 낸 서류 전부,
  벤치마크와 같은 촬영 조건 비율). 시나리오에 없는 거래내역서·패킹리스트는 실무에서 함께 내는 서류로 덧붙인다.
  - `--heavy` 0.7: 대상 서류를 목록이 긴 경우로 (거래 30~90줄, 품목 20~60개 등)
  - `--no-repeat-header` 0.3: 이어지는 쪽에 표 머리글을 다시 찍지 않음
  - `--twins`: 머리글을 뺀 서류마다 머리글을 반복한 쌍둥이 판도 렌더링 (통제 D 용, 같은 내용·같은 증강)
  - 학습 고객(seed 500,000~)과 평가 고객(1,500,000~)은 겹치지 않는다.
- **정답.** docgen이 렌더링한 그대로라 모든 칸의 값, 쪽, 박스(px)가 있다. 행은 첫 칸이 놓인 쪽에 속한다.
- **실제 서류.** `bundles.jsonl`에 `pages: [{image, ocr}]`만 있으면 `run`과 `check`가 된다(사내 자료는 부서장과 협의 후 사용).

## 5. 모듈

`python -m mpx <명령>` (이 폴더에서). 각 파일 첫머리에 자세한 설명이 있다.

| 파일 | 하는 일 | 입력 → 출력 |
|---|---|---|
| `mpx/gen.py` | 묶음 생성(docgen 렌더링, 병렬), 쌍둥이 판 | → `data/images`, `labels/<서류>.json`, `bundles.jsonl` |
| `mpx/pages.py` | 쪽별 정답, 질문 문장(목록·칸 안내 포함), 쪽 답 병합, 상태 | |
| `mpx/parse.py` | 모델 답에서 JSON 꺼내기, 잘린 답 살리기 | 원문 → (객체, 잘림 여부) |
| `mpx/run.py` | 묶음 실행: `allatonce`(한 번에), `pagewise`(한 장씩, 상태 선택). `--oracle` 정답 답, `--simulate` 오류 주입 | → `preds/<방법>.jsonl` |
| `mpx/score.py` | 문서 맞추기, 항목·행 채점, 잔액·합계 검사 | |
| `mpx/rows.py` | **행 결과 분류와 행 특징** | 예측 → `rows.jsonl` |
| `mpx/analyze.py` | **결과 분포, 구간별 누락률, 로지스틱 회귀** | `rows.jsonl` → `analysis.md` |
| `mpx/probe.py` | **통제 실험 A~D** 문항 만들기·실행·채점 | → `probes/items.jsonl`, `answers.jsonl`, `probes.md` |
| `mpx/report.py` | 방법별 종합 점수표 | → `report.md` |
| `mpx/viewer.py` | 묶음별 쪽 이미지, 정답, 방법별 답, 행마다 결과 분류 | → `viewer/index.html` |
| `mpx/sft.py` | (3단계) 쪽 단위·한 번에 넣기 학습 데이터 | → `swift_page/`, `swift_all/` |
| `mpx/pipeline.py` | 위 전부를 한 번에 | → `summary.json` |

## 6. 한 번에 실행

```bash
# 모델 없이 점검 (Chromium 필요): 정답을 답으로 넣으면 모든 행이 exact, 오류를 넣으면 분류가 그 오류를 잡아야 통과
python -m mpx pipeline --out runs/check --n-test 6

# 띄워 둔 모델로 (OpenAI 호환 서버, 예: vLLM)
python -m mpx pipeline --out runs/obs1 --n-test 100 --base-url http://127.0.0.1:8000/v1 --model bank-ocr
```

단계: ① 생성 → ② 관찰 실행(한 번에 넣기, 쪽 단위) → ③ 행 기록·분류 → ④ 분석 → ⑤ 통제 실험 A~D → ⑥ 종합표·viewer.
모델 없이 돌리면 각 실행을 정답(oracle)과 오류 주입(simulated) 두 가지로 해서 분류·분석·viewer가 맞는지 확인한다.

| 결과 파일 (`<out>/`) | 내용 |
|---|---|
| `analysis.md` | 관찰: 결과 분포, 특징별 누락률, 회귀 순위 |
| `probes/probes.md` | 통제 실험: 실험·조건별 누락률과 짝지은 차이 (모델 없이 돌리면 `probes_oracle/`, `probes_simulated/`) |
| `probes/viewer.html` | 통제 실험 viewer: 기준 쪽마다 조건별 행 결과를 기호 줄로 (✓ △ ≠ ↷ ✗ ✂ ■) |
| `report/report.md` | 방법별 종합 점수와 비용 |
| `data/test/viewer/index.html` | 묶음 viewer: 쪽 이미지, 정답, 방법별 답, 행마다 결과 분류 (`python -m mpx viewer ... --serve 7862`로 띄울 수도 있음) |
| `rows.jsonl` | 정답 행마다 결과와 특징 (직접 분석할 때) |
| `summary.json` | 단계별 시간, 점검 결과 |

단계를 따로 돌릴 때:

```bash
python -m mpx gen     --out data/test --n 100 --split test --twins --workers 8
python -m mpx run     --data data/test --method allatonce --base-url $URL --model $M --out preds/allatonce.jsonl
python -m mpx rows    --data data/test --pred preds/*.jsonl --out rows.jsonl
python -m mpx analyze --rows rows.jsonl --out analysis.md
python -m mpx probe   --data data/test --out probes --base-url $URL --model $M
python -m mpx viewer  --data data/test --pred preds/*.jsonl --serve 7862
```

내부망 GPU 서버에서는 `run_experiment.sh`가 vLLM 서버를 띄우고 관찰·통제 실험을 돌린다(3단계 학습은 단계를 지정해서).

```bash
START_MODEL=/models/bank_sft_merged GPUS=0 ./run_experiment.sh                  # gen observe probe score
START_MODEL=... N_TEST=10 PROBE_ITEMS=5 ./run_experiment.sh                      # 리허설
```

모델 없이 점검한 결과(평가 묶음 6개, 묶음당 6~18쪽, 기준 쪽 8개): 약 50초. oracle 실행은 모든 정답 행이 exact,
오류 주입 실행은 넣은 오류 종류를 분류가 모두 찾아냄, 통제 실험 4종(머리글 쌍둥이 판 포함) 문항 생성 — 점검 6개 모두 통과.

## 7. 판정

- 관찰: 진짜 누락(●)이 전체 정답 행의 몇 %이고, 그중 `skipped` / `cut_length` / `cut_stop`이 각각 얼마인지.
  채점 착시(`misread`, `misplaced`)가 누락으로 잘못 세어지던 비율.
- 통제: 한 가지만 바꿨을 때 누락률 변화가 크고 일관되면(짝지은 비교에서 같은 방향) 원인으로 본다.
  예) 해상도를 1/4로 줄여도 그 쪽만 물으면 누락이 거의 없고, 같은 입력에서 문서 전체를 물을 때만 늘면 → 출력 길이가 원인.
- 일반성: 결과가 한 모델의 특성이 아님을 보이려면 다른 계열 모델 하나 이상에서 같은 방향이어야 한다.
- 처방: 원인을 겨냥한 처방이 시나리오 묶음과 실제 서류(정답 없는 검사)에서 누락을 줄이고, 비용(요청 수, 가장 긴 입력,
  출력 토큰, 시간)을 같이 보고한다.

## 8. 한계

- 생성 서류와 실제 서류는 다르다. 실제 서류에서는 정답 없는 검사로만 방향을 확인한다.
- 관찰 단계의 회귀는 상관일 뿐이다. 원인 판정은 통제 실험으로만 한다.
- 질문에 목록·칸 이름을 알려 주므로, 키 이름을 모르는 상황의 누락은 따로 보지 않는다.
