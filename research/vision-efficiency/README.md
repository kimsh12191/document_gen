# 연구: 은행 서류 VLM의 페이지 토큰 효율화

> **핵심 가설:** 서류 페이지의 비전 토큰은 전부 필요하지 않다. **질문과 무관하게 페이지마다 한 번** 필요 없는 토큰을 빼면, 그 페이지에 대한 모든 질문과 여러 페이지 질문이 함께 빨라지고 성능은 그대로다. 아낀 토큰은 해상도를 올리는 데 다시 쓸 수 있다.

브랜치 `claude/vision-token-efficiency` (출발점: `claude/ocr-banking-benchmark`의 1부 OCR 학습 코드와 생성기)

## 1. 실제 사용 조건과 그에 따른 방향

### 조건

| 항목 | 내용 |
|---|---|
| 서빙 | vLLM (프리픽스 캐싱 사용) |
| 질문 | OCR 과제, 정보 추출, 서류 분류, 체크박스 · 도장 · 서명, 서류 구비 확인, 서류 대조, 심사 질의. 모두 정해진 틀 |
| 사용 패턴 | **한 페이지에 질문이 매우 많음** + **여러 페이지를 함께 봐야 하는 질문도 매우 많음** |
| 사내 OCR | 단어 단위. 추론에서는 쓰지 않음 (학습 라벨로만) |
| 데이터 | 내부 OCR 1만 장 이상(실제 이미지 + 단어 박스), 생성 데이터(정확한 박스 라벨, 은행 업무 과제) |
| 자원 | A100 80GB 4장 이상. 전체 미세조정 가능 |
| 출발점 모델 | Qwen3.5-9B, 페이지당 약 3,600 비전 토큰(토큰 ≈ 32×32px), 긴 변 2300 · 짧은 변 1600 |

### 왜 "질문과 무관한 페이지 단위 압축"인가

- **한 페이지에 질문이 많음:** 지금은 페이지 이미지를 질문 앞에 두어 이미지 부분을 프리픽스 캐시로 재사용합니다.
  - 질문마다 다른 영역을 고르는 방식(질문별 확대)은 이미지 부분이 질문마다 달라져 **이 캐시 이득을 잃습니다.**
  - 반면 페이지 토큰을 질문과 무관하게 한 번 줄이면 캐시는 그대로 살고, 줄어든 만큼 이득입니다.
  - 이득 1: 첫 계산이 빨라집니다.
  - 이득 2: 페이지당 KV 메모리가 줄어 캐시에 더 많은 페이지가 남고, 동시에 처리하는 요청이 늘어납니다.
  - 이득 3: 모든 질문의 답 생성 단계가 더 짧은 이미지 문맥을 봅니다.
- **여러 페이지 질문이 많음:** 페이지 수만큼 토큰이 곱해지고, 페이지 조합이 질문마다 달라 프리픽스 캐시도 잘 안 맞습니다. 페이지당 토큰을 줄이면 이득이 페이지 수에 비례합니다. 지금 은행 업무 설정의 `max_model_len 20480`, 이미지 16장 제한 안에 더 많은 페이지가 들어갑니다.
- **원래 문제(작은 글자 · 좌표):** 아낀 토큰을 해상도를 올리는 데 다시 쓰면, 같은 토큰으로 더 자세히 볼 수 있습니다.

질문별 확대(Q-Zoom 류)는 **주 방법이 아니라 보조**로 둡니다. 어려운 질문에만, 캐시된 페이지 토큰 **뒤에** 확대 조각을 덧붙이는 방식이면 캐시를 깨지 않습니다.

## 2. 관련 연구

| 연구 | 내용 | 이 연구와의 관계 |
|---|---|---|
| [PixelPrune](https://github.com/OPPO-Mente-Lab/PixelPrune) (2026) | 학습 없이 **인코더 앞에서** 같은 픽셀 패치(여백 등)를 제거. 문서에서 고유 패치는 22~71%뿐. 8B에서 정확도 0.2점 하락에 추론 최대 4.2배 가속(저자 보고). **Qwen3.5 지원 코드 공개** | 바로 써 볼 1차 기준선. 무늬나 복잡한 배경이 있는 문서에서는 덜 효과적이라는 지적이 있음 |
| [Index-Preserving Token Pruning](https://github.com/sujin-1013/index-preserving-lightweight-token-pruning) (ICLR 2026 워크숍) | 가벼운 **글자 영역 판별기**로 배경 패치를 VLM 앞에서 제거. 남은 토큰은 원래 위치 번호 유지. FLOPs 40~60% 감소, 정확도 비슷(Qwen2.5-VL, VLM 재학습 없음) | 이 연구의 학습형 판별기와 가장 가까움. 우리는 정확한 생성 마스크 + 실제 OCR 단어 박스로 학습시킬 수 있음 |
| [LayoutLite](https://arxiv.org/abs/2607.22200) (2026) | 인코더와 언어 모델 사이에서 토큰 점수를 매겨 제거. OCR 출력 일치도로 강화학습 + 레이아웃 보조 감독. 50% 압축에서 점수 유지, prefill · FLOPs · KV 40% 이상 감소(저자 보고) | 인코더 뒤에서 빼는 방식의 비교군. 인코더 시간은 줄지 않음 |
| [Grounding-Aware Token Pruning](https://arxiv.org/abs/2506.21873) (2025) | 토큰을 빼면 grounding 성능이 무너지는데, 주원인이 **위치 번호가 어긋나는 것**. 남은 토큰의 원래 격자 위치를 유지하면 회복 | **좌표 과제가 핵심인 우리에게 필수 설계 원칙**: 위치 번호 유지 |
| [Spatial Provenance Audit](https://arxiv.org/abs/2608.00077) (2026) | 정답이 맞아도 남은 토큰이 근거 영역을 덮지 않는 경우가 있음. **남은 토큰이 정답 근거 영역을 얼마나 덮는지**를 같이 보고해야 한다고 제안 | 평가 지표로 채택. 우리는 근거 영역 라벨이 있어서 바로 계산 가능 |
| [DeepSeek-OCR](https://arxiv.org/abs/2510.18234) (2025) | 문서 이미지를 아주 적은 비전 토큰으로 압축. 글자 토큰이 비전 토큰의 10배 이내면 OCR 정밀도 약 97%, 20배에서 약 60%(저자 보고) | 문서는 크게 압축 가능하다는 근거. 다만 전용 인코더라 지금 모델에 바로 적용 불가 |
| [RTPrune](https://icml.cc/virtual/2026/poster/62926) (ICML 2026) | DeepSeek-OCR에서 일반 VLM용 가지치기 기법은 **무작위보다도 나빴음**. 문서 전용 기준이 필요 | 일반 기법(어텐션 기반 등)을 그대로 쓰면 안 된다는 근거 |
| [mPLUG-DocOwl2](https://arxiv.org/abs/2409.03420) (2024) | 여러 페이지 문서에서 페이지마다 324토큰으로 압축 | 여러 페이지 문항의 압축 목표치 참고 |
| [Q-Zoom](https://huggingface.co/papers/2604.06912) (2026) | 질문을 보고 쉬운 질문은 거친 특징으로, 세밀한 질문은 관심 영역만 확대. 문서 · OCR에서 2.52배 가속(Qwen2.5-VL-7B, 저자 보고) | 보조 단계(어려운 질문만 확대)의 참고. 캐시 공유와의 충돌은 다루지 않음 |
| [MPIC](https://arxiv.org/abs/2502.01960) (2025) | 이미지 KV 캐시를 프롬프트 **어느 위치에서든** 재사용(위치 무관 캐시). 일부 토큰만 다시 계산해 정확도 유지. 응답 시간 최대 54% 감소(저자 보고) | 여러 페이지 질문에서 같은 페이지가 다른 조합으로 반복될 때의 서빙 측 해법. 선택 단계 |
| [vLLM V1](https://vllm.ai/blog/2025-01-27-v1-alpha-release) | 이미지 해시를 프리픽스 캐시 식별에 사용, 전처리 캐시로 같은 이미지의 전처리 재사용 | 지금 캐시 동작의 근거. 버전별 세부 동작은 0단계에서 직접 확인 |

**정리하면**
- 문서는 압축 여지가 크다는 것이 여러 연구에서 확인됐습니다.
- 다만 일반 기법은 OCR · 좌표에 약합니다. 문서 전용 기준(글자 영역, 위치 유지)이 필요합니다.
- 대부분의 논문은 **요청 하나의 prefill 시간**으로 속도를 잽니다. 우리처럼 프리픽스 캐시 · 질문이 많은 페이지 · 여러 페이지 질문이 섞인 **실제 서빙 부하**에서의 효과는 직접 재야 합니다.

## 3. 방법

### 구조

```
페이지 이미지 ──▶ [토큰 선택기] ──▶ 남길 패치만 ──▶ 비전 인코더 ──▶ 언어 모델
                  (질문과 무관,                     (원래 위치 번호 유지)
                   페이지당 한 번)
```

- **빼는 위치는 인코더 앞:** 인코더와 언어 모델 시간이 모두 줄어듭니다. PixelPrune과 Index-Preserving이 Qwen 계열에서 이 위치로 동작함을 보였습니다.
- **위치 번호 유지:** 남은 토큰은 원래 격자 위치를 그대로 씁니다. 좌표 과제를 위한 필수 조건입니다.
- **선택 단위:** 언어 모델 토큰 하나(32×32px, 인코더 패치 2×2)입니다.

### 토큰 선택기 후보

| 선택기 | 학습 | 근거 |
|---|---|---|
| S0 중복 패치 제거 (PixelPrune) | 없음 | 공개 코드, Qwen3.5 지원 |
| S1 잉크 규칙 (패치 밝기 분산 · 에지) | 없음 | 가장 단순한 기준선 |
| S2 정답 마스크 (상한) | 없음 | 생성 데이터는 렌더링 박스, 내부 데이터는 OCR 단어 박스 + 주변 여유. 추론 때는 쓸 수 없는 **이상적인 경우** |
| S3 학습형 판별기 (주 방법) | 있음 | 축소 이미지 → 토큰별 "남김" 확률. 생성 정확 마스크 + 실제 OCR 단어 박스 + (생성 데이터의) 체크박스 · 도장 · 서명 · 선으로 학습 |
| S4 인코더 뒤 점수 (LayoutLite 류) | 있음 | 비교군. 인코더 시간은 그대로 |

### VLM 적응 학습

토큰을 뺀 입력으로 VLM을 미세조정합니다(전체 미세조정). 남기는 비율을 무작위로 바꿔 가며 학습해서, 여러 압축 수준에서 버티게 만듭니다. 데이터는 내부 OCR, 생성 데이터의 OCR 형식 변환, 생성 은행 업무를 모두 씁니다.

### 해상도 재투자

아낀 토큰으로 입력 해상도를 올립니다(예: 긴 변 2300 → 3000 이상). 페이지당 토큰은 지금 이하로 유지합니다. 작은 글자 · 좌표 정확도가 오르는지 봅니다.

## 4. 데이터

| 데이터 | 형식 | 쓰임 |
|---|---|---|
| 내부 OCR (1만 장 이상) | 실제 이미지 + 사내 OCR 단어 박스 → `bank_ocr prepare` | OCR 과제 학습 · 평가의 중심. 판별기의 실제 분포 라벨(글자 영역) |
| 생성 → OCR 형식 | 생성 이미지 + **모든 글자의 단어 박스**를 사내 OCR 형식 JSON으로 → `bank_ocr prepare` | OCR 학습 보강. 판별기의 정확한 라벨(글자 + 체크박스 · 도장 · 서명 · 선) |
| 생성 → 은행 업무 | `docgen.bench build` | 은행 업무 학습 · 평가, 여러 페이지 문항 |

**생성 데이터 보강 (0단계)**
- 지금 변환(`guide/examples/labels_to_ocr.py`)은 값 칸과 항목명만 넣어 고정 글자(제목, 안내 문구, 약관)가 빠집니다.
- 생성기는 Chromium으로 렌더링하므로(`docgen/image.py`), 렌더링 시 모든 글자의 **단어 단위** 박스와 선 · 체크박스 · 도장 · 서명 위치를 함께 뽑습니다.
- 위변조 방지 무늬 · 워터마크 · 컬러 배경을 넣는 옵션을 추가합니다. 단순 규칙(S0, S1)이 실패하는 조건에서 판별기를 시험하기 위해서입니다.

**근거 영역 라벨:** 모든 문항에 "정답의 근거가 되는 박스"를 붙입니다. OCR 과제는 정답 · 질문 박스, 은행 업무는 묻는 항목의 값 칸 · 체크박스 · 도장입니다. 남긴 토큰이 근거를 덮는지(커버리지) 계산하는 데 씁니다.

## 5. 평가

### 실제 서빙 부하

논문들처럼 요청 하나만 재지 않고, **실제와 비슷한 질문 흐름**을 vLLM에 흘려 잽니다.
- 페이지당 질문 수, 문항당 페이지 수를 실제 분포(또는 가정한 분포)로 정해 benchmark 문항으로 부하를 만듭니다.
- 프리픽스 캐싱은 켭니다.

### 지표

| 구분 | 지표 |
|---|---|
| 성능 (과제별) | 글자 CER · 완전 일치율, 좌표 IoU≥0.5 F1 · 평균 IoU, 은행 업무 점수 |
| 근거 커버리지 | 남긴 토큰이 정답 근거 박스를 덮는 비율. **정답이 맞아도 근거가 빠졌으면 위험 신호** |
| 압축 | 페이지당 남긴 토큰 비율, 판별기 자체 시간 |
| 서빙 | 처리량(질문/초), 첫 토큰까지 시간 p50 · p95, 페이지당 KV 메모리, 캐시 적중률 |

**판정:** 과제별 성능 하락 1%p 이내, 근거 커버리지 99% 이상에서 실제 부하 처리량이 의미 있게 오르면 가설 성립.

## 6. 단계

| 단계 | 내용 | 결정 |
|---|---|---|
| **0. 기반** | ① 생성기에 단어 박스 · 선 · 체크박스 등 전체 마스크 추출, 무늬 옵션 ② 생성 → OCR 형식 → prepare ③ 근거 영역 라벨 ④ **실제 부하 측정 도구**(vLLM, 캐시 켬, 처리량 · 지연 · KV · 적중률) ⑤ Qwen3.5 인코더에 일부 패치만 넣는 경로 확인(HF, vLLM) | vLLM에서 패치 제거를 어떻게 넣을지 결정 |
| **1. 학습 없는 검증** | 지금 SFT 모델에 S0 · S1 · S2를 적용. 남긴 비율별 성능 · 커버리지, 실제 부하 처리량 | **S2(이상적 마스크)로도 40% 이상 못 빼면 중단.** S0 · S1과 S2의 차이가 판별기 연구 여지 |
| **2. 학습형 판별기** | S3 학습(두 데이터 모두). 근거 커버리지 재현율 최우선. S4와 비교 | 주 선택기 확정 |
| **3. VLM 적응 학습** | 뺀 입력으로 전체 미세조정(남김 비율 무작위) | 같은 남김 비율에서 성능 회복 |
| **4. 해상도 재투자** | 입력 해상도를 올리고 토큰은 지금 이하로. 작은 글자 · 좌표 정확도 | 원래 문제(잘 안 보임) 개선 확인 |
| **5. 선택 확장** | (a) 어려운 질문만 캐시 뒤에 확대 조각 덧붙이기 (b) 여러 페이지 질문에서 페이지 KV 위치 무관 재사용(MPIC 류) | 1~4 결과와 실제 부하를 보고 결정 |

## 7. 폴더 구조 (예정)

```
research/vision-efficiency/
  README.md       이 문서
  NOTES.md        실험 기록 (날짜, 설정, 결과, 결론)
  data/           생성 데이터 전체 마스크 · OCR 형식 변환, 근거 영역 라벨
  select/         토큰 선택기 S0~S4, 패치 제거 + 위치 유지
  measure/        실제 부하 생성, vLLM 측정, 채점 · 커버리지 · 비교표
  train/          판별기 학습, VLM 적응 학습 설정
```

`training/`은 OCR 브랜치(`claude/bank-ocr-pipeline`)와 같은 코드라 직접 고치지 않습니다. 연구 코드는 이 폴더에서 `training/bank_ocr`, `docgen`을 가져다 씁니다. 생성기 수정은 기능 추가로 하고 기존 출력은 바꾸지 않습니다.

## 8. 실행 환경

- 실제 실험은 내부망의 서류 이미지 · 사내 OCR 결과 · SFT 모델 · vLLM으로 합니다.
- 이 저장소의 합성 예시 데이터(`guide/examples/make_examples.sh`)로는 코드가 돌아가는지만 확인합니다.
- 실험 기록에 남기는 숫자는 내부망 실측 값만 씁니다. 관련 연구의 수치는 모두 저자 보고 값입니다.
