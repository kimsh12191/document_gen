# 연구: 훑어보고 필요한 곳만 자세히 보는 문서 VLM

> **핵심 가설:** 질문에 필요한 곳만 자세히 보면, 페이지 전체를 자세히 보는 것과 성능은 같고 더 빠르다.
> 사람이 서류를 볼 때처럼 **전체를 대충 훑고 → 질문에 필요한 곳을 골라 → 그곳만 자세히 본다.**

브랜치 `claude/vision-token-efficiency` (출발점: `claude/ocr-banking-benchmark`의 1부 OCR 학습 코드와 생성기)

## 1. 배경

### 문제

- 1부 OCR 학습 후에도 좌표 밀림과 글자 오독이 남습니다. 원인은 주로 글자가 입력에서 너무 작은 것(픽셀 부족)과 인코더의 구분 능력입니다.
- 해상도를 올리면 좋아지지만, 실제 서비스(vLLM)에서는 추론 속도가 중요해서 무작정 올릴 수 없습니다.
- 그런데 질문 하나에 필요한 곳은 페이지의 일부입니다. "신청금액"을 묻는데 약관 문구를 고해상도로 볼 필요는 없습니다. **질문과 관계없는 곳의 고해상도 토큰이 필요 없는 토큰**입니다.

### 현재 설정 (출발점)

| 항목 | 값 | 위치 |
|---|---|---|
| 모델 | Qwen3.5-9B (`model_type: qwen3_5`) | `training/configs/sft.yaml` |
| 이미지 크기 | 긴 변 2300 · 짧은 변 1600 이하로 축소 | `image_max_size`, `training/bank_ocr/pipeline.py` |
| 비전 토큰 | 토큰 하나 ≈ 32×32px, 페이지 한 장 ≈ 3,600토큰 | `training/train.py` (`IMAGE_MAX_TOKEN_NUM`) |
| 학습 | LoRA rank 32 (`all-linear`, 인코더 포함). **이 연구는 전체 미세조정도 허용** | `training/configs/sft.yaml` |
| 서빙 | ms-swift + vLLM. 이미지를 질문 앞에 두어 같은 이미지의 질문끼리 프리픽스 캐시 공유 | `training/run_pipeline.py`, `training/bank_ocr/inference.py` |
| 평가 | 예측과 점수만 기록, **지연 시간은 기록 안 함** | `training/bank_ocr/inference.py` |

### 실제 사용 조건 (확인한 것)

- **서빙:** vLLM. 문항 하나에 호출을 여러 번 해도 됨.
- **질문 종류:** OCR 과제, 은행 업무 벤치마크 질문(정보 추출, 서류 분류, 체크박스 · 도장 · 서명, 서류 구비 확인, 서류 대조, 심사 질의). **모두 정해진 틀이 있는 질문**이라 "볼 곳"의 정답을 데이터에서 정확히 만들 수 있음.
- **사내 OCR:** 단어 단위. **실서비스 추론에서는 쓰지 않음** → 볼 곳은 이미지만 보고 정해야 함. OCR 결과는 학습 라벨로만 씀.
- **자원:** 내부 OCR 데이터 1만 장 이상, A100 4장 이상 → 전체 미세조정 가능.

## 2. 방법: 훑어보기 → 볼 곳 정하기 → 자세히 보기

| 단계 | 하는 일 | 토큰 |
|---|---|---|
| ① 훑어보기 | 페이지 전체를 저해상도로 봄 (서류 종류, 배치 파악) | 적음 (예: 긴 변 800 ≈ 400토큰). 같은 이미지의 모든 질문이 공유 |
| ② 볼 곳 정하기 | 질문과 훑어본 이미지로 자세히 볼 영역을 고름. **"안 봐도 됨"도 답이 될 수 있음** (예: 서류 분류는 훑어보기만으로 충분할 수 있음) | 출력 몇 토큰 |
| ③ 자세히 보기 | 고른 영역을 원본 해상도 조각으로 넣음 | 고른 영역 크기만큼 |
| ④ 답하기 | 훑어본 이미지 + 조각 + 질문으로 답 | - |

### 볼 곳의 단위: 고정 격자의 조각

볼 곳을 임의의 박스가 아니라 **원본 해상도 페이지를 고정 격자로 나눈 조각 번호**로 정합니다(예: 512px 조각, 페이지당 약 15~20개).

- **출력이 짧음:** 좌표 대신 조각 번호 몇 개("3, 7, 8")라 디코딩이 빠름
- **캐시가 잘 맞음:** 같은 조각은 질문이 달라도 같은 이미지라 재사용 가능성이 있음(아래 3절)
- **학습이 쉬움:** 조각마다 "필요 / 불필요"를 고르는 분류 문제가 됨
- **글자 잘림 방지:** 조각 경계에 걸친 글자는 이웃 조각을 같이 고르게 정답을 만들고, 조각끼리 조금 겹치게 자르는 것도 실험 변수로 둠

### 볼 곳을 누가 정하나

| 방법 | 내용 | 비고 |
|---|---|---|
| **(가) 같은 VLM** (주 방법) | 1차 호출: 훑어본 이미지 + 질문 → 조각 번호. 2차 호출: 조각 넣고 답 | 1부에서 grounding을 학습해 잘 맞음. vLLM 그대로 사용 |
| (나) 작은 판별기 | 저해상도 이미지 + 질문 → 조각별 필요 확률 | 1차 호출 대신 쓰면 더 빠를 수 있음. 비교군 |
| (다) 모델 안에서 한 번에 | 저해상도 토큰에 대한 질문의 주의로 고해상도 토큰을 불러옴 | 호출 1번이지만 모델 · vLLM 수정이 큼. (가)가 성립한 뒤 검토 |

**확신이 없으면 넓게 보기:** 고른 조각의 확신이 낮으면 이웃 조각을 더하거나 전체를 고해상도로 봅니다. 쉬운 질문은 싸게, 어려운 질문은 비싸게 처리합니다.

**페이지 전체가 필요한 과제(spotting, 전체 받아쓰기):** 질문으로 거를 게 없으므로, 글자가 있는 조각을 모두 고르는 경우가 됩니다. 이득은 여백 조각만큼입니다.

## 3. vLLM 프리픽스 캐싱과의 관계

**걱정할 점이 맞습니다.** 지금 방식은 이미 캐싱으로 이득을 보고 있어서, 새 방식이 항상 빠르지는 않습니다.

**지금 방식:** 고해상도 이미지(약 3,600토큰)를 질문 앞에 둡니다. 같은 이미지에 질문이 N번 오면 이미지는 처음 한 번만 계산하고, 나머지는 캐시에서 읽습니다. 이미지 비용이 N개 질문에 나뉩니다.

**새 방식:**

| 호출 | 입력 순서 | 캐시 |
|---|---|---|
| 1차 (볼 곳) | 훑어본 이미지 → 질문 | 훑어본 이미지는 같은 페이지의 모든 질문이 공유 → 캐시됨 |
| 2차 (답) | 훑어본 이미지 → 조각들 → 질문 | 훑어본 이미지 부분은 1차와 같은 프리픽스라 캐시됨. **조각부터는 질문마다 달라 대부분 새로 계산** |

**비용 비교 (같은 이미지에 질문 N개)**
- 지금: 3,600 (한 번) + N × (질문 + 답)
- 새 방식: 약 400 (한 번) + N × (질문 2번 + 조각 번호 출력 + 조각 토큰 + 답)

**질문이 적을수록 새 방식이 유리하고, 한 이미지에 따로 묻는 질문이 아주 많으면 지금 방식이 유리할 수 있습니다.**
- **새 방식이 크게 이기는 곳:** 은행 업무처럼 **서류 여러 장에 질문 하나**인 문항(서류 구비 확인, 서류 대조, 심사 질의)입니다. 장마다 3,600토큰씩 들어가고 재사용도 적습니다. 첫 질문의 지연도 크게 줄어듭니다.
- **조심할 곳:** 한 페이지에 질문을 수십 번 따로 하는 경우입니다. 다만 정보 추출은 이미 항목 목록을 한 질문에 묶어서 묻습니다.

**캐시를 살리는 설계**
- **순서:** 공유되는 것(훑어본 이미지)을 항상 맨 앞에, 질문마다 다른 것(조각, 질문)을 뒤에 둡니다.
- **질문 묶기:** 같은 페이지에 질문이 여러 개 동시에 오면, 1차에서 필요한 조각을 한 번에 고르고 2차를 묶어서 처리합니다.
- **조각 정렬:** 고정 격자 조각을 번호 순으로 넣어 같은 조각 조합이 같은 프리픽스가 되게 합니다.
- **인코더 출력 재사용:** 같은 조각 이미지의 인코더 출력을 vLLM이 요청 간에 재사용하는지는 버전에 따라 다르므로 직접 확인합니다(0단계).

**그래서 측정은 실제 사용 패턴으로 합니다.** 캐시가 빈 상태(첫 질문)와 찬 상태, 이미지당 질문 수 N을 바꿔 가며 문항당 지연과 서류당 GPU 시간을 잽니다. 결과는 "N이 얼마 이하면 새 방식이 빠르다"는 형태로 냅니다.

## 4. 데이터: 두 종류를 모두 쓰고, 생성 데이터로 OCR 파이프라인도 채움

| 데이터 | 형식 | 쓰임 |
|---|---|---|
| **내부 OCR** (1만 장 이상) | 실제 이미지 + 사내 OCR 단어 박스 → `bank_ocr prepare` | OCR 과제 학습 · 평가의 중심. 실제 분포 |
| **생성 → OCR 형식** | 생성 이미지 + **모든 글자의 단어 박스**를 사내 OCR 형식 JSON으로 → `bank_ocr prepare` | OCR 과제 학습 보강. 박스가 정확함 |
| **생성 → 은행 업무** | `docgen.bench build` 그대로 | 은행 업무 과제 학습 · 평가 |

**생성 데이터를 OCR 형식으로 바꾸려면 보강이 필요합니다.**
- 지금 변환(`guide/examples/labels_to_ocr.py`)은 값 칸과 항목명만 넣고 제목, 안내 문구, 약관 같은 고정 글자가 빠져 있습니다. spotting 정답이 불완전합니다.
- 생성기는 Chromium으로 렌더링하므로(`docgen/image.py`), 렌더링 시 페이지의 모든 글자를 **단어 단위**로 박스를 뽑도록 추가합니다. 사내 OCR과 같은 단위입니다.
- 실제 스캔과의 차이는 생성기의 스캔 · 촬영 · 팩스 증강(`docgen/augment.py`)으로 줄이고, 섞는 비율을 실험 변수로 둡니다.

**모든 과제에 "볼 곳" 정답을 붙입니다.** 볼 곳 = 정답에 필요한 박스와 겹치는 조각입니다.

| 데이터 · 과제 | 볼 곳의 근거 |
|---|---|
| OCR: grounding, relation | 정답 박스 (relation은 기준 글자 + 옆 글자) |
| OCR: bbox_ocr, marked_ocr, marked_box, region_ocr | 질문에 준 박스 · 영역 |
| OCR: crop_ocr | 이미 잘린 이미지라 해당 없음 (자세히 보기 단계의 성능 확인용) |
| OCR: spotting | 글자가 있는 모든 조각 |
| 은행: 정보 추출, 체크 · 도장 · 서명 | 묻는 항목의 값 칸 · 체크박스 · 도장 박스 (생성 라벨) |
| 은행: 서류 대조, 심사 질의 | 비교 · 계산에 쓰는 항목들의 박스 (meta의 항목 키 → 라벨 박스) |
| 은행: 서류 분류, 서류 구비 확인 | 제목 영역. **훑어보기만으로 충분한지가 실험 대상** |

## 5. 연구 단계

| 단계 | 내용 | 결정 |
|---|---|---|
| **0. 기반** | ① 생성기에 단어 단위 전체 글자 박스 추가 → OCR 형식 변환 → prepare ② 모든 과제에 볼 곳(조각 번호) 정답 붙이기 ③ 훑어보기 + 조각 입력을 만드는 코드 ④ vLLM에서 지연(첫 토큰까지, 디코딩)과 캐시 적중을 기록하는 측정 도구 | - |
| **1. 정답 볼 곳으로 상한 확인** | **학습 없이** 지금 SFT 모델에 "훑어보기 + 정답 조각"을 넣어 성능과 토큰을 전체 고해상도와 비교. 조각 크기, 겹침, 훑어보기 해상도를 바꿔 봄 | **가설의 1차 검증.** 정답 조각으로도 안 되면 입력 형식부터 다시 설계 |
| **2. 입력 형식 학습** | "훑어보기 + 조각" 형식으로 VLM 미세조정(전체 또는 LoRA). 내부 OCR + 생성 데이터 전부 | 정답 조각 기준 성능이 전체 고해상도와 같아지는지 |
| **3. 볼 곳 정하기 학습** | (가) 같은 VLM이 질문 → 조각 번호를 답하도록 학습(2와 함께 학습 가능). 조각 재현율, "안 봐도 됨" 판단 정확도, 실제 성능 | 주 방법 확정. 필요하면 (나) 판별기와 비교 |
| **4. 넓게 보기 정책** | 확신이 낮을 때 조각 추가 · 전체 보기. 정확도와 평균 비용 곡선 | 운영 기준값 결정 |
| **5. 실사용 측정** | vLLM에서 캐시 빈 상태 / 찬 상태, 이미지당 질문 수 N별 지연과 서류당 GPU 시간. OCR 과제와 은행 업무 다중 이미지 문항 | 최종 결과: 언제, 얼마나 빠른가 |

## 6. 비교 기준과 지표

**비교 기준**
- 전체 고해상도 1회 (지금 방식)
- 저해상도만 (훑어보기만)
- 전체를 조각으로 나눠 모두 넣기
- 여백 조각만 빼기 (질문과 무관하게)
- 정답 볼 곳 사용 (상한)

**지표**
- **성능 (과제별):** 글자 CER · 완전 일치율, 좌표 IoU≥0.5 F1 · 평균 IoU, 은행 업무 점수
- **볼 곳 정하기:** 필요한 조각 재현율(놓치면 바로 오답), 고른 조각 수, "안 봐도 됨" 정확도
- **비용:** 문항당 총 비전 토큰, 첫 토큰까지 시간, 전체 지연(호출 2번 포함), 처리량, 캐시 적중률
- **판정:** 과제별 성능 하락 1%p 이내에서 문항당 지연 또는 서류당 GPU 시간이 의미 있게 줄면 가설 성립. 이미지당 질문 수 N에 따른 손익분기점을 함께 보고

## 7. 폴더 구조 (예정)

```
research/vision-efficiency/
  README.md       이 문서
  NOTES.md        실험 기록 (날짜, 설정, 결과, 결론)
  data/           생성 데이터 → OCR 형식(단어 박스), 볼 곳 정답 붙이기
  glance/         훑어보기 + 조각 입력 만들기, 조각 번호 ↔ 좌표 변환
  measure/        vLLM 예측 + 지연 · 캐시 기록, 원래 좌표로 되돌려 채점, 비교표
  train/          입력 형식 + 볼 곳 정하기 학습 설정
```

`training/`은 OCR 브랜치(`claude/bank-ocr-pipeline`)와 같은 코드라 직접 고치지 않습니다. 연구 코드는 이 폴더에서 `training/bank_ocr`, `docgen`을 가져다 씁니다. 생성기 수정(단어 박스 추출)은 `docgen/`에 기능을 추가하는 방식으로 하고, 기존 출력은 바꾸지 않습니다.

## 8. 실행 환경

- 실제 실험은 내부망의 서류 이미지 · 사내 OCR 결과 · SFT 모델 · vLLM으로 합니다.
- 이 저장소의 합성 예시 데이터(`guide/examples/make_examples.sh`)로는 코드가 돌아가는지만 확인합니다.
- 실험 기록에 남기는 숫자는 내부망 실측 값만 씁니다.
