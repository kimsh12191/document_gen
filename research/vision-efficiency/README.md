# 연구: 문서 VLM에 모든 비전 토큰이 필요한가

> **핵심 가설:** 서류 이미지의 비전 토큰이 전부 필요하지는 않다. 필요 없는 토큰을 빼면 **추론은 빨라지고 성능은 그대로**다.

브랜치 `claude/vision-token-efficiency` (출발점: `claude/ocr-banking-benchmark`의 1부 OCR 학습 코드와 데이터)

## 1. 배경

### 왜 이 질문인가

- 1부 OCR 학습 후에도 좌표 밀림과 글자 오독이 남습니다. 원인은 주로 글자가 입력에서 너무 작은 것(픽셀 부족)과 인코더의 구분 능력입니다.
- 해상도를 올리면 좋아지지만, 실제 응용에서는 추론 속도가 중요해서 무작정 올릴 수 없습니다.
- 그런데 서식 문서는 대부분 여백입니다. **여백에 쓰는 토큰이 필요 없다면**, 그만큼 빨라지고 그 예산을 글자에 돌릴 수도 있습니다.
- 이 연구는 그 전제, 즉 "빼도 성능이 그대로인가"부터 확인합니다.

### 현재 설정 (출발점)

| 항목 | 값 | 위치 |
|---|---|---|
| 모델 | Qwen3.5-9B (`model_type: qwen3_5`) | `training/configs/sft.yaml` |
| 이미지 크기 | 긴 변 2300 · 짧은 변 1600 이하로 축소 | `image_max_size`, `training/bank_ocr/pipeline.py` |
| 비전 토큰 | 토큰 하나 ≈ 32×32px, 페이지 한 장 ≈ 3,600토큰 | `training/train.py` (`IMAGE_MAX_TOKEN_NUM`) |
| 인코더 학습 | LoRA rank 32 (`all-linear`, `freeze_vit: false`) | `training/configs/sft.yaml` |
| 서빙 | ms-swift + vLLM, `IMAGE_MAX_TOKEN_NUM`으로 해상도 고정 | `training/run_pipeline.py` |
| 평가 | 예측과 점수만 기록, **지연 시간은 기록 안 함** | `training/bank_ocr/inference.py` |

비전 토큰 수는 인코더 시간, 언어 모델 prefill, KV 메모리를 함께 정합니다. 토큰을 빼면 이 셋이 줄어듭니다. 디코딩(답 생성) 시간은 줄지 않으므로, 답이 긴 과제(spotting 등)는 이득이 작고 이미지가 많은 문항(은행 업무)은 이득이 큽니다.

## 2. "필요 없는 토큰"의 정의

**잉크가 없는 32×32 패치**를 필요 없는 토큰으로 봅니다. 패치 안의 픽셀 밝기 분산이 기준값보다 작은 패치입니다.

- OCR 박스가 아니라 잉크로 정하는 이유: **글자 외의 표시도 자동으로 남기기 위해서**입니다. 표 선, 체크박스, 도장, 서명은 잉크가 있으니 남고, 빈 칸 안쪽 같은 순수 여백만 빠집니다. 빈 칸도 테두리는 남으므로 "비어 있다"는 판단은 가능합니다.
- 기준값과 패치 주변 여유(잉크 패치 주변 몇 칸을 같이 남길지)는 실험 변수입니다.

## 3. 실험

### 실험 1: 뺄 수 있는 토큰이 얼마나 되나 (모델 없음)

- prepared의 views 이미지에서 잉크 없는 패치 비율 r을 서류 종류별로 셉니다.
- **산출물:** 서류 종류별 r 분포. 이 값이 속도 이득의 상한입니다. r이 작으면 연구를 여기서 멈춥니다.

### 실험 2: 빼면 성능이 그대로인가 (핵심)

**같은 배율**(글자 크기 그대로)에서 토큰만 줄인 입력을 만들어, 원래 입력과 비교합니다.

**토큰을 빼는 방법 두 가지**

| 방법 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **(가) 빈 띠 제거** | 잉크 없는 가로 · 세로 띠를 잘라 내고 나머지를 이어 붙여 한 장으로 만듦 | 모델 · 서빙 변경 없음. 좌표를 구간별로 정확히 되돌릴 수 있음 | 띠 단위라 칸이 빽빽한 표에서는 덜 빠짐. 배치가 바뀌어 보임 |
| **(나) 모델 안에서 토큰 제거** | 원래 이미지를 인코딩한 뒤, 언어 모델에 넣기 전에 잉크 없는 패치의 토큰을 뺌. 위치 정보(M-RoPE 위치 id)는 원래 값 유지 | 패치 단위라 더 많이 빠짐. 배치가 그대로 | 모델 코드 수정 필요, vLLM 지원 확인 필요. 인코더 시간은 그대로 |

(가)부터 합니다. 서빙을 바꾸지 않고 바로 잴 수 있어서입니다. (나)는 (가)에서 배치 변화 때문에 성능이 떨어질 때 원인을 가르는 비교군으로 씁니다.

**좌표 처리 (가):** 질문에 들어가는 박스(bbox_ocr, marked 등)는 줄인 이미지 좌표로 바꿔 넣고, 모델이 답한 박스는 원래 페이지 좌표로 되돌려 채점합니다. 정답과 채점 코드는 그대로 씁니다.

**비교 조건**

| 조건 | 입력 | 학습 |
|---|---|---|
| 기준 | 원래 views | 지금 SFT 모델 |
| 2-1 | 빈 띠 제거 views | 지금 SFT 모델 (추가 학습 없음) |
| 2-2 | 빈 띠 제거 views | 빈 띠 제거 입력으로 짧게 추가 SFT |

2-1에서 성능이 그대로면 바로 결론이 납니다. 떨어지면 2-2로, 모델이 입력 형식에 익숙하지 않아서인지 정말 정보가 빠져서인지를 가릅니다.

**측정 (과제별)**

- **성능:** 글자 CER · 완전 일치율 (crop_ocr · bbox_ocr · region_ocr · spotting), 좌표 IoU≥0.5 F1 · 평균 IoU (grounding · spotting · marked_box · relation)
- **속도:** 페이지당 비전 토큰 수, 문항당 지연을 인코더+prefill(첫 토큰까지 시간)과 디코딩으로 나눠 기록, 같은 GPU · 같은 동시 요청 수에서의 처리량
- **측정 조건 고정:** GPU 종류, vLLM · ms-swift 버전, 동시 요청 수, `max_tokens`, 같은 benchmark 문항. 실험 기록마다 함께 저장합니다.

**판정 기준:** 비전 토큰 30% 이상 감소, 첫 토큰까지 시간 의미 있게 감소, **과제별 성능 하락 1%p 이내**면 가설 성립.

### 실험 3: 어디까지 뺄 수 있나

- 잉크 기준값과 주변 여유를 바꿔 가며 토큰 감소율과 성능의 관계를 그립니다.
- 성능이 꺾이기 시작하는 지점에서 빠진 토큰이 무엇이었는지(선, 작은 점, 흐린 글자 등) 확인합니다. 이것이 "필요한 토큰"의 실제 정의가 됩니다.

## 4. 그다음 (가설이 성립하면)

- **확대에 재투자:** 아낀 토큰으로 글자 영역의 배율을 올립니다. 같은 토큰에서 좌표 · 오독 오류가 줄어드는지 봅니다. 원래 문제(픽셀 부족)를 푸는 단계입니다.
- **은행 업무 문항:** 서류 여러 장이 들어가는 2부 문항에 적용합니다. 토큰 예산이 장마다 나뉘는 곳이라 이득이 가장 클 것으로 봅니다.
- **인코더 학습:** 확대해도 남는 오류(크게 보여 줘도 비슷한 글자를 틀림)를 보고 인코더 전체 학습 여부를 정합니다.

## 5. 폴더 구조 (예정)

```
research/vision-efficiency/
  README.md     이 문서
  NOTES.md      실험 기록 (날짜, 설정, 결과, 결론)
  ink.py        잉크 없는 패치 찾기, 서류별 비율 (실험 1)
  trim.py       빈 띠 제거 이미지 + 좌표 변환 (실험 2 (가))
  make_tasks.py benchmark 문항을 줄인 이미지 기준으로 다시 쓰기
  measure.py    예측 + 지연 기록, 원래 좌표로 되돌려 채점, 비교표
```

`training/`은 OCR 브랜치(`claude/bank-ocr-pipeline`)와 같은 코드라 직접 고치지 않습니다. 연구 코드는 이 폴더에서 `training/bank_ocr`를 가져다 씁니다.

## 6. 데이터와 실행 환경

- 실제 실험은 내부망의 서류 이미지와 사내 OCR 결과, 1부 SFT 모델로 합니다(1부와 같은 prepared 폴더).
- 이 저장소의 합성 예시 데이터(`guide/examples/make_examples.sh`)로는 코드가 돌아가는지만 확인합니다.
- 실험 기록에 남기는 숫자는 내부망 실측 값만 씁니다.
