# 은행 업무 VLM 프로젝트 소개

팀 내부 개발자용으로, 무엇을 만들었고 왜 그렇게 설계했는지 정리한 문서입니다. 생성기와 벤치마크의 세부 내용은 맨 뒤 부록에 있습니다.

- [부록 A. 합성 데이터 생성기 상세](#부록-a-합성-데이터-생성기-docgen-상세)
- [부록 B. 벤치마크 설계 상세](#부록-b-벤치마크-설계-상세)

## 1. 한 장 요약

**목표:** VLM(Qwen3.5-9B)이 은행 창구·심사 담당자가 하는 서류 업무를 하도록 학습시킵니다.

| 업무 | 모델이 하는 일 |
|---|---|
| 서류 구비 확인 | 고객이 낸 서류 묶음에서 빠진 서류, 필요 없는 서류, 다른 사람 서류 찾기 |
| 서류 대조 | 서류 2~3건을 맞대어 불일치 찾기 (오기, 타인 서류, 소득 부풀리기, 임대인≠등기부 소유자 등) |
| 심사 질의 | LTV, 소득 대비 배수, 만 나이, 서류 유효기간 같은 질문에 숫자나 예/아니오로 답하기 |
| 정보 추출 | 서류에서 항목 값 뽑기 (+ 체크박스·도장·서명, 서류 분류, 글자 읽기) |

**왜 합성 데이터인가:** 실제 고객 서류는 학습에 쓸 수 없고, 정답(어느 칸에 무슨 값이 있는지, 어디가 틀렸는지)을 사람이 다는 비용도 큽니다. 그래서 서류를 직접 생성해 정답을 공짜로 얻고, 불일치도 일부러 만들어 넣습니다.

**구성 (4단계)**

```text
① 합성 서류 생성기 docgen      서류 476종, 고객 단위 서류 묶음, 정답 자동 기록         (CPU, 도커)
② OCR 학습                    실제 서류 이미지 + 내부 OCR 결과로 글자·위치 읽기       (GPU, SFT → GRPO)
③ 은행 업무 학습               ②의 모델에서 출발, docgen 데이터로 업무 학습            (GPU, SFT → GRPO)
④ 벤치마크 비교               같은 평가 세트로 출발·SFT·GRPO 모델 비교 + viewer
```

**코드 위치**

| 무엇 | 위치 | 브랜치 |
|---|---|---|
| 생성기·벤치마크 | `docgen/`, `docgen/bench/` | `claude/ocr-banking-benchmark` |
| OCR 학습 | `training/` (`run_pipeline.py`, `bank_ocr/`) | `claude/bank-ocr-pipeline` (은행 브랜치의 `training/`에 같은 코드) |
| 은행 업무 학습 | `training/` (`run_bank_pipeline.py`, `bank_task/`) | `claude/ocr-banking-benchmark` |
| viewer | `training/viewer/` (`bank_*` = 은행 업무, 나머지 = OCR) | 〃 |
| 사용 가이드 | `guide/` | 〃 |

## 2. 합성 데이터 생성기 (docgen)

고객이 은행에 내는 서류 **476종**을 만듭니다. 세부 내용은 [부록 A](#부록-a-합성-데이터-생성기-docgen-상세)에 있습니다.

- **두 가지 방식:**
  - HTML 템플릿 70종: 신분증, 등본, 소득·세금 서류, 등기부, 계약서, 은행 서식 등
  - 하나은행 공개 서식 PDF 406종: 원본 위에 손글씨·인쇄체로 값을 얹습니다
- **정답과 이미지가 어긋나지 않습니다.** 화면에 찍힌 문자열을 그대로 정답으로 기록하고, 위치(박스)도 함께 남깁니다.
- **고객 단위로 서류끼리 값이 맞습니다.** 이름·주민번호·주소·소득·부동산·대출금이 서류 사이에 일관됩니다. 그래서 "서류 대조"처럼 여러 서류를 보는 과제를 만들 수 있습니다.
- **업무 12종의 서류 묶음:** 계좌개설, 신용대출, 주택담보대출, 전세자금대출, 법인 여신, 해외송금 등입니다. 업무별 필수 서류 목록으로 묶음을 만듭니다.
- **실제처럼 다양하게 만듭니다:** 여러 쪽 서류, 말소·개명·정정 같은 특수 상황, 스캔·촬영·팩스 증강, 글꼴·선·여백 무작위
- **재현성:** 같은 설정이면 언제, 몇 프로세스로 만들어도 같은 데이터가 나옵니다.

## 3. 벤치마크 설계

같은 생성기로 **고정된 평가 세트 약 9천 문항**을 만들어 모델을 비교합니다. 세부 내용은 [부록 B](#부록-b-벤치마크-설계-상세)에 있습니다.

- **과제 8종, 3개 영역:**
  - OCR: 값 칸 읽기, 전체 받아쓰기
  - 문서 이해: 분류, 정보 추출, 체크·도장·서명
  - 은행 업무: 서류 구비 확인, 서류 대조, 심사 질의
- **불일치 14종:** 전세사기, 업계약, 작업대출, 명의도용 같은 실제 사고 유형을 근거로 골랐습니다.
- **변조 방식:** 값 **하나만** 바꿔 다시 렌더링합니다. 같은 서류 조합의 정상 문항과 짝을 지어 냅니다.
- **학습과 평가의 고객 분리:** seed 범위를 나눠 학습 데이터와 평가 세트에 같은 고객이 나오지 않습니다.
- **채점은 규칙 기반입니다.** 날짜·금액·번호는 표기 방식을 맞춘 뒤 비교합니다. 사람이나 LLM 판정이 없어 결과가 늘 같습니다.
- **찍어도 나오는 점수를 따로 봅니다.** 서류 대조는 "문제없음"만 답해도 약 60%가 나옵니다. 그래서 "위치 정확도(변조 문항에서 서류·값까지 짚은 비율)"를 함께 봅니다.

## 4. 학습 파이프라인

```bash
python run_bank_pipeline.py --config configs/bank_pipeline.json     # prepare → 평가 → SFT → 평가 → 선정 → GRPO → 평가 → 비교표
```

한 명령으로 끝까지 돌고, 멈추면 같은 명령으로 끝난 단계부터 이어서 갑니다(`state.json`). 구조는 OCR 단계의 `run_pipeline.py`를 그대로 물려받았고, 데이터·채점·보고서만 바꿨습니다.

**prepare: docgen 데이터를 학습 형식으로 바꿉니다**
- **이미지 토큰 예산:** 한 장은 2300×1600 이하(약 3600토큰)입니다. 한 문항에 이미지가 최대 13장이라 합계 12,000토큰을 넘지 않게 장마다 같은 비율로 줄입니다. 평가도 같은 규칙이라 학습과 평가가 같은 픽셀을 봅니다.
- **묶음 학습:** 같은 이미지에 대한 질문(분류, 추출, 체크 등)은 한 대화로 묶어 이미지를 한 번만 처리합니다.
- **GRPO 몫 떼기:** 고객 20%의 문항은 SFT에서 빼고 GRPO용으로 둡니다. SFT에서 본 문제로 GRPO를 하면 학습 신호가 약하기 때문입니다.
- **OCR 데이터 섞기:** OCR 단계 학습 데이터 3000개를 섞어 글자 읽기 능력을 잊지 않게 합니다.
- **검사:**
  - 학습 데이터와 평가 세트에 같은 고객이 있으면 멈춥니다.
  - 정답을 모델 출력 형식으로 쓴 답이 채점기에서 만점이 나오는지 확인합니다.
- **과제 비율:** `task_mix`로 SFT 2만 문항을 뽑습니다. 서류 대조 25%, 심사 질의 20%, 정보 추출 15% 등입니다.

**SFT:** OCR 모델(병합본)에 새 LoRA(rank 32)를 붙여 1 epoch 학습합니다.

**GRPO**
- **보상 = 평가 채점기 그대로**(`bank_task/score.py`): 정답이 분명해서 OCR 단계의 의사정답보다 신호가 깨끗합니다.
- **부분 점수:** 전부 맞거나 전부 틀리기 쉬운 과제는 부분 점수를 줍니다. 0점 아니면 1점만 있으면 답 여러 개의 점수가 같아져 학습 신호가 없어지기 때문입니다.
  - 서류 구비 확인: 0.5 × 완전 일치 + 0.5 × F1
  - 서류 대조 변조 문항: 0.5 × (불일치라고 함) + 0.5 × (서류·값까지 짚음)
- **어려운 문제 고르기:** SFT 평가 때 띄운 서버로 후보 3000문제를 풀고, SFT가 틀린 문제(보상 0.9 미만)를 절반 섞어 1000문제를 고릅니다.
- **대상 과제:** 서류 대조, 심사 질의, 서류 구비 확인, 정보 추출 중 이미지 4장 이하 문항만 씁니다. 메모리 때문입니다.

**평가**
- 학습한 LoRA를 병합한 모델로 GPU마다 vLLM 서버를 하나씩 띄우고 문항을 나눠 보냅니다.
- 같은 서버로 OCR 단계 벤치마크 1000문항도 함께 풀어 OCR 능력이 유지됐는지 봅니다.

**결과물:** `reports/benchmark.html`
- 모델별 점수와 출발 모델 대비 변화
- 답 형식 오류 비율
- 불일치 사례별·심사 질의 능력별·서식별 세부 표
- `ocr_retention.html`: OCR 능력 유지 여부

## 5. 도구와 문서

- **viewer** (`bash viewer/bank_start.sh`, 포트 7861)
  - 문항마다 모델들의 답을 정답과 나란히 봅니다. 항목별로 맞으면 초록, 틀리면 빨강입니다. 서류 이미지에는 이름·쪽·변조 사본 표시가 붙습니다.
  - "SFT는 맞히고 출발 모델은 틀린 문제"처럼 좋아진 문제나 나빠진 문제만 걸러 봅니다.
  - 내 서류(이미지·PDF)를 올려 학습한 질문 문장 그대로 물어봅니다. 이미지 크기도 학습과 같은 규칙으로 줄입니다.
  - 저장된 답만 보는 모드는 GPU가 필요 없습니다.
- **guide/**
  - `questions.md`: 질문 문장과 답 형식. 테스트가 코드의 질문 문장과 같은지 확인합니다.
  - `fields/`: 서류별 항목 키와 체크박스 보기
  - `results.md`: 결과 읽는 법과 이상 신호
- **데이터 생성 스크립트:** `scripts/make_bank_data.sh`를 도커 안에서 한 번 실행하면 평가 세트와 학습 데이터를 만듭니다. 백그라운드로 돌고 중간에 멈추면 이어서 만듭니다.

## 8. 한계와 다음 단계

- **합성 서류라 점수가 높게 나옵니다.** 학습 데이터와 평가 세트는 고객만 다르고 서식·질문·변조 방식이 같습니다. **실제 서류 검증 세트**(소량, 사람이 정답 작성)가 다음 단계에서 가장 중요합니다.
- **서류 대조는 한 질문에 불일치를 1개까지만** 학습했습니다. 불일치가 여러 개인 문항이 필요합니다.
- **알려진 데이터 문제:**
  - 법인등기부 발행일이 날짜가 아니라 글자로 채점됩니다.
  - 하나은행 원본 서식은 정보 추출 정답의 약 절반이 빈 칸입니다. 다만 주 지표인 F1은 빈 칸 때문에 부풀지 않습니다.
- **생성기 한계:**
  - 증강이 단순합니다. 원근 왜곡이나 구겨짐이 없습니다.
  - 손글씨 글꼴이 4종뿐입니다.
  - 원본 서식은 칸 인식이 일부 틀립니다.
  - 한 고객이 근로자·개인사업자·법인 대표를 겸하는 조합이 나옵니다.

| 하나은행 원본 서식 | 406 | 하나은행 공개 서식 PDF (FATCA 확인서, 각종 동의서·신청서 등) |

전체 목록은 [documents.md](documents.md), 서류별 항목은 [fields/](fields/README.md)에 있습니다.

### A-2. 만드는 방식

**HTML 템플릿 (70종)**
- 서식마다 Jinja2 템플릿과 값 생성 함수를 둡니다.
- 템플릿의 값은 모두 `f("경로")`로 찍습니다. 이렇게 찍은 문자열이 그대로 정답이 되고, 위치(박스)도 렌더링에서 함께 뽑습니다. 그래서 정답과 이미지가 어긋날 수 없습니다.
- 서식 구성은 법령 별지 서식, 은행연합회 표준, 공공기관 발급본을 웹 검색으로 교차 확인해 맞췄습니다. 근거는 `docs/REALISM_STATUS.md`에 있습니다.
- 은행 서식은 은행별 표기(은행명, 서식번호 줄, 결재란, 인쇄색)가 다르게 나옵니다. 옛 은행(KEB하나, 외환) 서식은 그 시기 날짜·제도로 만듭니다.

**하나은행 원본 서식 (406종)**
1. **기재 자리 찾기:** PDF의 글자 위치·색과 표 선에서 고객이 쓰는 칸을 찾습니다. 대상은 빈 칸, `□` 보기, `년 월 일`, `(서명 또는 인)`, 자필 기재란입니다.
2. **값 채우기:** 항목명으로 값을 정합니다.
   - 성명·주소·계좌 등은 고객 프로필에서 가져와 다른 서류와 맞춥니다.
   - 서식 고유 항목은 항목명으로 종류만 추론합니다.
   - 뜻을 모르는 칸은 비워 둡니다.
3. **그리기:** 원본 PDF 이미지를 배경으로 깔고 값을 절대 위치로 얹습니다.
   - 글씨: 서류마다 손글씨 70%(글꼴 4종, 글자마다 기울기·흔들림), 인쇄체 30%
   - 체크 표시: V, ■, ○ 중 하나

### A-3. 고객 프로필과 일관성

- 고객 한 명의 프로필에 본인·가족·직장·사업체·법인·부동산·계좌·해외 거래처가 들어 있습니다. 같은 프로필로 만든 서류들은 값이 서로 맞습니다.
  - 급여명세서 실수령액 = 통장 급여 입금액
  - 등기부 근저당 = 대출 약정
  - 상호 변경일 = 등기부·정관·사업자등록증에서 같음
- **숫자 정합성:** 합계, 세액(누진세율·4대보험), 잔액 흐름, 대차대조(자산=부채+자본), 환율 환산, 한글 금액(`금 이억일천사백만원정`)을 계산으로 맞춥니다.
- **식별번호:** 주민·사업자·법인등록번호는 체크섬까지 맞는 형식입니다(값은 무작위). 여권 MRZ도 체크디지트를 맞춥니다.
- **위조 방지:** 신분증·여권·인감증명서 등에는 항상 "견본 SAMPLE" 워터마크를 넣습니다. 실제 기관 로고·관인은 넣지 않습니다.

### A-4. 다양성

### B-2. 서류 구비 확인 (`doc_check`) 문항 만들기

1. 업무 묶음의 필수 서류 중 0 / 1 / 2건을 뺍니다. 비율은 30 / 50 / 20%입니다.
2. 30%는 제출 서류 하나를 **다른 고객의 같은 서류**로 바꿉니다. 그 서류는 `not_customer`이면서 `missing`에도 들어갑니다. 본인 서류는 안 낸 것이기 때문입니다.
3. 35%는 **다른 업무의 서류** 한 건을 끼워 넣습니다(`not_required`).
4. 남은 서류의 **첫 쪽만** 순서를 섞어 이미지로 줍니다. 질문에는 고객 성명, 업무명, 필수 서류 목록이 들어갑니다.

**채점**
- 세 목록이 모두 맞아야 완전 일치입니다. 목록별 일치율과 F1도 함께 봅니다.
- 모델이 쓴 서류명은 후보 서류명에 비슷한 이름으로 대응시킵니다. 예를 들어 "원천징수영수증"은 "근로소득 원천징수영수증"으로 인정합니다.

### B-3. 서류 대조 (`cross_check`) 문항 만들기

**불일치 14종** (실제 심사·금융사고 사례 기반, 근거 자료는 [benchmark.md](benchmark.md#참고-자료))

| 사례 | 분류 | 무엇을 바꾸나 | 실제 사례 |
|---|---|---|---|
| `typo` | 오기 | 여러 서류에 나오는 성명·주민번호·연락처·주소·계좌·생년월일 한 자리 | 신청서·약정서 기재 오류 |
| `other_person` | 타인 서류 | 신분증·등본·재직증명서·소득서류 등 한 건을 다른 고객 것으로 | 명의도용, 가족 서류 혼입 |
| `loan_vs_agreement` | 금액 | 신청서 또는 약정서의 대출금액 | 약정서 작성 오류·변조 |
| `income_inflated` | 금액 | 원천징수영수증 급여를 20~60% 부풀림 → 소득금액증명원과 불일치 | 작업대출: 소득 서류 위·변조 |
| `lease_owner` | 관계 | 등기부 소유자를 다른 사람으로 → 임대인 ≠ 소유자 | 전세사기 |
| `seller_owner` | 관계 | 등기부 소유자를 다른 사람으로 → 매도인 ≠ 소유자 | 무권리자 매도 |
| `hire_date` | 관계 | 재직증명서 입사일을 1~4년 앞당김 → 건강보험 취득일과 불일치 | 작업대출: 재직기간 부풀리기 |
| `rep_director` | 관계 | 법인인감증명서 대표자를 다른 사람으로 | 권한 없는 자의 신청 |
| `contract_before_apply` | 관계 | 약정일을 신청일보다 앞으로 | 서류 소급 작성 |
| `collateral_short` | 관계 | 채권최고액을 대출금의 60~95%로 | 근저당 설정 금액 부족 |
| `jeonse_over` | 관계 | 전세대출 신청금액을 보증금의 105~130%로 | 보증금 부풀리기 |
| `sales_sum` | 관계 | 매매대금을 8~25% 올림 → 계약금+중도금+잔금과 불일치 | 업계약 |
| `fx_beneficiary` | 관계 | 송금 수취인을 다른 회사로 → 송장 수출자와 불일치 | 증빙과 다른 상대방에게 송금 |
| `format_only` | 정상 | 같은 값을 다른 표기로(날짜 형식, 하이픈, 주민번호 뒷자리 가림) | 오탐 방지 |

**만드는 순서**
1. **원본 확인:** 사례마다 원본 서류에서 그 관계가 실제로 맞는지 먼저 확인합니다(예: 임대인 = 등기부 소유자). 맞지 않는 묶음에서는 그 사례를 만들지 않습니다. 생성기 자체의 우연한 불일치가 정답을 오염시키지 않게 하려는 것입니다.
2. **변조와 정상 짝:** 50% 확률로 변조하고, 나머지는 같은 서류 조합을 정상 문항으로 냅니다.
3. **값만 바꿔 다시 렌더링:** HTML의 해당 값 칸 글자만 바꾸고, 같은 서류 안에 같은 값이 여러 번 있으면 함께 바꿉니다. 바뀐 서류는 그 값 말고는 원본과 같고 촬영 증강도 같습니다. 타인 서류 사례는 같은 종류 서류를 다른 고객 프로필로 새로 만듭니다.
4. **관련 서류만 보여 줍니다:** 사례에 관련된 서류 2~3건(이미지 10장 이하)만 줍니다. 상관없는 서류에서 생기는 우연한 불일치를 줄이기 위해서입니다.

**채점**
- 정상 문항: `consistent: true`이면 맞습니다.
- 변조 문항: 불일치라고 하고, 문제 서류와 함께 그 값·원래 값·항목명 중 하나를 맞게 짚어야 맞습니다.
  - 관계 사례는 짝 서류를 지목해도 인정합니다. 예를 들어 임대인≠소유자는 계약서와 등기부 어느 쪽을 짚어도 됩니다.
- 따로 보고하는 지표: 탐지(불일치 여부만), 위치(변조 문항에서 서류·값까지), 오탐률(정상 문항을 불일치라고 함), 사례별·분류별 점수

### B-4. 심사 질의 (`review`) 문항 만들기

정답은 서류의 정답 값으로 계산합니다. 질문에 반올림 자릿수, 기준일, 답 형식을 적어 정답이 하나로 정해지게 합니다.

| 규칙 | 업무 | 질문 | 능력 |
|---|---|---|---|
| `ltv` | 주택담보 | 대출신청금액 ÷ 매매대금 (%) | 계산(비율) |
| `collateral_ratio` | 주택담보 | 채권최고액 ÷ 약정 대출금액 (%) | 계산(비율) |
| `jeonse_ratio` | 전세자금 | 대출신청금액 ÷ 임차보증금 (%) | 계산(비율) |
| `income_multiple` | 신용대출 | 대출신청금액 ÷ 원천징수 급여 합계 (배) | 계산(비율) |
| `age` | 신분증+신청서 | 신청일 기준 만 나이 | 날짜 계산 |
| `tenure` | 대출 | 입사일~신청일 만 재직연수 | 날짜 계산 |
| `doc_valid` | 발급일 있는 서류 | 발급 후 90일 이내인가 | 날짜 계산 |
| `net_pay` | 신용대출 | 급여명세서 지급액계 − 공제액계 | 계산(합계) |
| `sales_rest` | 주택담보 | 매매대금 − 계약금 − 중도금 | 계산(합계) |
| `invoice_sum` | 해외송금 | 상업송장 품목 금액 합계 | 표 계산 |
| `tuition_due` | 유학생 송금 | 이전 잔액 + 청구액 − 납부액 | 계산(합계) |
| `debt_ratio` | 법인 여신 | 부채총계 ÷ 자본총계 (%) | 표 계산 |
| `case:<사례>` | 불일치 사례마다 | "임대인이 등기부 소유자와 같은 사람입니까?" 같은 예/아니오 질문 (변조 문항이면 "아니오") | 서류 대조 |

- **90일 이내 질문:** 묶음 서류의 발급일은 대개 신청일과 같아서 그대로 두면 답이 늘 "예"가 됩니다. 그래서 절반은 발급일을 93~400일 앞당긴 사본으로 묻습니다.
- **채점:** 숫자는 `%`·`배`·`원` 같은 단위를 떼고 허용 오차(소수 자릿수 기준) 안이면 정답입니다. 예/아니오는 "네", "아니요"도 알아듣습니다.

### B-5. 공통 채점 규칙

- **값 비교 (`kie` 등):**
  - 날짜: `2025년 9월 20일` = `2025-09-20`
  - 금액: `금 오억원정` = `500,000,000`, 1원 차이도 오답
  - 번호: 숫자만 비교
  - 그 밖: 공백·문장부호 무시
- **답이 없거나 형식이 틀리면 0점입니다.** 빈 답이 빈 칸(`null`)이나 "도장 없음"을 우연히 맞히지 않게 하려는 것입니다. 보고서에 비율이 따로 나옵니다.
- **채점기 점검:** 정답을 그대로 출력으로 넣으면 모든 과제가 100점이어야 합니다. 파이프라인의 prepare가 매번 확인합니다.
- **비교 조건 고정:** 평가 문항이 다르거나 추론 설정(temperature, 이미지 등)이 다른 결과끼리는 비교표 만들기를 거부합니다.
