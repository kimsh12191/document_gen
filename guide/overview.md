## 0. 전체 그림

**목표:** VLM(Qwen3.5-9B)이 은행 서류를 읽고, 창구·심사 담당자가 하는 서류 업무를 하도록 학습시킵니다.

```text
           데이터                                   학습                         결과
1부  실제 서류 이미지 + 내부 OCR 결과  ──▶  OCR 학습 (SFT → GRPO)      ──▶  글자·위치를 읽는 모델
                                                   │ 출발 모델
2부  합성 서류 생성기 docgen           ──▶  은행 업무 학습 (SFT → GRPO) ──▶  서류 업무를 하는 모델
     (서류 476종, 고객 단위 묶음)                                              + 벤치마크 비교표
```

- **두 단계로 나눈 이유:** 은행 업무는 결국 "서류를 정확히 읽는 것" 위에서 돌아갑니다.
  - 1부는 실제 서류로 읽기 능력을 올립니다.
  - 2부는 정답을 마음대로 만들 수 있는 합성 서류로 업무 판단을 가르칩니다.
- **두 단계의 공통 틀:** 한 명령으로 데이터 준비 → 출발 모델 평가 → SFT → 평가 → GRPO 문제 선정 → GRPO → 평가 → 비교표까지 돕니다. 멈추면 같은 명령으로 이어서 갑니다. 2부 파이프라인은 1부 파이프라인 코드를 물려받고 데이터·채점·보고서만 바꿨습니다.

| 무엇 | 위치 | 브랜치 |
|---|---|---|
| OCR 학습 | `ocr/` (`run_pipeline.py`, `bank_ocr/`) | `claude/bank-ocr-pipeline` (이 브랜치의 `ocr/`에 같은 코드) |
| 합성 데이터 생성기, 은행 업무 벤치마크 | `docgen/`, `docgen/bench/` | `claude/ocr-banking-benchmark` |
| 은행 업무 학습 | `bank/` (`run_bank_pipeline.py`, `bank_task/`) | 이 브랜치에만 |
| viewer | `ocr/viewer/start.sh` = OCR, `bank/viewer/bank_start.sh` = 은행 업무 | 〃 |
| 사용 가이드 | `guide/` | 〃 |

## 1부. OCR 학습

### 1-1. 컨셉

- **무엇을 배우나:** 서류 이미지에서 **글자 내용과 위치(박스 좌표)**를 정확히 읽는 능력, 그리고 스캔·촬영 노이즈에 강한 것입니다.
- **정답을 어디서 얻나:**
  - 실제 서류 이미지를 사내 OCR에 돌린 결과를 정답으로 씁니다.
  - 사람이 검수하지 않은 **의사정답**입니다. 그래서 벤치마크 점수도 실제 정답률이 아니라 "사내 OCR과 얼마나 같은지"입니다.
- **과제 8종:** 글자→위치, 위치→글자 양방향을 모두 가르칩니다.

| 과제 | 입력 | 출력 | 배우는 것 |
|---|---|---|---|
| `crop_ocr` | 단어를 잘라낸 이미지 | 글자 | 노이즈 속 글자 인식 |
| `bbox_ocr` | 페이지 + 단어 박스 | 글자 | 좌표 → 내용 |
| `grounding` | 페이지 + 글자 | 그 글자의 **모든** 박스, 없으면 `[]` | 내용 → 좌표, 반복 글자, 없는 글자 |
| `region_ocr` | 페이지 + 여러 단어를 덮는 영역 | 영역 안 글자 전부(줄 단위) | 영역과 읽는 순서 |
| `spotting` | 페이지를 잘라낸 타일 | 모든 글자 + 박스 | 문서 전체 배치 |
| `relation` | 페이지 + 기준 글자 + 방향 | 바로 옆 글자와 박스 | 좌표 사이 관계 (항목명 → 값) |
| `marked_ocr` | 빨강·파랑·초록 박스를 그린 페이지 + 색 | 그 박스 안 글자 | 그림으로 표시한 위치 → 내용 |
| `marked_box` | 같은 이미지 + 색 | 그린 박스 좌표와 글자 | 그림으로 표시한 위치 → 좌표 숫자 |

- **좌표 형식:** Qwen-VL 방식입니다.
  - 좌표는 이미지 기준 0~1000 정수 `[x1, y1, x2, y2]`입니다.
  - 박스 답은 `[{"bbox_2d": [...], "label": "글자"}]`입니다.
- **정답이 불완전한 곳은 안 씁니다.** 영역 안에 신뢰도가 낮은 단어나 잘린 단어가 하나라도 있으면 그 영역은 버립니다. 정답이 조용히 글자를 빠뜨리지 않게 하기 위해서입니다.

### 1-2. 데이터 구조

**입력**

```text
페이지 이미지 (PNG/JPG, PDF는 미리 쪽별 이미지로)
사내 OCR 결과 JSON  {"success": "Y", "data": {"basicData": [[{"text", "confidence", "bounding": {"vertices": [...]}}]]}}
        │  python -m bank_ocr scan
        ▼
data/manifest.jsonl  {"document_id": "doc123", "page_id": "p001", "image": "/share/.../doc123_p001.png", "split": "train", "ocr_json": "..."}
```

- **문서 ID가 중요합니다.** 학습·검증·벤치마크를 **문서 단위**로 나눕니다. 같은 문서의 다른 쪽이 학습과 평가에 갈라져 들어가면 안 되기 때문입니다.
  - 벤치마크: 문서의 10%
  - 검증: 학습 문서의 5%
- **OCR 결과는 캐시합니다.** 이미지 픽셀, OCR 함수, OCR 버전을 키로 저장해서 다시 실행해도 OCR을 재호출하지 않습니다.

**prepare 결과** (`data/prepared-v2/`)

| 파일 | 내용 |
|---|---|
| `pages.jsonl` | 페이지별 OCR 원본: 글자, 픽셀 박스, 0~1000 박스, 신뢰도, split |
| `views/` | 모델 입력 이미지. 긴 변 2300·짧은 변 1600 이하로 줄인 **깨끗한 사본(clean)**과 **노이즈 사본(aug)** |
| `crops/`, `tiles/`, `marked/` | 잘라낸 단어 이미지, spotting 타일, 색 박스를 그린 이미지 |
| `train_sft.jsonl`, `val_sft.jsonl` | ms-swift SFT 입력. 같은 이미지에 대한 질문 최대 8개를 한 대화로 묶음 |
| `train_grpo.jsonl` | GRPO 문제. 보상 계산용 `task`·`target` 포함 |
| `*_tasks.jsonl` | 평가·분석용 문항. `view`(clean/aug), `confidence`, `size` 포함 |
| `DONE.json` | 완료 표시, 분리별 개수, 필터 통계 |

**한 문항의 모양** (`benchmark_tasks.jsonl`)

```json
{"id": "…_v0_grounding_0", "task": "grounding", "document_id": "doc_3", "split": "benchmark",
 "view": "aug", "view_ops": ["scale0.760", "blur"], "reference_type": "ocr_pseudo_unreviewed",
 "images": ["views/…_v0.png"],
 "messages": [{"role": "user", "content": "<image>\n\"DATE\" 와 정확히 같은 글자가 있는 곳을 모두 찾으세요. …"}],
 "target": "{\"boxes\": [{\"bbox_2d\": [50, 500, 200, 600], \"label\": \"DATE\"}, …]}",
 "confidence": 0.99, "size": "medium"}
```

**노이즈 사본 만들기:** 같은 페이지에서 깨끗한 사본 1장과 노이즈 사본 2장(학습 기준)을 만듭니다. 기하 변환은 박스 좌표에도 똑같이 적용합니다.
- 기하: 자르기(각 변 70% 이상 유지), ±1.5° 회전, 여백, 축소
- 화질(1~3개 무작위): 흐림, 흔들림, JPEG 압축, 노이즈, 저해상도 후 확대, 대비·밝기, 그림자, 팩스형 이진화, 흑백

### 1-3. 학습 방법

**SFT**
- **학습 대상:** 원래 모델에 LoRA(rank 32, alpha 64)를 붙이고, 비전 인코더·연결부·언어 모델을 모두 학습합니다.
- **분량:** 최대 3만 문항, learning rate 1e-4, 문항 길이 10,240토큰
- **과제 비율:** crop 10 / bbox 15 / grounding 20 / region 15 / spotting 15 / relation 15 / marked 5+5%
  - grounding의 약 10%는 페이지에 없는 글자를 묻는 문항입니다. 답은 `[]`입니다.
- **묶음 학습:** 같은 이미지에 대한 질문 최대 8개를 한 대화로 묶습니다. 이미지(약 3600토큰)를 한 번만 처리하므로 같은 문항 수를 훨씬 빨리 학습합니다.

**GRPO**
- **대상 과제:** 답이 여러 개라 점수 차이가 잘 생기는 `grounding`, `spotting`, `relation`. 단어 하나짜리 과제는 SFT 뒤 답이 거의 같아져 학습 신호가 없습니다.
- **보상:**
  ```text
  글자 과제 = 0.7 × 문자 유사도 + 0.3 × 숫자 유사도
  박스 과제 = 2 × Σ(짝별 점수) / (예측 박스 수 + 정답 박스 수)
     짝별 점수: grounding = min(1, IoU / 0.8)
                spotting·relation = 0.5 × min(1, IoU / 0.8) + 0.5 × 글자 유사도
     정답이 [] 이면 예측도 [] 일 때 1. JSON 형식 오류는 0
  ```
  - 박스는 IoU 순으로 1:1로 짝짓고, 빠진 박스와 남는 박스는 분모에서 깎습니다. 그래서 박스를 많이 내거나 크게 덮는 꼼수가 통하지 않습니다.
  - IoU 0.8 이상은 만점입니다. 사내 OCR 박스가 얼마나 꽉 맞는지가 일정하지 않아서, 그 이상을 맞추라고 하면 정답 박스의 잡음까지 배우게 됩니다.
- **문제 고르기:** 후보 6000문제를 SFT 모델로 풀고, 보상 0.9 미만인 문제를 절반 섞어 2000문제를 고릅니다.
- **설정:** learning rate 5e-6, beta 0.04, temperature 1.0, 한 문제에 답 8개 생성(40GB 설정은 4개)

### 1-4. 평가 방법

- **벤치마크:** 문서 단위로 떼어 둔 10% 문서로 만든 문항입니다. 깨끗한 사본과 노이즈 사본을 하나씩 씁니다.
- **같은 조건:** Base·SFT·GRPO 모델이 같은 문항, 같은 이미지, 같은 이미지 토큰 예산으로 풉니다. GPU마다 vLLM 서버를 띄우고 학습한 LoRA는 병합해서 씁니다.
- **지표:**

  | 과제 | 지표 |
  |---|---|
  | 글자 과제 | CER(틀린 글자 비율), 완전 일치(EM), 숫자 완전 일치. `region_ocr`은 순서와 무관한 단어 F1도 |
  | 박스 과제 | IoU 0.5 기준 정밀도·재현율·F1, IoU 0.75 F1, 중심점 F1, 평균 IoU, 개수 정확도, 없는 글자 맞힘, JSON 형식 정상 비율 |
  | `spotting`·`relation`·`marked_box` | 박스와 글자가 모두 맞아야 맞는 위치+글자 F1 |

- **나눠 보기:** 전체, 깨끗한 사본 / 노이즈 사본, 사내 OCR 신뢰도(0.95 이상 / 미만), 글자 크기(소·중·대)로 나눠 봅니다. **깨끗한 사본과 노이즈 사본의 점수 차이가 노이즈에 얼마나 강한지**를 보여 줍니다.
- **결과:** `runs/exp1/reports/benchmark.html`에 Base·SFT·GRPO 점수와 Base 대비 변화가 나옵니다. 깨끗한 사본, 노이즈 사본 표도 따로 있습니다.

### 1-5. viewer (`bash viewer/start.sh`, 포트 7860)

- **직접 테스트:** 이미지나 PDF를 올리고 질문을 고르면 답의 박스를 이미지 위에 그려 줍니다.
  - 전체 글자+위치: 페이지를 타일로 나눠 묻습니다.
  - 글자 찾기
  - 드래그한 영역 읽기
  - 기준 글자 옆 찾기
  - 직접 입력 질문
- **벤치마크 문제:** 무작위 문항을 풀게 하고 정답(초록)과 모델 답(빨강) 박스를 겹쳐 그립니다. GRPO 보상 점수도 보여 줍니다.
- **저장된 답 보기:** 파이프라인이 저장한 평가 답을 GPU 없이 정답과 비교합니다. 보상 기준으로 틀린 문제만 골라 볼 수 있습니다.

## 2부. 은행 업무 학습

### 2-1. 컨셉

- **무엇을 배우나:** 1부 모델에서 출발해, 고객이 낸 **서류 묶음을 보고 판단하는** 업무를 배웁니다.

  | 업무 | 모델이 하는 일 |
  |---|---|
  | 서류 구비 확인 | 빠진 서류, 필요 없는 서류, 다른 사람 서류 찾기 |
  | 서류 대조 | 서류 2~3건을 맞대어 불일치 찾기 (오기, 타인 서류, 소득 부풀리기, 임대인≠등기부 소유자 등 14종) |
  | 심사 질의 | LTV, 소득 대비 배수, 만 나이, 서류 유효기간 같은 질문에 숫자나 예/아니오로 답하기 |
  | 정보 추출 외 | 항목 값 추출, 체크박스·도장·서명, 서류 분류, 글자 읽기 |

- **왜 합성 데이터인가:**
  - 실제 고객 서류는 학습에 쓸 수 없습니다.
  - "어느 서류의 어느 값이 틀렸다" 같은 정답을 사람이 다는 비용도 큽니다.
  - 그래서 서류를 직접 생성해 **정답을 공짜로** 얻고, 불일치도 **일부러 만들어 넣습니다**.
- **합성 데이터 생성기 docgen** (자세히: [부록 A](#부록-a-합성-데이터-생성기-docgen-상세))
  - 서류 476종을 만듭니다. HTML 템플릿 70종에, 하나은행 원본 서식 PDF 위에 값을 써넣는 406종입니다.
  - 화면에 찍힌 문자열을 그대로 정답으로 기록해서, 정답과 이미지가 어긋나지 않습니다.
  - 고객 한 명의 서류끼리 이름·주소·소득·대출금이 맞습니다. 업무 12종의 서류 묶음 단위로 만듭니다.

### 2-2. 데이터 구조

```text
[docgen 도커, 한 번]  scripts/make_bank_data.sh
   bench/        평가 세트 : 서류 476종 × 1건 + 업무 12종 × 고객 40명      (seed 1,000,000~ / 2,000,000~)
   bank_train/   학습 데이터: 서류 476종 × 5건 + 업무 12종 × 고객 200명     (seed 10,000,000~ / 20,000,000~)
        │  run_bank_pipeline.py 의 prepare
        ▼
[GPU 서버]  data/prepared-bank/   학습·평가 형식으로 변환
```

**docgen이 만드는 서류 정답** (`labels/*.json`, 서류 한 건)

```json
{"doc_type": "loan_application", "doc_name": "대출거래신청서", "images": ["images/loan_application_000003.png"],
 "fields": [
```

### 2-3. 학습 방법

**prepare에서 정한 것**
- **이미지 토큰 예산:** 한 장은 약 3600토큰 이하(2300×1600)입니다. 한 문항에 이미지가 최대 13장이라 합계가 12,000토큰을 넘지 않게 장마다 같은 비율로 줄입니다. 평가도 같은 규칙이라 학습과 평가가 같은 픽셀을 봅니다.
- **과제 비율:** SFT 2만 문항을 서류 대조 25%, 심사 질의 20%, 정보 추출 15%, 값 칸 OCR 10%, 서류 구비 확인 10%, 체크·도장·서명 8%, 분류 7%, 받아쓰기 5%로 뽑습니다.
- **GRPO 몫 떼기:** 고객 20%의 문항은 SFT에서 빼고 GRPO용으로 둡니다. SFT에서 본 문제로 GRPO를 하면 학습 신호가 약하기 때문입니다.
- **OCR 데이터 섞기:** 1부 학습 데이터 3000개를 섞어 글자·위치 읽기를 잊지 않게 합니다.
- **검사:**
  - 학습 데이터와 평가 세트에 같은 고객이 있으면 멈춥니다.
  - 정답을 모델 출력으로 넣었을 때 채점기가 만점을 주는지 확인합니다.

**SFT:** 1부 결과 모델(병합본)에 새 LoRA(rank 32)를 붙여 1 epoch, learning rate 1e-4로 학습합니다. 문항 길이는 최대 16,384토큰입니다.

**GRPO**
- **보상 = 평가 채점기 그대로**(`bank_task/score.py` → `docgen/bench/evaluate.py`): 정답이 분명해서 1부의 의사정답보다 신호가 깨끗합니다.
- **부분 점수:** 0점 아니면 1점만 있으면 한 문제의 답 여러 개가 같은 점수를 받아 배울 게 없어집니다. 그래서 두 과제에 부분 점수를 줍니다.
  - 서류 구비 확인: 0.5 × 완전 일치 + 0.5 × F1
  - 서류 대조 변조 문항: 0.5 × (불일치라고 함) + 0.5 × (서류·값까지 짚음)
- **문제 고르기:** 후보 3000문제를 SFT 모델로 풀고, 보상 0.9 미만인 문제를 절반 섞어 1000문제를 고릅니다.
- **대상 과제:** 서류 대조, 심사 질의, 서류 구비 확인, 정보 추출 중 이미지 4장 이하 문항입니다(메모리 때문).
- **설정:** learning rate 5e-6, beta 0.04, 한 문제에 답 8개(40GB 설정은 4개)

**GPU별 설정**
- A100 80GB × 2: 기본 설정
- A100 40GB × 2: 비전 인코더 고정, SFT는 zero3, GRPO는 GPU당 1개 × 누적 8 (`*_a100_40g_x2.yaml`)

### 2-4. 평가 방법

- **평가 세트:** 약 9천 문항, 과제 8종입니다. 문항을 만드는 방법과 채점 규칙은 [부록 B](#부록-b-벤치마크-설계-상세)에 있습니다.
  - 은행 업무: 서류 구비 확인 480, 서류 대조 약 2000, 심사 질의 약 2400
  - 문서 이해: 분류 476, 정보 추출 476, 체크·도장·서명 약 410
  - OCR: 값 칸 읽기 약 2400, 전체 받아쓰기 약 460
- **채점은 규칙 기반입니다.** 날짜·금액·번호는 표기를 맞춘 뒤 비교합니다. 사람이나 LLM 판정이 없어서 결과가 늘 같습니다.
- **같은 조건 강제:** 출발·SFT·GRPO 모델이 같은 문항, 같은 이미지, 같은 추론 설정으로 풉니다. 조건이 다르면 비교표 만들기를 거부합니다.
- **OCR 유지 확인:** 각 모델로 1부 벤치마크 1000문항도 같이 풀어, 은행 업무를 배우는 동안 읽기 능력이 떨어지지 않았는지 봅니다.
- **결과** (`runs/bank1/reports/benchmark.html`)
  - 과제별 점수와 출발 모델 대비 변화(%p)
  - 답 형식 오류 비율
  - 세부 표: 불일치 분류별·사례별, 심사 질의 능력별, 빠진 서류 수별, 서식별, 인쇄체/손글씨별
  - `ocr_retention.html`: OCR 유지
- **읽을 때 주의:**
  - 찍어도 나오는 점수가 있습니다. 서류 대조는 "문제없음"만 답해도 약 60%가 나옵니다. 그래서 **위치 정확도**(변조 문항에서 서류·값까지 짚은 비율)를 함께 봅니다.
  - 지표 뜻, 오차 범위, 이상 신호는 [results.md](results.md)에 있습니다.

### 2-5. viewer (`bash viewer/bank_start.sh`, 포트 7861)

- **벤치마크 보기:**
  - 문항마다 모델들의 답을 정답과 나란히 봅니다. 정보 추출은 항목별로 초록(맞음)과 빨강(틀림)으로 표시합니다.
  - 서류 이미지는 모델이 본 크기 그대로 보여 줍니다. 서류 이름·쪽과 변조 사본 표시(다른 고객 서류, 값 바뀜, 발급일 바뀜)가 붙습니다.
  - 과제, 업무, 불일치 사례, 심사 능력으로 거릅니다. "**SFT는 맞히고 출발 모델은 틀린 문제**"처럼 좋아진 문제나 나빠진 문제만 골라 볼 수 있습니다.
  - 저장된 답만 보는 모드는 GPU가 필요 없어 학습 중에도 쓸 수 있습니다.
- **직접 테스트:** 내 서류(이미지·PDF)를 올려 서류 구비 확인, 서류 대조, 심사 질의, 정보 추출, 분류를 물어봅니다. 질문 문장과 이미지 크기는 학습과 같은 규칙을 씁니다.

자세한 내용: 질문 문장과 답 형식은 [questions.md](questions.md), 실행과 설정은 [bank/README.md](../bank/README.md), viewer는 [ocr/viewer/README.md](../ocr/viewer/README.md) 6번에 있습니다.

### A-2. 만드는 방식

**HTML 템플릿 (70종)**
- 서식마다 Jinja2 템플릿과 값 생성 함수를 둡니다.
- 템플릿의 값은 모두 `f("경로")`로 찍습니다. 이렇게 찍은 문자열이 그대로 정답이 되고, 위치(박스)도 렌더링에서 함께 뽑습니다. 그래서 정답과 이미지가 어긋날 수 없습니다.
- 서식 구성은 법령 별지 서식, 은행연합회 표준, 공공기관 발급본을 웹 검색으로 교차 확인해 맞췄습니다. 근거는 `docgen/manual/REALISM_STATUS.md`에 있습니다.
- 은행 서식은 은행별 표기(은행명, 서식번호 줄, 결재란, 인쇄색)가 다르게 나옵니다. 옛 은행(KEB하나, 외환) 서식은 그 시기 날짜·제도로 만듭니다.

**하나은행 원본 서식 (406종)**
1. **기재 자리 찾기:** PDF의 글자 위치·색과 표 선에서 고객이 쓰는 칸을 찾습니다. 대상은 빈 칸, `□` 보기, `년 월 일`, `(서명 또는 인)`, 자필 기재란입니다.
2. **값 채우기:** 항목명으로 값을 정합니다.
   - 성명·주소·계좌 등은 고객 프로필에서 가져와 다른 서류와 맞춥니다.
   - 서식 고유 항목은 항목명으로 종류만 추론합니다.
   - 뜻을 모르는 칸은 비워 둡니다.
3. **그리기:** 원본 PDF 이미지를 배경으로 깔고 값을 절대 위치로 얹습니다.
   - 글씨: 서류마다 손글씨 70%(글꼴 4종, 글자마다 기울기·흔들림), 인쇄체 30%
   - 체크 표시: V, ■, ○ 중 하나

### A-3. 고객 프로필과 일관성

- 고객 한 명의 프로필에 본인·가족·직장·사업체·법인·부동산·계좌·해외 거래처가 들어 있습니다. 같은 프로필로 만든 서류들은 값이 서로 맞습니다.
  - 급여명세서 실수령액 = 통장 급여 입금액
  - 등기부 근저당 = 대출 약정
  - 상호 변경일 = 등기부·정관·사업자등록증에서 같음
- **숫자 정합성:** 합계, 세액(누진세율·4대보험), 잔액 흐름, 대차대조(자산=부채+자본), 환율 환산, 한글 금액(`금 이억일천사백만원정`)을 계산으로 맞춥니다.
- **식별번호:** 주민·사업자·법인등록번호는 체크섬까지 맞는 형식입니다(값은 무작위). 여권 MRZ도 체크디지트를 맞춥니다.
- **위조 방지:** 신분증·여권·인감증명서 등에는 항상 "견본 SAMPLE" 워터마크를 넣습니다. 실제 기관 로고·관인은 넣지 않습니다.

### A-4. 다양성

| 종류 | 내용 |
|---|---|
| 시각 | 샘플마다 글꼴(나눔·Noto·명조), 글자 크기, 선 굵기, 배경색, 여백이 바뀝니다. 열람용/발급용, 마스킹 여부도 무작위입니다 |

| 촬영 조건 | 평가 세트 기준 원본 50%, 스캔 20%, 촬영 15%, 팩스 15%. 기울기, 배경, 조명, 흐림, 노이즈, JPEG 압축. 위치 정답도 증강에 맞춰 옮깁니다 |

### B-2. 서류 구비 확인 (`doc_check`) 문항 만들기

1. 업무 묶음의 필수 서류 중 0 / 1 / 2건을 뺍니다. 비율은 30 / 50 / 20%입니다.
2. 30%는 제출 서류 하나를 **다른 고객의 같은 서류**로 바꿉니다. 그 서류는 `not_customer`이면서 `missing`에도 들어갑니다. 본인 서류는 안 낸 것이기 때문입니다.
3. 35%는 **다른 업무의 서류** 한 건을 끼워 넣습니다(`not_required`).
4. 남은 서류의 **첫 쪽만** 순서를 섞어 이미지로 줍니다. 질문에는 고객 성명, 업무명, 필수 서류 목록이 들어갑니다.

**채점**
- 세 목록이 모두 맞아야 완전 일치입니다. 목록별 일치율과 F1도 함께 봅니다.
- 모델이 쓴 서류명은 후보 서류명에 비슷한 이름으로 대응시킵니다. 예를 들어 "원천징수영수증"은 "근로소득 원천징수영수증"으로 인정합니다.

### B-3. 서류 대조 (`cross_check`) 문항 만들기

**불일치 14종** (실제 심사·금융사고 사례 기반, 근거 자료는 [benchmark.md](benchmark.md#참고-자료))

| 사례 | 분류 | 무엇을 바꾸나 | 실제 사례 |
|---|---|---|---|
| `typo` | 오기 | 여러 서류에 나오는 성명·주민번호·연락처·주소·계좌·생년월일 한 자리 | 신청서·약정서 기재 오류 |
| `other_person` | 타인 서류 | 신분증·등본·재직증명서·소득서류 등 한 건을 다른 고객 것으로 | 명의도용, 가족 서류 혼입 |
| `loan_vs_agreement` | 금액 | 신청서 또는 약정서의 대출금액 | 약정서 작성 오류·변조 |
| `income_inflated` | 금액 | 원천징수영수증 급여를 20~60% 부풀림 → 소득금액증명원과 불일치 | 작업대출: 소득 서류 위·변조 |
| `lease_owner` | 관계 | 등기부 소유자를 다른 사람으로 → 임대인 ≠ 소유자 | 전세사기 |
| `seller_owner` | 관계 | 등기부 소유자를 다른 사람으로 → 매도인 ≠ 소유자 | 무권리자 매도 |
| `hire_date` | 관계 | 재직증명서 입사일을 1~4년 앞당김 → 건강보험 취득일과 불일치 | 작업대출: 재직기간 부풀리기 |
| `rep_director` | 관계 | 법인인감증명서 대표자를 다른 사람으로 | 권한 없는 자의 신청 |
| `contract_before_apply` | 관계 | 약정일을 신청일보다 앞으로 | 서류 소급 작성 |
| `collateral_short` | 관계 | 채권최고액을 대출금의 60~95%로 | 근저당 설정 금액 부족 |
| `jeonse_over` | 관계 | 전세대출 신청금액을 보증금의 105~130%로 | 보증금 부풀리기 |
| `sales_sum` | 관계 | 매매대금을 8~25% 올림 → 계약금+중도금+잔금과 불일치 | 업계약 |
| `fx_beneficiary` | 관계 | 송금 수취인을 다른 회사로 → 송장 수출자와 불일치 | 증빙과 다른 상대방에게 송금 |
| `format_only` | 정상 | 같은 값을 다른 표기로(날짜 형식, 하이픈, 주민번호 뒷자리 가림) | 오탐 방지 |

**만드는 순서**
1. **원본 확인:** 사례마다 원본 서류에서 그 관계가 실제로 맞는지 먼저 확인합니다(예: 임대인 = 등기부 소유자). 맞지 않는 묶음에서는 그 사례를 만들지 않습니다. 생성기 자체의 우연한 불일치가 정답을 오염시키지 않게 하려는 것입니다.
2. **변조와 정상 짝:** 50% 확률로 변조하고, 나머지는 같은 서류 조합을 정상 문항으로 냅니다.
3. **값만 바꿔 다시 렌더링:** HTML의 해당 값 칸 글자만 바꾸고, 같은 서류 안에 같은 값이 여러 번 있으면 함께 바꿉니다. 바뀐 서류는 그 값 말고는 원본과 같고 촬영 증강도 같습니다. 타인 서류 사례는 같은 종류 서류를 다른 고객 프로필로 새로 만듭니다.
4. **관련 서류만 보여 줍니다:** 사례에 관련된 서류 2~3건(이미지 10장 이하)만 줍니다. 상관없는 서류에서 생기는 우연한 불일치를 줄이기 위해서입니다.

**채점**
- 정상 문항: `consistent: true`이면 맞습니다.
- 변조 문항: 불일치라고 하고, 문제 서류와 함께 그 값·원래 값·항목명 중 하나를 맞게 짚어야 맞습니다.
  - 관계 사례는 짝 서류를 지목해도 인정합니다. 예를 들어 임대인≠소유자는 계약서와 등기부 어느 쪽을 짚어도 됩니다.
- 따로 보고하는 지표: 탐지(불일치 여부만), 위치(변조 문항에서 서류·값까지), 오탐률(정상 문항을 불일치라고 함), 사례별·분류별 점수

### B-4. 심사 질의 (`review`) 문항 만들기

정답은 서류의 정답 값으로 계산합니다. 질문에 반올림 자릿수, 기준일, 답 형식을 적어 정답이 하나로 정해지게 합니다.

| 규칙 | 업무 | 질문 | 능력 |
|---|---|---|---|
| `ltv` | 주택담보 | 대출신청금액 ÷ 매매대금 (%) | 계산(비율) |
| `collateral_ratio` | 주택담보 | 채권최고액 ÷ 약정 대출금액 (%) | 계산(비율) |
| `jeonse_ratio` | 전세자금 | 대출신청금액 ÷ 임차보증금 (%) | 계산(비율) |
| `income_multiple` | 신용대출 | 대출신청금액 ÷ 원천징수 급여 합계 (배) | 계산(비율) |
| `age` | 신분증+신청서 | 신청일 기준 만 나이 | 날짜 계산 |
| `tenure` | 대출 | 입사일~신청일 만 재직연수 | 날짜 계산 |
| `doc_valid` | 발급일 있는 서류 | 발급 후 90일 이내인가 | 날짜 계산 |
| `net_pay` | 신용대출 | 급여명세서 지급액계 − 공제액계 | 계산(합계) |
| `sales_rest` | 주택담보 | 매매대금 − 계약금 − 중도금 | 계산(합계) |
| `invoice_sum` | 해외송금 | 상업송장 품목 금액 합계 | 표 계산 |
| `tuition_due` | 유학생 송금 | 이전 잔액 + 청구액 − 납부액 | 계산(합계) |
| `debt_ratio` | 법인 여신 | 부채총계 ÷ 자본총계 (%) | 표 계산 |
| `case:<사례>` | 불일치 사례마다 | "임대인이 등기부 소유자와 같은 사람입니까?" 같은 예/아니오 질문 (변조 문항이면 "아니오") | 서류 대조 |

- **90일 이내 질문:** 묶음 서류의 발급일은 대개 신청일과 같아서 그대로 두면 답이 늘 "예"가 됩니다. 그래서 절반은 발급일을 93~400일 앞당긴 사본으로 묻습니다.
- **채점:** 숫자는 `%`·`배`·`원` 같은 단위를 떼고 허용 오차(소수 자릿수 기준) 안이면 정답입니다. 예/아니오는 "네", "아니요"도 알아듣습니다.

### B-5. 공통 채점 규칙

- **값 비교 (`kie` 등):**
  - 날짜: `2025년 9월 20일` = `2025-09-20`
  - 금액: `금 오억원정` = `500,000,000`, 1원 차이도 오답
  - 번호: 숫자만 비교
  - 그 밖: 공백·문장부호 무시
- **답이 없거나 형식이 틀리면 0점입니다.** 빈 답이 빈 칸(`null`)이나 "도장 없음"을 우연히 맞히지 않게 하려는 것입니다. 보고서에 비율이 따로 나옵니다.
- **채점기 점검:** 정답을 그대로 출력으로 넣으면 모든 과제가 100점이어야 합니다. 파이프라인의 prepare가 매번 확인합니다.
- **비교 조건 고정:** 평가 문항이 다르거나 추론 설정(temperature, 이미지 등)이 다른 결과끼리는 비교표 만들기를 거부합니다.

### B-6. 찍어도 나오는 점수와 오차

| 지표 | 찍는 방법 | 그래도 나오는 점수 |
|---|---|---|
