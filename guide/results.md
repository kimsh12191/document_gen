# 결과 읽는 법

`python -m train`이 남기는 결과를 어디서 보고 어떻게 읽는지입니다. 각 과제가 무엇을 묻고 어떻게 채점하는지는 [benchmark.md](benchmark.md), 평가 세트·채점 방식은 [eval.md](eval.md)에 있습니다.

## 어디서 보나

| 파일 (`<workdir>` 아래) | 내용 |
|---|---|
| `reports/summary.html` | **한 화면.** 평가 세트·과제마다 주 지표 한 줄, 열은 모델(출발·SFT·GRPO), 괄호는 출발 모델(`eval.compare_models`가 있으면 그 첫 모델) 대비 %p (초록 좋아짐, 빨강 나빠짐) |
| `reports/benchmark.html` (`.md`, `.csv`) | **자세한 표.** 평가 세트별 점수, 출발 모델 대비 변화, 답 형식 오류, 세부 표(사례·서식·필드별) |
| `reports/start.json`, `sft.json`, `grpo-*.json` | 모델별 원본 점수. 표에 없는 지표도 들어 있음 (예: `kie`의 `field_acc`, `classify`의 `acc_lenient`) |
| `state.json` | 단계별 완료 여부, 걸린 시간(`timings`) |
| `logs/` | 단계별 실행 로그. GRPO 문제 선정 결과는 `mine.log` |
| `sft/…/logging.jsonl`, `grpo/…/logging.jsonl` | 학습 중 로그 (loss, 보상). 아래 [학습 중 로그](#학습-중-로그) |
| `reports/answers.html` | **문항별 모델 답.** 평가 세트·과제마다 표본(모델끼리 점수가 갈린 문항 먼저)의 질문·그림·정답과 모델마다 답·점수. 아래 [문항별 답 보기](#문항별-답-보기) |
| `predictions/*.jsonl` | 모델 답 원문 (`{id, prediction}`). 문항은 섞은 폴더의 `benchmark_items.jsonl` |
| studio 데이터셋 › 문항·모델 답 탭 | 문항 하나하나의 그림·박스·답·점수. 점수가 이상할 때 실제 답을 봅니다 |

**실험 묶음**(`python -m train sweep`)은 모델이 끝날 때마다 `<root>/summary.html`(묶음의 모델 한 화면, 괄호는 `baseline` 대비 %p, 모델마다 바꾼 설정), `<root>/compare.html`(자세한 비교표), `<root>/answers.html`(문항별 모델 답)을 다시 씁니다.

### 문항별 답 보기

`answers.html`에서 평가 세트·과제를 고르면 문항마다 질문(그림 포함)·정답과 모델마다 답·점수가 나란히 나옵니다.

- 기본은 평가 세트·과제마다 30개입니다. 모델끼리 점수가 갈린 문항을 절반까지 먼저 넣고 나머지는 무작위입니다.
- **모델끼리 점수가 갈린 문항만**, **기준보다 나빠진 모델이 있는 문항만**으로 거르고, 문항 ID로 찾습니다.
- 점수는 그 과제의 주 지표를 문항 하나로 잰 값입니다. 초록은 기준 모델보다 좋음, 빨강은 나쁨입니다.
- 표본 수를 바꾸거나 모든 문항을 넣으려면 `python -m train answers <결과 폴더 또는 workdir> --per-task 100` (`--all`이면 전부, 파일이 커짐). 묶음 밖 workdir는 `--data <섞은 폴더>`(설정의 `data.output_dir`)도 줍니다.
- 그림은 섞은 폴더를 상대 경로로 겁니다. 결과 폴더를 다른 곳으로 옮기면 그림이 안 보일 수 있습니다.

### 여러 실험을 한 화면에

```bash
python -m train summary ../runs/E01 ../runs/E02 ../runs/exp1 --out ../runs/summary.html
```

- 실험 묶음 결과 폴더, 묶음 파일, 학습 `workdir`를 섞어 줄 수 있습니다. 끝난 보고서만 읽습니다.
- 행은 평가 세트·과제의 주 지표, 열은 실험별 모델입니다. 괄호는 그 실험의 기준 모델 대비 %p입니다.
- **굵게**는 같은 평가 문항을 쓴 칸 중 가장 좋은 값입니다.
- 평가 문항이 다른 실험의 칸은 흐리게 `†`를 붙입니다. 다른 실험과 직접 비교하지 않습니다. 실험 간 비교가 필요하면 평가 세트를 고정하세요.

## 읽는 순서

1. **답 형식 오류 표부터 봅니다.** 모델이 JSON을 못 쓰거나 형식을 지키지 않으면 그 문항은 0점입니다.
   - 출발 모델은 형식을 배운 적이 없어서 높은 게 정상입니다.
   - **SFT 뒤에는 거의 0%여야 합니다.** 남아 있으면 SFT가 덜 됐거나, 답이 `max_tokens`에서 잘린 것입니다. studio에서 답 끝을 확인하세요.
2. **점수 표와 기준 대비 변화 표(Δ%p)를 봅니다.** 과제별 주 지표가 출발 → SFT → GRPO로 얼마나 올랐는지 확인합니다.
3. **찍어도 나오는 점수와 비교합니다.** 아래 [기준선](#찍어도-나오는-점수-기준선) 근처면 사실상 못 푸는 것입니다.
4. **세부 표를 봅니다.** 어떤 사례, 능력, 서식에서 약한지 봅니다. 문항 수(`n`)가 작은 줄은 흔들림이 큽니다([오차](#점수-차이가-의미-있나)).
5. **OCR 열을 봅니다.** 출발 모델보다 OCR 점수가 많이 떨어졌으면 업무를 배우면서 글자 읽기를 잊은 것입니다([OCR 열](#ocr-열-읽기-능력-유지)).
6. **이상한 칸은 studio(데이터셋 › 문항·모델 답 탭)로 실제 답을 봅니다.** 문항을 점수 낮은 것부터 정렬해 정답·모델 답 박스를 겹쳐 볼 수 있습니다.

## 지표 사전

점수는 모두 0~100(%)이고 높을수록 좋습니다. ↓ 표시가 있는 칸만 낮을수록 좋습니다.

| 열 | 과제 | 뜻 | 볼 때 |
|---|---|---|---|
| 칸 잘라 읽기 CER ↓ | crop_ocr | 잘라낸 단어의 틀린 글자 비율 | 깨끗한/변형한 쪽 표로 노이즈에 강한지 봅니다 |
| 좌표→글자 일치 / 좌표→숫자 일치 | bbox_ocr | 박스 안 글자를 정확히 읽은 비율 / 숫자만 본 일치 | 숫자 일치가 낮으면 금액·번호를 틀림 |
| 영역 받아쓰기 CER ↓ | region_ocr | 영역 안 글자 전부의 틀린 글자 비율 | 읽는 순서가 틀려도 오릅니다 |
| 글자→좌표 F1@0.5 / 없음 정확도 | grounding | 그 글자의 박스를 IoU 0.5 이상으로 찾은 F1 / 없는 글자에 `[]`로 답한 비율 | 없음 정확도가 낮으면 없는 글자를 지어냄 |
| 글자 찾기 위치 F1@0.5 / 위치+글자 F1 | spotting | 타일의 모든 글자 박스 F1 / 박스와 글자가 모두 맞은 F1 | 주 지표는 위치+글자 |
| 항목명→값 위치+글자 F1 | relation | 기준 글자 옆 값의 박스와 글자가 모두 맞은 F1 | 항목명 → 값 관계 |
| 그린 박스→글자 일치 / 좌표 F1@0.75 | marked_ocr / marked_box | 색 박스 안 글자 일치 / 그 박스 좌표를 IoU 0.75 이상으로 낸 F1 | |
| 서류 구비 완전 일치 | doc_check | 빠진 서류·불필요 서류·타인 서류 **세 목록이 모두** 정확한 문항 비율 | 주 지표. 하나라도 틀리면 0이라 엄격합니다 |
| 서류 구비 F1 | doc_check | 세 목록을 합쳐 서류 단위로 맞힌 정도 | 완전 일치보다 높게 나옵니다. 둘의 차이가 크면 "대부분 맞히지만 한두 개씩 틀림" |
| 서류 대조 종합 | cross_check | 정상 문항은 "문제없음"이라고 하면 1점, 변조 문항은 불일치라고 하고 **문제 서류와 값까지** 짚어야 1점 | 주 지표. 정상 문항이 약 6할이라 항상 "문제없음"이라고만 해도 약 60%가 나옵니다 |
| 서류 대조 탐지 | cross_check | 불일치 여부(true/false)만 맞힌 비율 | 종합보다 높으면 "있다는 건 알지만 어디인지 못 짚음" |
| 서류 대조 위치(변조 문항) | cross_check | 변조 문항 중 문제 서류와 값을 맞게 짚은 비율 | **실제 잡아내는 능력은 이 값입니다.** 기준선이 0입니다 |
| 서류 대조 오탐률 ↓ | cross_check | 정상 문항을 불일치라고 한 비율 | 위치 정확도가 오르면서 오탐률도 오르면 "아무거나 의심"하는 것 |
| 심사 질의 정확도 | review | 숫자(허용 오차 안) 또는 예/아니오가 맞은 비율 | 능력별 표(계산, 날짜 계산, 서류 대조)로 나눠 봅니다 |
| 정보 추출 값+위치 F1 | kie | 값도 맞고 박스(`bbox_2d`, 같은 쪽, IoU 0.5 이상)도 맞은 항목의 F1 | 주 지표. 위치만 본 `loc_f1`은 `*.json`에 있습니다. 서식 `questions.json`의 답 틀에 위치(`bbox_2d`)가 없는 문항은 위치 점수 없이 아래 F1이 주 지표 (marks는 정확도) |
| 정보 추출 F1 | kie | 값이 있는 항목을 맞힌 정도(위치는 안 봄). 빈 칸에 값을 지어내면 깎입니다 | 값+위치보다 높으면 "값은 읽지만 위치를 못 짚음". 빈 칸까지 센 항목 정확도는 `field_acc` |
| 체크·도장·서명 값+위치 F1 | marks | 값도 맞고 체크된 □·찍힌 자리의 박스도 맞은 항목의 F1 | 주 지표 |
| 체크·도장·서명 정확도 | marks | 항목별로 값을 맞힌 비율(위치는 안 봄) | 전부 비었다고 해도 약 40%가 나옵니다 |
| 서식 전용 질문 정확도 | form_qa | 서식 폴더 `qa.py`의 질문을 맞힌 비율. 정답 꼴대로 비교 (숫자·예/아니오·글은 띄어쓰기·문장부호 무시·JSON은 칸마다) | 주 지표. 세부 표는 서식별(`doc_type`)·질문별(`question`) |
| 기타 칸 정리 F1 | freetext | 대충 쓴 글을 DB 칸으로 정리한 값이 키마다 맞은 정도 | 지어낸 키 비율 `extra_key`(↓)와 함께 봅니다 |
| 서류 분류 | classify | 서류명이 정식 명칭과 같은 비율 (공백·문장부호 무시) | 답 안에 정식 명칭이 들어 있으면 맞힌 것으로 보는 값은 `acc_lenient` |
| 표 칸 F1 | table / table_read | 표의 행·열 칸마다 값이 맞은 정도 (`cell_f1`) | 주 지표. `table` 은 열을 정해 주고, `table_read` 는 머리글까지 그대로 옮김 |
| 표 찾기 F1@0.5 | table_find | 서류의 표를 머리글·위치·행 수로 찾은 F1 (위치 IoU 0.5 이상, `f1_iou50`) | 주 지표 |
| 표 질의 정확도 | table_qa | 표를 보고 행 수·찾기·합계를 묻는 질문을 맞힌 비율 (`acc`) | 주 지표 |
| 전체 받아쓰기 재현율 | ocr_page | 서류에 적힌 값이 받아쓴 글에 들어 있는 비율 | 서식 고정 문구(항목명)는 세지 않습니다 |
| 값 칸 OCR 일치 / CER ↓ | ocr_field | 값 칸 하나를 정확히 읽은 비율 / 틀린 글자 비율 | 인쇄체·손글씨별 표로 봅니다 |

### 세부 표

| 표 | 보는 법 |
|---|---|
| 서류 대조 — 불일치 분류별 | `typo` 오기, `other_person` 타인 서류, `amount` 금액, `logic` 관계(임대인≠소유자 등), `format` 표기만 다름. 이 줄들은 정상 문항과 변조 문항이 섞인 점수입니다. **`format`은 정상 문항만 있으므로 100에서 떨어지면 오탐입니다** |
| 서류 대조 — 사례별 | 14개 사례 각각의 점수. 드문 사례(`fx_beneficiary`, `seller_owner` 등)는 `n`이 작아 흔들립니다 |
| 심사 질의 — 능력별 | 서류 대조(예/아니오), 날짜 계산, 계산(비율·합계), 표 계산. 계산 쪽이 보통 가장 낮습니다 |
| 서류 구비 — 빠진 서류 수별 | 0, 1, 2건. 0건(다 낸 경우)에서 틀리면 없는 누락을 지어낸 것입니다 |
| 정보 추출 — 서식 그룹별 | `hana`(하나은행 서식)와 그 밖의 그룹(`income`·`tax`·`fx` 등 외부 서류)을 나눠 봅니다 |
| 값 칸 OCR — 인쇄체/손글씨별 | 손글씨가 보통 많이 낮습니다 |
| 글자 찾기·칸 잘라 읽기 — 깨끗한 쪽 / 변형한 쪽 | 둘의 차이가 노이즈(스캔·촬영)에 얼마나 강한지입니다 |

## 찍어도 나오는 점수 (기준선)

아래 값 근처의 점수는 모델이 그 과제를 사실상 못 푼다는 뜻입니다. 평가 세트 기본 구성 기준의 대략적인 값입니다.

| 지표 | 찍는 방법 | 그래도 나오는 점수 |
|---|---|---|
| 서류 대조 종합 | 항상 "문제없음" | 약 60% |
| 서류 대조 탐지 | 항상 "문제없음" | 약 60% |
| 서류 대조 위치 | 항상 "문제없음" | 0% |
| 심사 질의 (예/아니오 문항) | 항상 "아니오" | 약 57% |
| 체크·도장·서명 | 전부 비었다고 | 약 40% |
| 서류 구비 완전 일치 | 세 목록 모두 빈 칸 | 약 15% |
| 정보 추출 F1 | 전부 `null` | 0% |

## 점수 차이가 의미 있나

문항 수가 유한해서 점수에는 흔들림이 있습니다. 과제별 문항 수 `n` 은 `summary.html`·`benchmark.html` 에 나옵니다. 대략적인 95% 범위는 다음과 같습니다(점수 50% 근처 기준, 끝으로 갈수록 좁아짐).

| 문항 수 n | 흔들림 |
|---:|---|
| 2,000 이상 | ±2%p |
| 약 500 | ±4.5%p |
| 100 | ±10%p |
| 30 이하 (세부 표의 작은 줄) | ±18%p 이상 |

- **판단 기준:** 두 모델의 차이가 이 범위보다 작으면 "차이 없음"으로 봅니다.
- **두 모델 비교:** 같은 문항을 풀기 때문에 실제로는 이보다 조금 더 작은 차이도 의미가 있을 수 있습니다. 확실하지 않으면 studio 데이터셋 › 문항 탭에서 두 모델의 문항 점수를 견주어 보세요.

## OCR 열 (읽기 능력 유지)

따로 된 OCR 유지 표는 없습니다. OCR 데이터셋을 `data.benchmark`에 넣으면 같은 표에 OCR 열(칸 잘라 읽기 ~ 그린 박스)이 생기고, 그 Δ가 곧 읽기 능력 유지입니다.

- **볼 것:** 출발 모델 대비 Δ입니다. 출발 모델이 이미 OCR을 학습한 모델이면 몇 %p 정도 떨어지는 건 흔합니다.
- **크게 떨어졌을 때:** 박스 F1이 10%p 이상 떨어지는 식이면 SFT에 섞는 OCR 문항을 늘리세요(`data.train`의 OCR 데이터셋 `count`). 데이터가 바뀌므로 `data.output_dir`을 새 이름으로 하고 `--from prepare`로 다시 돌립니다.
- **언제 걱정하나:** "값 칸 OCR"이나 "전체 받아쓰기"가 함께 떨어졌다면 실제로 읽기 능력이 약해진 것입니다.
- OCR 정답이 사내 OCR 그대로(의사정답)면 점수는 "사내 OCR과 얼마나 같은지"입니다.

## 학습 중 로그

ms-swift가 학습 폴더에 `logging.jsonl`을 남깁니다(`<workdir>/sft/<버전>/`, `<workdir>/grpo/<버전>/`). 항목 이름은 ms-swift 버전에 따라 조금 다를 수 있습니다.

### SFT

| 값 | 뜻 | 정상 |
|---|---|---|
| `loss` | 학습 문항에서의 손실 | 처음 수백 step에 빠르게 내려가고 천천히 낮아짐 |
| `eval_loss` | 검증 문항(학습에 안 쓴 200문항)의 손실 | `loss`와 함께 내려감. `loss`만 내려가고 `eval_loss`가 오르면 과적합 |
| `token_acc` | 정답 토큰을 맞힌 비율 | 오름 |

### GRPO

| 값 | 뜻 | 정상 / 이상 |
|---|---|---|
| `reward` (`rewards/…/mean`) | 생성한 답들의 평균 보상(벤치마크 채점과 같은 점수, 0~1) | 천천히 오름. 처음부터 0.9 이상이면 배울 게 적은 문제들입니다 |
| `reward_std` | 한 문제에 만든 답 8개(`num_generations`, 40GB yaml은 4개)의 보상 차이 | 0보다 커야 학습됩니다. 계속 0 근처면 답이 다 같아 배울 신호가 없습니다 |
| `frac_reward_zero_std` | 답 8개의 보상이 모두 같은 문제의 비율 | 낮을수록 좋음. 0.8 이상이면 GRPO가 거의 헛돕니다(문제가 너무 쉽거나 너무 어려움) |
| `completions/mean_length` | 답 길이(토큰) | 갑자기 길어지면 반복 출력. `completions/clipped_ratio`(잘린 답 비율)가 오르면 형식 오류가 됩니다 |
| `kl` | SFT 모델에서 멀어진 정도 | 천천히 오름. 급하게 오르면 학습률이 큰 것 |

- **문제 선정 결과:** `logs/mine.log`에서 확인합니다.
  - `hard_available`은 후보 3000개 중 SFT가 보상 0.9 미만을 받은 문제 수입니다.
  - 이 값이 아주 작으면 SFT가 이미 거의 다 맞힌다는 뜻입니다. 이때는 GRPO로 오를 여지가 적습니다.
- **생성된 답 보기:** `log_completions`가 켜져 있어 학습 중 생성한 답도 학습 폴더에 남습니다. 보상이 안 오를 때 실제 답을 확인하세요.

## 이상 신호와 대처

| 보이는 것 | 의심 | 대처 |
|---|---|---|
| SFT 뒤에도 답 형식 오류가 5% 이상 | 답이 잘리거나 형식을 덜 배움 | studio에서 답 끝 확인. 잘렸으면 평가는 `train/configs/inference.json`의 `max_tokens`, GRPO는 yaml의 `max_completion_length` 확인 |
| 서류 대조 종합 ≈ 60%, 위치 ≈ 0 | 항상 "문제없음" | 변조 문항 비율, SFT 데이터의 `task_mix` 확인 |
| 위치는 오르는데 오탐률도 크게 오름 | 아무거나 의심 | GRPO 전후 비교. GRPO에서 생겼으면 `format_only` 정상 문항이 문제 풀에 충분한지 확인 |
| 탐지는 높은데 위치가 낮음 | 불일치를 느끼지만 서류·값을 못 짚음 | studio로 `issues` 내용 확인. 서류명을 다르게 쓰는지 봅니다 |
| 심사 질의 계산만 낮음 | 숫자를 잘못 읽거나 계산 실수 | studio에서 읽은 값과 계산을 분리해 봅니다. 정보 추출 F1이 높으면 계산 문제 |
| 서류 구비 F1은 높은데 완전 일치가 낮음 | 서류명을 조금씩 다르게 씀 | 답의 서류명이 필수 서류 목록 표기와 같은지 확인 |
| SFT보다 GRPO가 떨어짐 | 보상 신호 없음, 또는 과하게 학습 | `frac_reward_zero_std`, `kl` 확인. `grpo.count`나 학습률을 줄여 `--from grpo` |
| OCR 열이 크게 떨어짐 | 잊어버림 | OCR 데이터셋 `count`를 늘리고 새 `data.output_dir`로 `--from prepare` |
| 실서류 세트가 맞게 읽었는데 틀림 (날짜·금액 표기 차이) | 그 세트에 맞지 않는 비교 기준 | 그 세트에 채점 함수(`scorer`)를 붙이고 `rescore` ([eval.md 2·4절](eval.md#2-채점)) |

## 주의

- **합성 서류입니다.** 학습 데이터와 평가 세트는 같은 생성기로 만들어서 고객만 다릅니다. 그래서 점수가 크게 오르는 건 당연하고, 실제 서류 성능은 이보다 낮습니다. 실제 서류는 실서류 데이터셋([eval.md 1절](eval.md#1-평가-세트-정하기))을 평가에 넣어 따로 확인하세요.
- **출발 모델 점수에는 "형식을 모르는 몫"이 섞여 있습니다.** 그래서 출발 → SFT 상승폭의 상당 부분은 형식을 배운 효과입니다. 실력 변화는 SFT → GRPO 사이와 세부 표에서 보는 편이 정확합니다.
- **조건이 다른 결과는 비교표를 만들지 않습니다.** 평가 문항이나 추론 설정(temperature 등)이 다른 보고서끼리는 표 만들기를 거부합니다.
- **채점 함수(`scorer`)가 다른 평가 세트끼리는 같은 기준이 아닙니다.** 같은 세트라도 채점 함수를 바꾸면 예전 결과를 `rescore`로 맞춘 뒤 비교합니다.
- 시나리오·정답 구조·서식·원본 데이터셋별 점수는 `benchmark.breakdowns.csv`·`.json`에 있습니다 (아래 [구분별 점수](#구분별-점수-업무시나리오정답-구조서식별)).

## 구분별 점수 (업무·시나리오·정답 구조·서식별)

평가 세트는 과제 폴더 하나로 저장하고, 문항의 메타데이터로 업무·시나리오·정답 구조·서식별로 나눠 세고 채점합니다.

| 기준 | 예시 | 용도 |
|---|---|---|
| 과제 그룹 `task_group` | `ocr`, `doc`, `work` | OCR / 문서 이해 / 은행 업무 구분 |
| 과제 `task` | `crop_ocr`, `kie`, `doc_check`, `cross_check`, `review` | 같은 채점 방식끼리 비교 |
| 업무 시나리오 `scenario` | `mortgage`, `jeonse_loan` | 업무별 성능 |
| 정답 구조 `label_format` | `text`, `text_boxes`, `key_values`, `mark_states`, `record`, `table_rows`, `table_list`, `document_sets`, `consistency_issues`, `scalar`, `text_list` | 텍스트·좌표·추출·표시·업무 판단 구분 (과제 → 정답 구조 대응은 `docgen/bench/tracking.py` 의 `FORMATS`. `record` 는 `freetext`, `scalar` 는 `review`·`form_qa`) |
| 서식 `doc_type` | `employment_certificate` | 어떤 서식에서 틀리는지 |
| 원본 데이터셋 `source_dataset` | `bench-a@<메타데이터 해시>` | 여러 폴더를 섞어도 출처 추적 |
| 넣은 쪽 `view` | `page`, `all` | 여러 쪽 서류에서 한 쪽만 넣었는지, 모든 쪽을 넣었는지 |

정답 구조는 답의 꼴이고, 필드 타입(이름·금액·날짜·체크·서명 등)과는 별개입니다. 실제 답 규격은 [benchmark.md](benchmark.md#과제)에 있습니다.

### studio에서 보기

1. **데이터셋 → 데이터셋 → 구성·추적**: 전체 문항 / 평가 문항별로 업무·시나리오·과제·정답 구조별 수량. 수량을 누르면 그 문항이 열립니다.
2. **문항** 탭: 그룹·시나리오·정답 구조·서식으로 걸러 봅니다. 여러 과제를 함께 보려면 과제를 **과제 전체**로.
3. **모델 답**에서 모델 결과를 붙여 채점한 뒤, **구성·추적 → 구분별 평가 결과**에서 구분별 과제 지표를 봅니다.
4. 구분에서 **필드 타입 · 항목 단위**를 고르면 정보 추출·체크/도장/서명의 필드별 값 정확도가 나옵니다.

명령줄에서는 `python docker/remote_build.py composition <데이터셋 이름> [--out 파일.json]`. `all`은 전체 문항, `evaluation`은 평가 문항, `provenance`는 레시피·생성기 버전·서식 해시입니다.

### 학습 보고서에서 보기

`python -m train`의 보고서(`reports/benchmark.*`)에 구분별 점수가 같이 나옵니다.

| 결과 | 내용 |
|---|---|
| `benchmark.md`, `.html` | 전체 비교 + 시나리오·정답 구조·서식·원본 데이터셋별 점수와 기준 대비 변화 |
| `benchmark.breakdowns.csv` | 모델·구분·그룹·과제·지표·문항 수·값·변화량(`delta_pp`)을 한 행씩 |
| `benchmark.breakdowns.json` | 모델별 구성과 구분별 전체 지표, 필드 타입별 점수(`models[].field_type_scores`) |

- `n`은 **문항 수**입니다. 고객 수·문서 수·쪽 수와 다릅니다. CSV의 `unit: fields` 행(필드 타입별 값 정확도)은 **필드 항목 수**입니다.
- **과제끼리 점수를 합쳐 평균내지 않습니다.** 구분별 OCR CER은 그 구분의 전체 글자 수로 다시 계산합니다.
- `not_applicable`은 시나리오가 없는 단일 서류·OCR 문항, `unknown`은 기록되지 않은 정보입니다. 파일 이름으로 추측해 채우지 않습니다.
