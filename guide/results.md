# 결과 읽는 법 (학습 실행)

`python -m train`이 남기는 평가 지표를 해석하는 방법입니다. OCR·문서 이해·업무 과제가 한 표에 나옵니다. 각 과제가 무엇을 묻고 어떻게 채점하는지는 [benchmark.md](benchmark.md)에 있습니다.

## 어디서 보나

| 파일 (`train/runs/exp1/` 아래, 설정의 `workdir`) | 내용 |
|---|---|
| `reports/benchmark.html` (`.md`, `.csv`) | **본 결과.** 모델별 점수(OCR → 문서 이해 → 업무 열 순서), 출발 모델 대비 변화, 답 형식 오류, 세부 표 |
| `reports/start.json`, `sft.json`, `grpo-*.json` | 모델별 원본 점수. 표에 없는 지표도 들어 있음 (예: `kie`의 `field_acc`, `classify`의 `acc_lenient`) |
| `state.json` | 단계별 완료 여부, 걸린 시간(`timings`) |
| `logs/` | 단계별 실행 로그. GRPO 문제 선정 결과는 `mine.log` |
| `sft/…/logging.jsonl`, `grpo/…/logging.jsonl` | 학습 중 로그 (loss, 보상). 아래 [학습 중 로그](#학습-중-로그) |
| studio ⑥ 데이터셋(문항 탭)·⑦ 평가 | 문항 하나하나의 그림·박스·답·점수. 점수가 이상할 때 실제 답을 봅니다 |

## 읽는 순서

1. **답 형식 오류 표부터 봅니다.** 모델이 JSON을 못 쓰거나 형식을 지키지 않으면 그 문항은 0점입니다.
   - 출발 모델은 형식을 배운 적이 없어서 높은 게 정상입니다.
   - **SFT 뒤에는 거의 0%여야 합니다.** 남아 있으면 SFT가 덜 됐거나, 답이 `max_tokens`에서 잘린 것입니다. studio에서 답 끝을 확인하세요.
2. **점수 표와 기준 대비 변화 표(Δ%p)를 봅니다.** 과제별 주 지표가 출발 → SFT → GRPO로 얼마나 올랐는지 확인합니다.
3. **찍어도 나오는 점수와 비교합니다.** 아래 [기준선](#찍어도-나오는-점수-기준선) 근처면 사실상 못 푸는 것입니다.
4. **세부 표를 봅니다.** 어떤 사례, 능력, 서식에서 약한지 봅니다. 문항 수(`n`)가 작은 줄은 흔들림이 큽니다([오차](#점수-차이가-의미-있나)).
5. **OCR 열을 봅니다.** 출발 모델보다 OCR 점수가 많이 떨어졌으면 업무를 배우면서 글자 읽기를 잊은 것입니다([OCR 열](#ocr-열-읽기-능력-유지)).
6. **이상한 칸은 studio(⑥ 문항 탭, ⑦ 평가)로 실제 답을 봅니다.** 문항을 점수 낮은 것부터 정렬해 정답·모델 답 박스를 겹쳐 볼 수 있습니다.

## 지표 사전

점수는 모두 0~100(%)이고 높을수록 좋습니다. ↓ 표시가 있는 칸만 낮을수록 좋습니다.

| 열 | 과제 | 뜻 | 볼 때 |
|---|---|---|---|
| 칸 잘라 읽기 CER ↓ | crop_ocr | 잘라낸 단어의 틀린 글자 비율 | 깨끗한/변형한 쪽 표로 노이즈에 강한지 봅니다 |
| 좌표→글자 일치 / 좌표→숫자 일치 | bbox_ocr | 박스 안 글자를 정확히 읽은 비율 / 숫자만 본 일치 | 숫자 일치가 낮으면 금액·번호를 틀림 |
| 영역 받아쓰기 CER ↓ | region_ocr | 영역 안 글자 전부의 틀린 글자 비율 | 읽는 순서가 틀려도 오릅니다 |
| 글자→좌표 F1@0.5 / 없음 정확도 | grounding | 그 글자의 박스를 IoU 0.5 이상으로 찾은 F1 / 없는 글자에 `[]`로 답한 비율 | 없음 정확도가 낮으면 없는 글자를 지어냄 |
| 글자 찾기 위치 F1@0.5 / 위치+글자 F1 | spotting | 타일의 모든 글자 박스 F1 / 박스와 글자가 모두 맞은 F1 | 주 지표는 위치+글자 |
| 항목명→값 위치+글자 F1 | relation | 기준 글자 옆 값의 박스와 글자가 모두 맞은 F1 | 항목명 → 값 관계 |
| 그린 박스→글자 일치 / 좌표 F1@0.75 | marked_ocr / marked_box | 색 박스 안 글자 일치 / 그 박스 좌표를 IoU 0.75 이상으로 낸 F1 | |
| 서류 구비 완전 일치 | doc_check | 빠진 서류·불필요 서류·타인 서류 **세 목록이 모두** 정확한 문항 비율 | 주 지표. 하나라도 틀리면 0이라 엄격합니다 |
| 서류 구비 F1 | doc_check | 세 목록을 합쳐 서류 단위로 맞힌 정도 | 완전 일치보다 높게 나옵니다. 둘의 차이가 크면 "대부분 맞히지만 한두 개씩 틀림" |
| 서류 대조 종합 | cross_check | 정상 문항은 "문제없음"이라고 하면 1점, 변조 문항은 불일치라고 하고 **문제 서류와 값까지** 짚어야 1점 | 주 지표. 정상 문항이 약 6할이라 항상 "문제없음"이라고만 해도 약 60%가 나옵니다 |
| 서류 대조 탐지 | cross_check | 불일치 여부(true/false)만 맞힌 비율 | 종합보다 높으면 "있다는 건 알지만 어디인지 못 짚음" |
| 서류 대조 위치(변조 문항) | cross_check | 변조 문항 중 문제 서류와 값을 맞게 짚은 비율 | **실제 잡아내는 능력은 이 값입니다.** 기준선이 0입니다 |
| 서류 대조 오탐률 ↓ | cross_check | 정상 문항을 불일치라고 한 비율 | 위치 정확도가 오르면서 오탐률도 오르면 "아무거나 의심"하는 것 |
| 심사 질의 정확도 | review | 숫자(허용 오차 안) 또는 예/아니오가 맞은 비율 | 능력별 표(계산, 날짜 계산, 서류 대조)로 나눠 봅니다 |
| 정보 추출 F1 | kie | 값이 있는 항목을 맞힌 정도(위치는 안 봄). 빈 칸(`null`)을 맞혀도 점수에 들어가지 않고, 빈 칸에 값을 지어내면 깎입니다 | 1.x 세트의 주 지표. 빈 칸이 많은 서식도 부풀지 않습니다. 빈 칸까지 센 항목 정확도는 `*.json`의 `field_acc`에 있습니다 |
| 정보 추출 값+위치 F1 | kie | 값도 맞고 박스(`bbox_2d`, 같은 쪽, IoU 0.5 이상)도 맞은 항목의 F1 | 세트 2.0의 주 지표. 위치만 본 `loc_f1`은 `*.json`에 있습니다 |
| 체크·도장·서명 | marks | 항목별로 값을 맞힌 비율(위치는 안 봄) | 1.x 세트의 주 지표. 전부 비었다고 해도 약 40%가 나옵니다 |
| 체크·도장·서명 값+위치 F1 | marks | 값도 맞고 체크된 □·찍힌 자리의 박스도 맞은 항목의 F1 | 세트 2.0의 주 지표 |
| 서류 분류 | classify | 서류명이 정식 명칭과 같은 비율 (공백·문장부호 무시) | 답 안에 정식 명칭이 들어 있으면 맞힌 것으로 보는 값은 `acc_lenient` |
| 전체 받아쓰기 재현율 | ocr_page | 서류에 적힌 값이 받아쓴 글에 들어 있는 비율 | 서식 고정 문구(항목명)는 세지 않습니다 |
| 값 칸 OCR 일치 / CER ↓ | ocr_field | 값 칸 하나를 정확히 읽은 비율 / 틀린 글자 비율 | 인쇄체·손글씨별 표로 봅니다 |

### 세부 표

| 표 | 보는 법 |
|---|---|
| 서류 대조 — 불일치 분류별 | `typo` 오기, `other_person` 타인 서류, `amount` 금액, `logic` 관계(임대인≠소유자 등), `format` 표기만 다름. 이 줄들은 정상 문항과 변조 문항이 섞인 점수입니다. **`format`은 정상 문항만 있으므로 100에서 떨어지면 오탐입니다** |
| 서류 대조 — 사례별 | 14개 사례 각각의 점수. 드문 사례(`fx_beneficiary`, `seller_owner` 등)는 `n`이 작아 흔들립니다 |
| 심사 질의 — 능력별 | 서류 대조(예/아니오), 날짜 계산, 계산(비율·합계), 표 계산. 계산 쪽이 보통 가장 낮습니다 |
| 서류 구비 — 빠진 서류 수별 | 0, 1, 2건. 0건(다 낸 경우)에서 틀리면 없는 누락을 지어낸 것입니다 |
| 정보 추출 — 서식 그룹별 | `hana`(하나은행 원본 서식)와 나머지(HTML 서식)를 나눠 봅니다 |
| 값 칸 OCR — 인쇄체/손글씨별 | 손글씨가 보통 많이 낮습니다 |
| 글자 찾기·칸 잘라 읽기 — 깨끗한 쪽 / 변형한 쪽 | 둘의 차이가 노이즈(스캔·촬영)에 얼마나 강한지입니다 |

## 찍어도 나오는 점수 (기준선)

아래 값 근처의 점수는 모델이 그 과제를 사실상 못 푼다는 뜻입니다. 평가 세트 기본 구성 기준의 대략적인 값입니다.

| 지표 | 찍는 방법 | 그래도 나오는 점수 |
|---|---|---|
| 서류 대조 종합 | 항상 "문제없음" | 약 60% |
| 서류 대조 탐지 | 항상 "문제없음" | 약 60% |
| 서류 대조 위치 | 항상 "문제없음" | 0% |
| 심사 질의 (예/아니오 문항) | 항상 "아니오" | 약 57% |
| 체크·도장·서명 | 전부 비었다고 | 약 40% |
| 서류 구비 완전 일치 | 세 목록 모두 빈 칸 | 약 15% |
| 정보 추출 F1 | 전부 `null` | 0% |

## 점수 차이가 의미 있나

문항 수가 유한해서 점수에는 흔들림이 있습니다. 대략적인 95% 범위는 다음과 같습니다(점수 50% 근처 기준, 끝으로 갈수록 좁아짐).

| 문항 수 n | 흔들림 |
|---:|---|
| 2,000 이상 (서류 대조, 심사 질의, 값 칸 OCR) | ±2%p |
| 약 480 (서류 구비, 분류, 정보 추출) | ±4.5%p |
| 100 | ±10%p |
| 30 이하 (세부 표의 작은 줄) | ±18%p 이상 |

- **판단 기준:** 두 모델의 차이가 이 범위보다 작으면 "차이 없음"으로 봅니다.
- **두 모델 비교:** 같은 문항을 풀기 때문에 실제로는 이보다 조금 더 작은 차이도 의미가 있을 수 있습니다. 확실하지 않으면 studio ⑥ 문항 탭에서 두 모델의 문항 점수를 견주어 보세요.

## OCR 열 (읽기 능력 유지)

따로 된 OCR 유지 표는 없습니다. OCR 데이터셋을 `data.benchmark`에 넣으면 같은 표에 OCR 열(칸 잘라 읽기 ~ 그린 박스)이 생기고, 그 Δ가 곧 읽기 능력 유지입니다.

- **볼 것:** 출발 모델 대비 Δ입니다. 출발 모델이 이미 OCR을 학습한 모델이면 몇 %p 정도 떨어지는 건 흔합니다.
- **크게 떨어졌을 때:** 박스 F1이 10%p 이상 떨어지는 식이면 SFT에 섞는 OCR 문항을 늘리세요(`data.train`의 OCR 데이터셋 `count`). 데이터가 바뀌므로 `data.output_dir`을 새 이름으로 하고 `--from prepare`로 다시 돌립니다.
- **언제 걱정하나:** "값 칸 OCR"이나 "전체 받아쓰기"가 함께 떨어졌다면 실제로 읽기 능력이 약해진 것입니다.
- OCR 정답이 사내 OCR 그대로(의사정답)면 점수는 "사내 OCR과 얼마나 같은지"입니다.

## 학습 중 로그

ms-swift가 학습 폴더에 `logging.jsonl`을 남깁니다(`train/runs/exp1/sft/<버전>/`, `train/runs/exp1/grpo/<버전>/`). 항목 이름은 ms-swift 버전에 따라 조금 다를 수 있습니다.

### SFT

| 값 | 뜻 | 정상 |
|---|---|---|
| `loss` | 학습 문항에서의 손실 | 처음 수백 step에 빠르게 내려가고 천천히 낮아짐 |
| `eval_loss` | 검증 문항(학습에 안 쓴 200문항)의 손실 | `loss`와 함께 내려감. `loss`만 내려가고 `eval_loss`가 오르면 과적합 |
| `token_acc` | 정답 토큰을 맞힌 비율 | 오름 |

### GRPO

| 값 | 뜻 | 정상 / 이상 |
|---|---|---|
| `reward` (`rewards/…/mean`) | 생성한 답들의 평균 보상(벤치마크 채점과 같은 점수, 0~1) | 천천히 오름. 처음부터 0.9 이상이면 배울 게 적은 문제들입니다 |
| `reward_std` | 한 문제에 만든 답 8개의 보상 차이 | 0보다 커야 학습됩니다. 계속 0 근처면 답이 다 같아 배울 신호가 없습니다 |
| `frac_reward_zero_std` | 답 8개의 보상이 모두 같은 문제의 비율 | 낮을수록 좋음. 0.8 이상이면 GRPO가 거의 헛돕니다(문제가 너무 쉽거나 너무 어려움) |
| `completions/mean_length` | 답 길이(토큰) | 갑자기 길어지면 반복 출력. `completions/clipped_ratio`(잘린 답 비율)가 오르면 형식 오류가 됩니다 |
| `kl` | SFT 모델에서 멀어진 정도 | 천천히 오름. 급하게 오르면 학습률이 큰 것 |

- **문제 선정 결과:** `logs/mine.log`에서 확인합니다.
  - `hard_available`은 후보 3000개 중 SFT가 보상 0.9 미만을 받은 문제 수입니다.
  - 이 값이 아주 작으면 SFT가 이미 거의 다 맞힌다는 뜻입니다. 이때는 GRPO로 오를 여지가 적습니다.
- **생성된 답 보기:** `log_completions`가 켜져 있어 학습 중 생성한 답도 학습 폴더에 남습니다. 보상이 안 오를 때 실제 답을 확인하세요.

## 이상 신호와 대처

| 보이는 것 | 의심 | 대처 |
|---|---|---|
| SFT 뒤에도 답 형식 오류가 5% 이상 | 답이 잘리거나 형식을 덜 배움 | studio에서 답 끝 확인. 잘렸으면 `max_new_tokens`·`max_completion_length` 확인 |
| 서류 대조 종합 ≈ 60%, 위치 ≈ 0 | 항상 "문제없음" | 변조 문항 비율, SFT 데이터의 `task_mix` 확인 |
| 위치는 오르는데 오탐률도 크게 오름 | 아무거나 의심 | GRPO 전후 비교. GRPO에서 생겼으면 `format_only` 정상 문항이 문제 풀에 충분한지 확인 |
| 탐지는 높은데 위치가 낮음 | 불일치를 느끼지만 서류·값을 못 짚음 | studio로 `issues` 내용 확인. 서류명을 다르게 쓰는지 봅니다 |
| 심사 질의 계산만 낮음 | 숫자를 잘못 읽거나 계산 실수 | studio에서 읽은 값과 계산을 분리해 봅니다. 정보 추출 F1이 높으면 계산 문제 |
| 서류 구비 F1은 높은데 완전 일치가 낮음 | 서류명을 조금씩 다르게 씀 | 답의 서류명이 필수 서류 목록 표기와 같은지 확인 |
| SFT보다 GRPO가 떨어짐 | 보상 신호 없음, 또는 과하게 학습 | `frac_reward_zero_std`, `kl` 확인. `grpo.count`나 학습률을 줄여 `--from grpo` |
| OCR 열이 크게 떨어짐 | 잊어버림 | OCR 데이터셋 `count`를 늘리고 새 `data.output_dir`로 `--from prepare` |

## 주의

- **합성 서류입니다.** 학습 데이터와 평가 세트는 같은 생성기로 만들어서 고객만 다릅니다. 그래서 점수가 크게 오르는 건 당연하고, 실제 서류 성능은 이보다 낮습니다. 실제 서류는 실서류 데이터셋(studio ④·⑤)을 평가에 넣어 따로 확인하세요.
- **출발 모델 점수에는 "형식을 모르는 몫"이 섞여 있습니다.** 그래서 출발 → SFT 상승폭의 상당 부분은 형식을 배운 효과입니다. 실력 변화는 SFT → GRPO 사이와 세부 표에서 보는 편이 정확합니다.
- **조건이 다른 결과는 비교표를 만들지 않습니다.** 평가 문항이나 추론 설정(temperature 등)이 다른 보고서끼리는 표 만들기를 거부합니다. 섞여서 잘못 비교하는 일을 막기 위해서입니다.
