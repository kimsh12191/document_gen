# OCR·은행업무 벤치마크

docgen이 만드는 합성 서류로 **고정된 평가 세트**를 만들고, 모델을 돌리고, 채점합니다. 코드는 [docgen/bench/](../docgen/bench/)에 있습니다.

- **OCR:** 글자를 읽는 능력
- **문서 이해:** 서류를 알아보고 값을 뽑는 능력
- **은행 업무:** 고객 한 명이 낸 서류 묶음을 보고 심사 담당자처럼 판단하는 능력

이 세 가지를 따로 잽니다.

```bash
# 1) 평가 세트 만들기 (기본: 서류 476종 x 1건 + 업무 12종 x 고객 4명, 약 16분, 약 600MB)
python -m docgen.bench build --out bench_out

# 2) 모델 돌리기 — OpenAI 호환 API (vLLM, SGLang, LMDeploy 서버 등)
vllm serve Qwen/Qwen2.5-VL-7B-Instruct --port 8000 --limit-mm-per-prompt image=16
python -m docgen.bench run --bench bench_out --pred preds/qwen25vl7b \
    --base-url http://localhost:8000/v1 --model Qwen/Qwen2.5-VL-7B-Instruct --workers 8

# 3) 채점 → preds/qwen25vl7b/report.md, report.json
python -m docgen.bench eval --bench bench_out --pred preds/qwen25vl7b

# 모델 여러 개 비교표
python -m docgen.bench eval --bench bench_out --pred preds/model_a --pred preds/model_b
```

- **빠른 점검:** `run --limit 20`이면 과제마다 앞 20문항만 돌립니다.
- **이어서 돌리기:** 중단되거나 오류가 난 문항은 같은 명령을 다시 실행하면 그것만 다시 보냅니다.
- **예측 없음·파싱 실패:** 0점으로 셉니다(CER은 1). 빈 답이 빈 칸(null)이나 "도장 없음"을 우연히 맞히지 않게 하려는 것입니다. 보고서에 건수가 따로 나옵니다.
- **채점기 점검:** `run --oracle`은 정답을 그대로 출력으로 씁니다. 이때 모든 과제가 100점이어야 합니다.

## 실행 환경

데이터 생성기(`python -m docgen generate --png`)가 돌아가는 환경(같은 도커 이미지)이면 그대로 됩니다. 따로 설치할 것은 없습니다.

| 단계 | 필요한 것 |
|---|---|
| `build` | 생성기 `--png --augment`와 같음: `docgen/requirements.txt`, Playwright Chromium, 한글 폰트(`fonts-nanum`, `fonts-noto-cjk`) |
| `run` | Pillow, 그리고 컨테이너에서 모델 서버(vLLM 등) 주소로 나가는 네트워크 |
| `eval` | 파이썬 표준 라이브러리만 (생성기 코드 import) |

docgen 도커 컨테이너를 띄우는 방법은 [docker/README.md](../docker/README.md)에 있습니다. 컨테이너에 SSH로 접속하면 코드 폴더에서 시작하고, 결과는 `/out`(서버 폴더와 연결)에 둡니다.

```bash
# 예: docgen 컨테이너 안에서 평가 세트 만들기
python -m docgen.bench build --out /out/bench_out --workers 8
# 같은 서버의 vLLM 서버로 예측. 컨테이너 안의 localhost 는 컨테이너 자신이라 서버의 내부망 IP 를 씀
python -m docgen.bench run --bench /out/bench_out --pred /out/preds/my_model --base-url http://<서버IP>:8000/v1 --model <모델>
# SSH 없이 서버 터미널에서
docker exec -u docgen docgen bash -lc 'cd ~/document_gen && python -m docgen.bench build --out /out/bench_out'
```

평가 세트는 약 600MB이고, `build`는 CPU 코어 하나로 약 16분 걸립니다. 원본 서식 배경 이미지는 처음 렌더링할 때 `~/.cache/docgen/bg/`에 만들어지므로, 컨테이너를 여러 번 띄울 거면 이 경로도 볼륨으로 두면 빨라집니다.

## 과제

| 영역 | 과제 | 입력 → 출력 | 주 지표 |
|---|---|---|---|
| OCR | `ocr_field` | 값 칸 하나를 잘라낸 이미지 → 적힌 글자 | 완전 일치율 (CER 함께 보고) |
| OCR | `ocr_page` | 서류 전체(여러 쪽) → 전체 받아쓰기 | 값 재현율: 정답 값이 받아쓴 글에 들어 있는 비율 |
| 문서 이해 | `classify` | 서류 → 서류명 | 정확도 |
| 문서 이해 | `kie` | 서류 + 항목 목록(키·항목명) → 값과 위치 목록 `[{key, value, bbox_2d, page}]` | 값+위치 F1 (값 F1·위치 F1·항목 정확도 함께) |
| 문서 이해 | `marks` | 서류 + 체크박스·도장·서명 목록 → 상태와 위치 목록 | 값+위치 F1 (항목 정확도·위치 F1 함께) |
| 은행 업무 | `doc_check` | 업무명 + 필수 서류 목록 + 제출 서류 첫 쪽들 → 빠진 서류·불필요 서류·타인 서류 | 완전 일치율 (F1 함께) |
| 은행 업무 | `cross_check` | 서류 2~3건 → 불일치 여부와 문제 서류·항목 (불일치 사례 14종) | 종합 점수 (탐지·위치·오탐률 함께) |
| 은행 업무 | `review` | 심사 질문 + 관련 서류 → 숫자 또는 예/아니오 | 정확도 |

### OCR

- **`ocr_field`:** 서류마다 값 칸 6개를 골라 잘라냅니다(위아래 여백 포함).
  - 결과는 글씨(`print` 인쇄체 / `hand` 손글씨), 촬영 조건, 값 종류(이름·주민번호·금액·날짜·주소 …), 손글씨 정정 여부로 나눠 봅니다.
  - 손글씨는 하나은행 원본 서식(`hf*`)에서 나옵니다.
- **`ocr_page`:** 전체 정답 글자가 없어서 "문서에 적힌 값이 받아쓴 글에 들어 있는가"로 잽니다.
  - 공백은 무시합니다.
  - `recall_fuzzy`는 값 길이의 20%까지 글자가 틀려도 찾은 것으로 셉니다.
  - 서식의 고정 문구(항목명, 안내문)는 채점하지 않습니다.

### 문서 이해

- **`classify`:** 서류명을 자유롭게 답하게 하고, 공백·문장부호를 뺀 뒤 정식 명칭과 같으면 맞습니다.
  - `acc_lenient`는 답 안에 정식 명칭이 들어 있으면 맞은 것으로 셉니다.
- **`kie`:** 항목 키와 항목명을 질문에 같이 줍니다. 그래서 학습하지 않은 모델도 같은 조건으로 잴 수 있습니다.
  - 키가 많은 서류는 40개까지만 묻습니다.
  - 빈 칸은 `null`이 정답입니다.
  - 값은 **타입에 맞춰 비교**합니다.
    - 날짜: `2025년 9월 20일` = `2025-09-20`
    - 금액: `금 오억원정 (₩500,000,000)` = `500000000`, `327,000,000원` = `327,000,000`. 1원만 달라도 틀립니다.
    - 번호(전화·주민·계좌): 숫자만 비교
    - 그 밖: 공백·문장부호 무시
  - 중첩 JSON(`{"loan": {"amount": ...}}`)으로 답해도 점 경로로 펴서 채점합니다.
  - **위치 (세트 2.0부터):** 항목마다 `bbox_2d`(그 쪽 이미지 기준 0~1000 정수, OCR 과제와 같은 좌표)와 `page`(1부터)를 답합니다. 빈 칸은 `{"key", "value": null}`로 위치 없이 답합니다.
    - 값 점수(`f1`): 위치는 보지 않습니다. 1.x 세트 점수와 뜻이 같고, 위치를 못 내는 모델도 잽니다 (값만 담은 객체로 답해도 됨).
    - 위치 점수(`loc_f1`): 같은 키·같은 쪽에서 IoU 0.5 이상인 짝 (OCR 과제의 짝짓기와 같음).
    - 값+위치 점수(`vl_f1`, 주 지표): 박스도 맞고 값도 맞은 항목.
- **`marks`:** 체크된 보기 글자, 복수 선택 목록, 도장·서명 true/false를 맞힙니다.
  - 세트 2.0부터 목록으로 답합니다: 체크된 보기마다 `{key, value: 보기 글자, bbox_2d: 체크된 □, page}`, 체크된 것이 없으면 `{key, value: null}`, 도장·서명은 `{key, value: true/false, bbox_2d: 찍힌 자리}`. 점수는 `kie`와 같이 값(`acc`)·위치·값+위치(주 지표).
  - 은행 직원 결재란(담당·책임자·본인확인 등)도 항목에 들어갑니다. 키가 `seal.staff.책임자`처럼 `staff`를 포함하고, 직원 도장·서명이 찍혔는지를 묻습니다. 고객 도장 칸 옆의 직원 도장을 고객 도장으로 착각하지 않는지도 함께 봅니다.

### 은행 업무 (업무 묶음)

시나리오 12종([생성기 사용법](../docgen/README.md#사용법))마다 고객 4명분 서류 묶음을 만듭니다. 묶음 서류는 모두 현행 하나은행 서식이라 날짜가 서로 맞습니다.

- **`doc_check` — 서류 구비 확인**
  - 필수 서류 중 0~2건(30/50/20%)을 빼고, 나머지 첫 쪽만 순서를 섞어 줍니다. 질문에 고객 성명이 들어갑니다.
  - 30%는 제출 서류 하나를 **다른 고객의 같은 서류**로 바꿉니다. 그 서류는 `not_customer`이면서 `missing`에도 들어갑니다(본인 서류는 안 낸 것).
  - 35%는 **업무와 상관없는 서류** 한 건(다른 시나리오의 서류)을 끼워 넣습니다. 그 서류는 `not_required`입니다.
  - 답 형식: `{"missing": [...], "not_required": [...], "not_customer": [...]}`
    - 세 목록이 모두 맞아야 완전 일치입니다.
    - 목록별 일치율과 전체 F1을 함께 보고합니다.
    - 비슷한 서류명은 후보 서류에 대응시켜 채점합니다.
- **`cross_check` — 서류 간 대조:** 아래 [불일치 사례](#불일치-사례) 14종을 묶음마다 적용할 수 있는 만큼 만듭니다(묶음당 평균 4개 안팎).
  - 사례마다 깨끗한 서류에서 먼저 그 관계가 맞는지 확인합니다. 예를 들어 임대인이 등기부 소유자와 같은지 봅니다. 맞지 않는 묶음에서는 그 사례를 만들지 않습니다. 생성기 자체의 불일치가 정답을 오염시키지 않게 하려는 것입니다.
  - 각 사례는 50% 확률로 **변조**하고, 나머지는 같은 서류 조합의 **정상 문항**으로 냅니다.
  - 변조는 HTML의 해당 칸 글자만 바꿔 다시 렌더링합니다. 같은 서류 안에 같은 값이 여러 번 찍혀 있으면 함께 바꿉니다(금액·관계 사례). 바뀐 서류는 그 값 말고는 원본과 같고, 촬영 증강도 같습니다.
  - 타인 서류 사례는 같은 종류 서류를 다른 고객 프로필로 새로 렌더링합니다.
  - 보여 주는 서류는 사례에 관련된 2~3건뿐입니다. 상관없는 서류에서 생기는 우연한 불일치를 줄이려는 것입니다.
  - 채점
    - 정상 문항: `consistent: true`이면 맞습니다.
    - 변조 문항: 불일치라고 하고, 문제 서류(관계 사례는 짝 서류도 인정)와 함께 그 값·원래 값·항목명 중 하나를 짚어야 맞습니다.
    - 탐지 정확도, 위치 정확도, 오탐률을 따로 보고하고, 사례·분류별로도 나눠 봅니다.
  - `format_only`는 항상 정상 문항입니다. 같은 값을 한 서류에서만 다른 표기로 바꿉니다(날짜 형식, `원` 표기, 주민번호 뒷자리 가림, 전화 하이픈, 주소 참고항목). 이걸 불일치라고 하면 오탐입니다.
- **`review` — 심사 질의:** 정답은 서류 정답값으로 계산합니다. 질문에 반올림 자릿수와 기준일을 적어 답이 하나로 정해집니다.

| 규칙 | 시나리오 | 질문 | 능력 |
|---|---|---|---|
| `ltv` | 주택담보 | 대출신청금액 ÷ 매매대금 (%) | 계산(비율) |
| `collateral_ratio` | 주택담보 | 채권최고액 ÷ 약정 대출금액 (%) | 계산(비율) |
| `jeonse_ratio` | 전세자금 | 대출신청금액 ÷ 임차보증금 (%) | 계산(비율) |
| `income_multiple` | 신용대출 | 대출신청금액 ÷ 원천징수 급여 합계 (배) | 계산(비율) |
| `age` | 신분증 + 신청서가 있는 업무 | 신청일 기준 만 나이 (주민번호로) | 날짜 계산 |
| `tenure` | 대출 | 입사일~신청일 만 재직연수 | 날짜 계산 |
| `doc_valid` | 발급일이 있는 서류가 있는 업무 | 발급 후 90일 이내인가 (예/아니오) | 날짜 계산 |
| `net_pay` | 신용대출 | 급여명세서 지급액계 − 공제액계 | 계산(합계) |
| `sales_rest` | 주택담보 | 매매대금 − 계약금 − 중도금 | 계산(합계) |
| `invoice_sum` | 해외송금 | 상업송장 품목 금액 합계 | 표 계산 |
| `tuition_due` | 유학생 송금 | 이전 잔액 + 청구액 − 납부액 | 계산(합계) |
| `debt_ratio` | 법인 여신 | 부채총계 ÷ 자본총계 (%) | 표 계산 |

예/아니오 질문이 있는 불일치 사례는 같은 서류로 `review` 문항(`case:<사례>`)도 만듭니다. 예: "임대차계약서의 임대인이 등기사항전부증명서의 현재 소유자와 같은 사람입니까?" 변조 문항이면 "아니오"가 정답입니다.

`doc_valid`는 묶음 서류의 발급일이 대개 신청일과 같아 답이 늘 "예"가 됩니다. 그래서 절반은 발급일을 93~400일 앞당긴 사본을 만들어 묻습니다. 나머지 절반은 0~88일 전으로 옮깁니다.

### 불일치 사례

실제 심사·금융사고 사례를 바탕으로 골랐습니다. 근거는 아래 [참고 자료](#참고-자료)에 있습니다.

| 사례 | 분류 | 무엇을 바꾸나 | 실제 사례 근거 | 시나리오 |
|---|---|---|---|---|
| `typo` | 오기 | 여러 서류에 나오는 성명·주민번호·연락처·주소·계좌·생년월일 한 자리 | 신청서·약정서 기재 오류 | 전체 |
| `other_person` | 타인 서류 | 신분증·등본·재직증명서·소득서류 등 한 건을 다른 고객 것으로 | 명의도용, 가족 서류 혼입 | 전체 |
| `loan_vs_agreement` | 금액 | 신청서 또는 약정서의 대출금액(한글 금액 포함) | 약정서 작성 오류·변조 | 신용·주담대·사업자·법인 |
| `income_inflated` | 금액 | 원천징수영수증 급여·합계를 20~60% 부풀림 → 소득금액증명원과 불일치 | 작업대출: 소득 서류 위·변조 | 신용·주담대·전세 |
| `lease_owner` | 관계 | 등기부 현재 소유자를 다른 사람으로 → 임대인 ≠ 소유자 | 전세사기: 계약서상 임대인이 실소유자가 아님 | 전세 |
| `seller_owner` | 관계 | 등기부 현재 소유자를 다른 사람으로 → 매도인 ≠ 소유자 | 무권리자 매도·허위 매매계약 | 주담대 |
| `hire_date` | 관계 | 재직증명서 입사일을 1~4년 앞당김 → 건강보험 자격취득일(또는 신청서 입사일)과 불일치 | 작업대출: 재직기간 부풀리기, 건보 자격으로 재직 확인 | 신용 등 |
| `rep_director` | 관계 | 법인인감증명서 대표자를 다른 사람으로 | 대표이사 변경 미반영·권한 없는 자의 신청 | 법인 |
| `contract_before_apply` | 관계 | 약정일을 신청일보다 앞으로 | 서류 소급 작성 | 대출 |
| `collateral_short` | 관계 | 채권최고액을 대출금의 60~95%로 | 근저당 설정 금액 부족 | 주담대 |
| `jeonse_over` | 관계 | 전세대출 신청금액을 보증금의 105~130%로 | 허위 임대차·보증금 부풀리기 | 전세 |
| `sales_sum` | 관계 | 매매대금을 8~25% 올림 → 계약금+중도금+잔금과 불일치 | 업계약: 대출 한도를 늘리려 매매가를 부풀림 | 주담대 |
| `fx_beneficiary` | 관계 | 송금 수취인을 다른 회사로 → 상업송장 수출자와 불일치 | 증빙과 다른 상대방에게 송금 | 해외송금 |
| `format_only` | 정상(표기 차이) | 같은 값을 다른 표기로 | 오탐 방지 | 전체 |

생성기 데이터 특성상 조건이 맞는 묶음이 적은 사례가 있습니다(`fx_beneficiary`, `seller_owner` 등). 사례별 문항을 늘리려면 `--bundles`를 키우세요.

## 평가 세트

기본 설정으로 만든 세트의 문항 수입니다.

| ocr_field | ocr_page | classify | kie | marks | doc_check | cross_check | review |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 2,378 | 464 | 476 | 476 | 410 | 48 | 198 | 241 |

- `ocr_field`는 손글씨 1,379개, 인쇄체 999개입니다.
- `cross_check` 198문항은 정상 125(표기만 다름 44 포함), 변조 73입니다.
  - 변조 문항 사례별: 타인 서류 26, 오기 21, 신청↔약정 금액 8, 약정일<신청일 5, 재직기간 5, 소득 부풀리기 3, 업계약 3, 채권최고액 2, 법인 대표자 2, 임대인/매도인≠소유자 각 1, 전세대출>보증금 1, 송금 수취인 1
- `doc_check` 48문항 중 타인 서류가 섞인 것 11, 불필요 서류가 섞인 것 16입니다.
- **문항 수:** 은행 업무 과제는 문항이 적어 점수 오차가 크고, 일부 사례는 기본 설정에서 1~4문항뿐입니다. 모델끼리 전체 점수를 비교하려면 `--bundles 20` 이상, 사례별로 보려면 `--bundles 40` 이상으로 늘리세요(`docgen/scripts/make_bank_data.sh` 기본값 40). 고객이 1명 늘 때마다 묶음 12개가 추가되고, 묶음 하나는 약 20초 걸립니다.

- **고정 seed:** 같은 설정이면 언제 만들어도 같은 세트가 나옵니다(같은 코드 기준). `--workers` 수와도 상관없습니다.
  - 단일 서류 과제는 고객 seed `1,000,000`부터, 업무 묶음은 `2,000,000`부터 씁니다.
  - 학습 데이터(`python -m docgen generate --seed 0 …`)와 겹치지 않게 하려는 것입니다. **`generate`에는 seed 1,000,000 미만을 쓰세요.** 은행 업무 학습 데이터(`--split train`)는 따로 떨어진 seed를 씁니다([아래](#은행-업무-학습-데이터---split-train)).
  - 세트 버전 1.1부터 증강 노이즈가 이미지마다 고정됩니다. 1.0 세트와는 문항·정답은 같고 스캔·촬영·팩스 이미지의 노이즈 무늬만 다릅니다.
  - 세트 버전 1.2부터 하나은행 원본 서식(`hf…`)의 결재란에 직원 도장·서명이 찍힙니다. 원본 서식의 이미지와 `marks` 문항이 1.1과 다르므로 **1.1 세트의 점수와 직접 비교하지 마세요.** 다른 서류는 그대로입니다. 1.1로 만든 데이터는 일부만 고치지 말고 새로 만듭니다 → [tutorial.md 5-1](tutorial.md#5-1-생성기가-바뀌었을-때-예-평가-세트-12)
  - 세트 버전 3.0부터 **키 사전의 공통 키로 묻고 답합니다** (`docgen/dictionary/`, studio 키 사전). 서식이 달라도 같은 값이면 같은 키입니다 — 대출신청서의 `applicant.name`, 재직증명서의 `employee.name`, 주민등록증의 `name` 이 모두 `customer.name`(고객 성명). 공통 키에 이은 칸만 바뀌고 나머지는 서식의 키 그대로이며, 라벨 필드의 원래 키는 `doc_key` 에 남습니다. 분류 정답은 문서명이고(같은 문서의 서식이 여러 개여도 하나), 서식 이름·다른 이름으로 답해도 맞습니다. 10단계의 공식 대조 html 69종과 값 채우기 변경도 3.0부터입니다. **2.0 과 kie·marks·분류 점수는 바로 비교하지 마세요.**
  - 세트 버전 2.0부터 `kie`·`marks` 답에 위치가 들어가고 주 지표가 값+위치 F1 입니다. 건강보험료 납부확인서의 정산 분할납부 변형이 정한 확률(15%)대로 나옵니다(1.x 에서는 4월이 들어간 서류마다 붙음). **1.x 와는 값 점수(`f1`, `acc`)만 비교하세요.** 1.x 세트도 같은 채점기로 채점됩니다. 학습 데이터도 같은 2.0 코드로 새로 만듭니다 (학습 레코드의 `grounding`·`marks` 답도 같은 목록 꼴).
- **촬영 조건:** 서류마다 깨끗한 원본 50%, 스캔 20%, 촬영 15%, 팩스 15%입니다. 위치 정답은 증강에 맞춰 옮깁니다.
- **기록:** `meta.json`에 만든 설정, 생성기 커밋, 과제별 문항 수가 남습니다. 결과를 비교할 때는 같은 `meta.json`의 세트인지 확인하세요.

| 옵션 | 기본 | 뜻 |
|---|---|---|
| `--types` | all | 단일 서류 과제에 쓸 서류 (ID, 그룹명) |
| `--per-doc` | 1 | 서류 종류마다 샘플 수 |
| `--scenarios` | all | 업무 묶음 과제에 쓸 시나리오 |
| `--bundles` | 4 | 시나리오마다 고객 수 |
| `--fields-per-doc` | 6 | 서류마다 `ocr_field` 문항 수 |
| `--max-keys` | 40 | `kie`·`marks` 한 문항에 묻는 최대 항목 수 |
| `--scale` | 2.0 | 이미지 배율 (A4 한 쪽 약 1588×2246) |
| `--workers` | 1 | 동시에 렌더링할 프로세스 수. 결과는 같고 빨라집니다 (프로세스마다 Chromium 하나) |
| `--split` | test | `train`이면 학습 데이터 ([아래](#은행-업무-학습-데이터---split-train)) |
| `--start` | 0 | seed 시작 번호. 학습 데이터를 나중에 더 만들 때 씁니다 |

### 문항 형식 (`tasks/<과제>.jsonl`)

```json
{"id": "kie/loan_application_1000000", "task": "kie",
 "images": ["images/loan_application_1000000.jpg"],
 "prompt": "이 문서에서 아래 항목의 값과 위치를 찾아 JSON 목록으로 답하세요. …\n- applicant.name: 성명\n- loan.amount: 대출신청금액 …",
 "answer": [{"key": "applicant.name", "value": "김나우", "bbox_2d": [264, 231, 384, 249], "page": 1},
            {"key": "loan.amount", "value": "56,000,000", "bbox_2d": [264, 270, 440, 288], "page": 1}],
 "eval": {"fields": {"loan.amount": {"type": "amount", "norm": 56000000, "kind": "amount"}}},
 "meta": {"doc_type": "loan_application", "group": "bank_form", "condition": "scan", "writing": "print", "n_pages": 1}}
```

- `images`는 세트 폴더 기준 상대 경로이고, 질문 앞에 순서대로 넣습니다.
- `answer`는 정답이고, `eval`은 채점에 쓰는 추가 정보입니다.
- 다른 실행기(사내 추론 서버, ms-swift `infer` 등)를 쓰려면 예측을 `{"id": 문항 id, "output": "모델 출력"}` 꼴로 `<pred 폴더>/<과제>.jsonl`에 저장한 뒤 `eval`을 돌리면 됩니다.

### 실행 옵션 (`run`)

| 옵션 | 뜻 |
|---|---|
| `--base-url`, `--model` | OpenAI 호환 서버 주소와 모델 이름 |
| `--api-key-env` | API 키를 읽을 환경변수 (기본 `OPENAI_API_KEY`) |
| `--max-side` | 이미지 긴 변을 이 픽셀 이하로 줄여 보냄 (토큰·비용 조절) |
| `--workers` | 동시 요청 수 |
| `--tasks` | 일부 과제만 (`kie,review`) |
| `--limit` | 과제마다 앞 N 문항만 |
| `--system` | 시스템 프롬프트 |

업무 묶음 문항은 이미지가 여러 장입니다(`doc_check`는 최대 12장, `cross_check`는 최대 10장). vLLM은 `--limit-mm-per-prompt image=16`처럼 한 요청의 이미지 수를 늘려 주세요.

## 은행 업무 학습 데이터 (`--split train`)

`python -m docgen generate`의 학습 데이터는 서류 한 건짜리 과제(정보 추출, 위치, 체크·도장·서명, 질의응답)만 있습니다. 은행 업무 과제(`doc_check`, `cross_check`, `review`)를 학습하려면 같은 `build`를 `--split train`으로 돌립니다.

```bash
# 업무 12종 × 고객 100명 = 묶음 1,200개 → 학습 레코드 약 12,000개, 약 7GB
python -m docgen.bench build --split train --out bank_train --per-doc 0 --bundles 100 --workers 8

# 나중에 더 만들 때: 앞에서 만든 고객 수만큼 --start 를 올려 다른 폴더에
python -m docgen.bench build --split train --out bank_train2 --per-doc 0 --bundles 100 --start 100 --workers 8
```

- **seed:** 단일 서류 `10,000,000`부터, 업무 묶음 `20,000,000`부터입니다. 평가 세트(`1,000,000`·`2,000,000`대), `generate`(0부터)와 겹치지 않습니다.
- **출력:** 평가 세트와 같은 구조에 `swift/`가 더해집니다. `swift/<과제>.jsonl`, `swift/all.jsonl`이 ms-swift 학습 형식이고, 질문은 평가 프롬프트, 답은 정답을 모델 출력 형식(JSON 또는 글)으로 쓴 것입니다. `cross_check`의 채점용 `alt_documents`는 뺍니다.
- **`--per-doc 0`:** 단일 서류 과제(`classify`, `ocr_page`, `ocr_field`, `kie`, `marks`)를 만들지 않습니다. 이 과제들도 평가 프롬프트 형식으로 학습하려면 `--per-doc 1` 이상을 주세요.
- **문항 비율 (묶음 하나당 평균):** `review` 약 5, `cross_check` 약 4, `doc_check` 1. `cross_check`는 정상 55% 안팎, 변조 45% 안팎입니다.
- **속도·용량:** 묶음 하나에 CPU 1코어로 약 10초, 약 6MB입니다.

### 학습할 때

- **이미지 수:** 한 레코드에 이미지가 최대 13장입니다. 원본 해상도(약 1600×2250)를 그대로 쓰면 Qwen2.5-VL 기준 장당 약 4,700토큰이라 길이가 넘칩니다. 학습할 때 이미지 크기를 제한하세요. 예: ms-swift `MAX_PIXELS=1003520` (장당 약 1,280토큰) + `--max_length 16384`.
- **평가도 같은 해상도로:** 서버에서 같은 상한을 주세요. 예: vLLM `--mm-processor-kwargs '{"max_pixels": 1003520}'` 또는 `run --max-side`.
- **잊어버림 방지:** 은행 업무 데이터만 학습하면 OCR·추출 능력이 떨어질 수 있습니다. 앞 단계 학습 데이터(`generate`의 `swift/all.jsonl`)를 일부 섞으세요. 학습 실행(`python -m train`)은 OCR 데이터셋을 `data.train`에 함께 적어 섞습니다([tutorial.md 4-1](tutorial.md#4-1-설정-파일)).

## 해석할 때 주의

- **합성 서류입니다.** 서식·글꼴·증강이 실제 스캔본보다 단순합니다. 실제 서류 성능의 상한에 가깝게 보고, 실제 표본으로 따로 확인하세요.
- **학습 데이터와 같은 생성기입니다.** docgen으로 학습한 모델은 서식 분포를 이미 봤으므로 점수가 유리하게 나옵니다. 범용 모델과 비교할 때 이 점을 적어 두세요.
  - `--split train`으로 학습한 모델은 고객만 다를 뿐 **같은 프롬프트, 같은 서류 조합, 같은 변조 방식**을 봤습니다. 은행 업무 점수가 크게 오르는 건 당연하고, 그 점수는 "이 생성기의 업무 형식을 익혔다"는 뜻입니다. 실제 업무 능력은 실제 서류 묶음으로 따로 확인하세요.
- **`ocr_page`는 값만 셉니다.** 서식 고정 문구를 잘 읽어도 점수에 들어가지 않습니다.
- **`kie`는 항목명을 알려 줍니다.** "어떤 항목이 있는지 찾는" 능력은 재지 않습니다.
