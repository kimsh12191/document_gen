# docgen studio 설계서

- 상태: 11판 (2026-10-20). 1~9단계 구현됨([README.md](README.md)). 7~9단계는 이 PC에서 끝났고 내부망 확인이 남았다([11절](#11-구현-단계)). 남은 결정은 [12절](#12-정해야-할-것)에 있다.
- 위치: `studio/` — 이 설계서와 구현 코드를 함께 둔다. 브랜치 `claude/docgen-studio`.
- 관련 문서: [RESULTS_FORMAT.md](RESULTS_FORMAT.md) — 이미 만든 OCR·추론 결과를 가져올 때의 폴더 형식
- 내부망 배치(2026-10-20 정함): studio는 기존 docgen 도커 컨테이너에서 띄우고, 학습은 폴더를 공유하는 별도 학습 컨테이너에서 한다(3절 원칙 6, 9.9).
- 11판에서 바뀐 것: 범위를 줄였다(studio 안 모델 추론, 표시 요소 그리기·도장 틀 편집기, 영역 하나 제안 작업을 뺌). html 서식은 CLI로 이미지에서 만들고 화면에서 고치는 것으로 키웠다(4.3). 학습 연결(9.9, [TRAINING.md](TRAINING.md))과 데이터셋 설명서(9.1)를 더했다.
- 10판에서 바뀐 것: studio를 **벤치마크 데이터 생성·관리기**로 다시 정의했다(1절). OCR 벤치마크는 1부 형식으로 통일하고(9.2), 데이터셋 등록부·결과 보기·채점(9.1, 9.8), OCR 검수(8.7), 실서류 업무 묶음(9.7)을 더했다.

## 1. 목적

studio는 **은행 벤치마크 데이터를 만들고 관리하는 도구**다. 하는 일은 세 가지다.

1. **서식과 라벨을 사람이 보고, 고치고, 늘린다.** 합성 서류 생성기(`docgen`)의 기본 서식 476종에 공식 대조 HTML 69종을 더한 545종과 그 라벨을 다룬다. 문서 이미지 뭉치를 넣으면 사내 OCR로 읽어 같은 포맷끼리 묶어 주고, 사용자는 그걸 보고 템플릿으로 만들지 정한다.
2. **맞춰진 서식으로 벤치마크 데이터를 만든다.** OCR 벤치마크와 은행 업무 벤치마크를 둘 다 만든다. 같은 생성기로 학습 데이터도 만든다.
3. **이미 라벨링하거나 추론해 둔 결과를 관리한다.** 실서류 OCR·추론 결과를 가져와 사람이 검수하고, 검수한 결과를 실서류 평가 세트로 쓴다. 1부(OCR)·2부(은행 업무)에서 이미 만든 데이터셋, 모델 답, 점수도 같은 화면에서 본다.

### 1.1 관리하는 벤치마크

공식 서식 추가 원칙(2026-10-20): 기존 HTML 70종은 보존하고, 공식 원문을 확보한 경우 별도 HTML ID를 추가한다. 은행 서류는 하나은행 공식 자료실·약관 원문, 정부 서류는 법령 별지를 우선한다. 화면에 `공식대조 HTML` 배지를 붙이고(문서명·분류 정답에는 넣지 않음) `form.json.source`에 발급기관·원문 URL·개정 표기·SHA-256·기존 대응 ID를 남긴다. 종류는 HTML이며, 기존 hf### PDF 배경 버전도 유지한다. 69종(하나은행 44·정부 25)을 추가했다. 사람 검수 완료나 학습/평가 배정은 자동으로 바꾸지 않는다.

인쇄층은 HTML 글자·SVG 도형, 기재란은 기존 `f()`·생성값·정답 좌표 규약을 사용한다. 윤곽선으로만 저장된 원문 글자는 SVG로 보존하므로 그 부분의 문구 편집·DOM 기반 OCR 정답에는 한계가 있다. 자동 추출 기재란을 잇는 서식은 의미·라벨 검수가 별도로 필요하다. 발급 신청서와 발급 증명서, 안내장과 고객 기재 서류를 동일 문서로 매칭하지 않는다. 원문 미확보 항목을 공식 재현본으로 표시하지 않는다. 기존 70종의 개별 검토 결과와 새 서식별 범위는 [대조표](../docgen/manual/OFFICIAL_HTML_AUDIT.md)에 둔다.

| | 합성 (생성기) | 이미지 묶음 (사내 OCR) | 결과 폴더 (이미 있는 OCR·추론) |
|---|---|---|---|
| **OCR** (1부 형식, 8과제) | 생성 라벨 → OCR JSON → 1부 `prepare`. 정답이 정확하다 | 사내 OCR 결과 → 1부 `prepare`. 정답은 의사정답이고, 사람이 OCR을 검수하면 검수 정답이 된다 | 저장된 OCR → 1부 `prepare`. 의사정답과 검수 정답의 구분은 이미지 묶음과 같다 |
| **은행 업무** (2부 형식, `docgen.bench` 8과제) | `docgen.bench build` → 2부 `prepare`. 업무 묶음 단위 | 템플릿 재료와 실서류 예시로 쓴다 | 추론 결과 검수 → 서류 한 장 과제. 실서류 업무 묶음을 만들면 여러 서류 과제도 된다 |

어느 칸에서 만들든 **같은 형식, 같은 채점 코드**를 쓴다. 그래서 합성 점수와 실서류 점수, 사내 OCR 기준 점수와 검수 정답 기준 점수를 나란히 놓을 수 있다.

### 1.2 UI에서 한 번에 관리한다

- **studio 화면 하나에서** 서식 고치기, 데이터셋 만들기, 가져오기·검수, 데이터셋·모델 답·점수 보기를 모두 한다. 메뉴는 이 흐름 순서로 둔다(6절).
- **계산은 기존 코드를 불러서 한다.** 데이터셋을 만들고 채점하는 일은 `docgen.bench`(은행 업무), `ocr/bank_ocr`(1부 OCR), `bank/bank_task`(2부 준비·채점)가 이미 한다. studio는 이 코드를 복사하지 않고 불러 쓴다. 같은 일을 명령줄로 해도 같은 결과가 나온다. 서버에서 큰 데이터셋을 만들 때는 명령줄을 쓴다.
- **데이터셋 등록부** 하나에 모든 데이터셋을 올린다(9.1). studio에서 만든 것이든, 1부·2부 파이프라인이 명령줄로 만든 것이든, 경로만 등록하면 같은 화면에서 문항, 정답, 모델 답, 점수를 본다.
- 모델 학습 실행은 하지 않는다. 학습은 `ocr/` 파이프라인이 한다. studio는 학습이 남긴 모델 답과 점수를 읽어 보여 준다.

지금 생성기는 서류 476종을 만들지만, 이를 다루기가 어렵다.

| 문제 | 현재 |
|---|---|
| 한눈에 보기 어렵다 | 서류 목록, 키 목록, 변형, 근거 출처, 원본 서식 대응, 샘플이 문서 6곳에 흩어져 있다 |
| 라벨 스키마가 선언돼 있지 않다 | 키는 Python 생성 함수의 반환값과 템플릿의 `f()` 호출에서 생긴다. 키 목록 문서도 30번 렌더링해 거꾸로 모은 것이다 |
| 키가 통일돼 있지 않다 | [5절](#5-키-규칙) 참고. 원본 서식은 키의 71%가 한글 항목명이고, 영어 키도 HTML 서식과 원본 서식이 서로 다른 이름을 쓴다 |
| 원본 서식 라벨 품질이 고르지 않다 | 원본 서식 406종의 글자 칸 6,715개 중 31%는 30번 렌더링에서 값이 한 번도 안 채워진다. `는기관`·`미함` 같은 문장 조각을 칸으로 잘못 잡은 곳이 있고, 값이 칸 안 안내 문구와 겹치는 서식도 있다 |
| 고칠 방법이 없다 | 원본 서식 레이아웃은 자동 추출 결과라 손으로 고쳐도 다시 뽑으면 사라진다. HTML 서식은 수정할 때마다 코드를 고쳐야 한다 |
| 새 서식 추가가 무겁다 | 생성 함수 + 템플릿 + 문서 갱신을 개발자가 해야 한다 |

이 도구로 다음이 가능해진다.

- 벤치마크 평가 데이터를 **검수한 서식으로 고정**한다 (학습용/평가 전용 서식 배정 포함).
- 내부망 실서류를 **같은 라벨 형식**으로 옮겨 합성 결과가 실서류를 대변하는지 확인한다.
- 사내 OCR을 사람이 검수한 **OCR 검수 정답**으로, 지금 1부 점수의 한계("사내 OCR과 얼마나 같은지")를 벗어난다.
- 1부·2부의 데이터셋, 모델 답, 점수가 폴더마다 흩어져 있던 것을 한 곳에서 본다.

### 하지 않는 것

- 모델 학습과 추론 실행 (`ocr/`·`bank/`의 1부·2부 파이프라인과 viewer가 한다). studio는 그 파이프라인이 남긴 모델 답과 점수 파일을 읽는다(9.8)
- 계산이 얽힌 값 생성 로직(세액, 잔액 흐름, 서류 간 정합성) 편집. 이 부분은 코드로 남긴다
- 서식·설정의 별도 보관. 서식·설정의 원본은 저장소의 파일이고, UI는 그 파일을 읽고 쓰는 편집기다. 데이터셋 자체는 크고 실서류가 섞이므로 저장소 밖에 두고 등록부에 경로만 남긴다(4.4, 9.1)

|---|---|---|---|

| S11 | OCR 검수 | 가져온 이미지의 사내 OCR 결과를 쪽마다 보며 글자·박스를 고치고, 빠진 글자를 더하고, 확인을 누른다 | 검수한 OCR JSON (사내 OCR 형식 그대로) → OCR 검수 정답 |
| S12 | 결과 보기·채점 | 데이터셋 하나를 열어 문항·정답을 넘겨 보고, 모델 답 파일을 붙여 채점하고, 모델끼리·버전끼리 비교한다. 1부·2부가 명령줄로 만든 폴더도 경로만 등록하면 된다 | 같은 화면의 문항·정답·답·점수, 비교표 |
| S13 | 실서류 업무 묶음 | 검수한 실서류를 고객·업무 단위로 묶고 시나리오를 정한다. 구비·대조·심사 정답은 규칙 코드가 계산하고 사람이 확인한다 | 실서류 은행 업무 평가 세트 |

## 3. 원칙

1. **파일이 원본이다.** UI에서 고친 것은 모두 저장소 안의 JSON 파일로 저장되고 git diff로 검토한다. UI 없이도 파일만으로 생성이 된다.
2. **생성 결과는 다시 만들 수 있어야 한다.** 같은 seed면 같은 이미지가 나오고, 저장한 수정은 생성기가 그대로 읽는다.
3. **자동 결과 위에 사람의 수정을 덧씌운다.** 자동 추출, 분석기 결과, 오토 라벨은 바탕이고, 사람 수정은 별도 파일로 보관한다. 바탕을 다시 만들어도 사람 수정은 남는다.
4. **키는 영어 표준 키가 기본이다.** 한글은 항목명(`label`)에만 쓴다 ([5절](#5-키-규칙)).
5. **외부로 나가는 데이터를 구분한다.** 분석기마다 외부 여부(`external`)를 설정한다. 외부 분석기는 실서류 작업에서 고를 수 없다 ([7.4](#74-데이터-경계)).
6. **이 PC와 내부망에서 똑같이 돈다.**
   - 서버는 **FastAPI + uvicorn**, 화면은 빌드 없는 HTML·JS 한 벌이다. 생성기의 `requirements.txt`에 더해 `studio/requirements.txt`(fastapi, uvicorn, python-multipart)만 설치한다. 2026-10-20 이 PC의 `.venv`에 설치 확인.
   - **내부망 배치:** studio는 **기존 docgen 도커 컨테이너**(Chromium·글꼴·파이썬 포함)에서 띄운다. 새 이미지를 반입하기 어려우므로 이미지는 그대로 쓰고, studio 패키지는 코드에 든 Linux 설치 파일(`studio/wheels/`, 3.4MB)로 컨테이너 안 코드 폴더(`studio_deps/`)에 설치한다(`python -m studio.deps install`, 인터넷 불필요. 2026-10-20 반입 파일만으로 설치가 끝나는 것 확인). 다음에 이미지를 새로 만들 때는 이미지에 들어간다(`docker/requirements.lock`).
   - 윈도우 PC에서는 지금 쓰는 SSH 포트(2222)로 터널을 열어 접속한다. 컨테이너를 다시 만들 필요가 없고, 로그인이 없는 studio를 망에 그대로 열지 않는다([docker/README.md 4절](../docker/README.md#4-studio-띄우기-같은-컨테이너)).
   - 학습은 **별도 학습 컨테이너**에서 한다. 두 컨테이너는 폴더를 공유한다. 같은 폴더가 컨테이너마다 다른 경로로 보이면 설정의 `path_map`으로 바꿔 쓴다(9.9).
   - 브라우저가 없는 곳에서도 studio는 뜬다. 렌더링(미리보기, 합성 데이터 만들기)만 꺼지고, 등록부·평가·검수처럼 렌더링이 필요 없는 화면은 그대로 쓴다.
   - 설정·수정 파일은 JSON이다. YAML 라이브러리를 더 들이지 않기 위해서다.
   - 렌더링은 도커 이미지의 Playwright Chromium, 또는 이 PC에 설치된 Chrome/Edge(`CHROMIUM_PATH`)를 쓴다. 생성 데이터와 미리보기가 픽셀까지 같은 곳은 도커 컨테이너다.
   - 환경마다 다른 것(분석기 주소, OCR 주소, 가져오기 폴더, 실서류 경로, 브라우저 경로)은 설정 파일 하나에 모으고, 코드는 같다.
7. **라벨 형식은 기존 것을 따른다.** `labels/*.json`([docgen/README.md](../docgen/README.md#labelsjson))을 쓴다.
8. **벤치마크 형식과 채점은 1부·2부 것을 쓴다.** OCR 벤치마크는 1부 `bank_ocr prepare`의 결과 폴더, 은행 업무 벤치마크는 `docgen.bench build` + 2부 `bank_task prepare`의 결과 폴더다. studio용 형식을 새로 만들지 않고, 채점도 `bank_ocr.metrics`·`docgen.bench.evaluate`를 불러 같은 숫자를 낸다. `ocr/`의 모듈은 표준 라이브러리와 PIL만 쓰므로 생성기 환경에서 import된다(2026-10-20 확인).

## 4. 서식

### 4.1 서식은 두 종류다

| 종류 | 그리는 방법 | 현재 | 새로 만드는 방법 |
|---|---|---|---|
| `html` | Jinja HTML 템플릿을 브라우저로 렌더링한다. 글꼴·선·여백이 샘플마다 바뀐다 | 70종 | 분석기(CLI)가 이미지를 보고 작성한 뒤 화면에서 수정, 또는 기존 HTML 서식 **복제** 후 수정 (4.3) |
| `overlay` | 서식 이미지를 배경으로 깔고, 지정한 **값 영역**에 값을 쓴다. 모양은 원본과 똑같다 | 406종 (하나은행 원본 PDF) | 빈 서식 PDF·이미지를 올리고 값 영역을 지정 |

어디서 왔는지는 종류가 아니라 속성(`origin`)으로 남긴다.

| 종류 | origin | 뜻 |
|---|---|---|
| `html` | `builtin` | 기존 코드의 서식 (`docgen/docs/*.py` + `docgen/templates/<그룹>/`) |
| `html` | `copy` | 복제한 서식. 부모 서식의 생성 함수를 그대로 쓰고 템플릿만 사본 |
| `html` | `analyzer` | 분석기가 이미지를 보고 만든 서식 |
| `overlay` | `pdf` | 원본 PDF가 배경 (기존 406종) |
| `overlay` | `image` | 스캔·사진 이미지가 배경 (신규) |

### 4.2 overlay 서식: 값 영역 지정

overlay 서식은 **값이 들어갈 영역을 지정하면 된다.** 영역마다 아래를 정한다.

| 영역 종류 | 지정하는 것 | 예 |
|---|---|---|
| `text` | 박스, 키, 타입, 값 출처 | 성명 칸, 주소 칸, 금액 칸 |
| `check` | 보기마다 □ 위치와 보기 글자, 키 | `□ 자택 □ 직장 □ 원치않음` |
| `date` | 년·월·일 빈칸 세 곳, 키 | `____년 __월 __일` |
| `sign` | 서명·날인 자리, 키 | `(서명 또는 인)` |
| `copy` | 자필로 따라 쓰는 칸, 따라 쓸 문구 | `설명을 듣고 이해하였음` |
| `staff` | 결재란 칸, 칸 이름 | 담당, 책임자 |
| 표 반복 행 | 첫 행의 영역들 + 행 수와 행 간격 | 상품명·매수비율 5행 |

자동 추출 결과(`docgen/forms/layouts/`)는 이미 이 형식이다. 사람이 하는 일은 잘못 잡은 영역을 지우고, 빠진 영역을 그리고, 키·타입·값 출처를 채우는 것이다.

**값 출처**는 고객 프로필 값(`profile.person.name` …) 또는 단순 규칙(`rule:date`, `rule:amount`, `rule:choice` + 보기 목록, `rule:free_text`)에서 고른다. 서식 고유 값(상품명, 사유 등)은 지금 `realform.py`가 항목명으로 추론하는 규칙을 그대로 쓸 수 있다.

**배경 지우기.** overlay 배경에 지워야 할 것이 있으면 사람이 지운다. 가져온 문서 이미지(8절)에는 원래 적혀 있던 값이, PDF 배경에는 견본 글자나 미리 인쇄된 예시 값이 남아 있을 수 있다.

| 도구 | 하는 일 |
|---|---|
| 사각형 지우기 | 드래그한 사각형을 **흰색** 또는 **주변색**(사각형 바깥 테두리 픽셀의 중앙값)으로 덮는다. 표 선을 지우지 않게 칸 안쪽으로 잡는다 |
| OCR 단어 지우기 | OCR 단어 박스를 눌러 그 글자만 덮는다 (가져온 문서) |
| 지울 후보 | 같은 양식 문서들 사이에서 **문서마다 달라지는 글자**(= 값)를 후보로 표시한다. 한 번에 확정하거나 하나씩 뺀다 |
| 지운 곳을 값 영역으로 | 값을 지운 자리는 대개 값이 들어갈 자리다. 지운 사각형을 그대로 `text` 영역으로 바꾸고 키·타입을 붙인다 |

- 원본 배경은 그대로 두고 **지운 영역 목록**(`erase: [{"page", "rect", "fill": "white" | "auto"}]`)만 수정 파일에 저장한다. 되돌릴 수 있고, 렌더링할 때 배경에 적용한다.
- 지운 결과는 "지운 배경만 보기"로 확인한다. 실서류에서 온 배경은 덜 지우면 남은 개인정보가 생성 이미지마다 복제되므로, 확인을 눌러야 서식으로 등록된다(13절).

### 4.3 html 서식: 이미지에서 만들고 화면에서 고치기

**왜 html인가.** overlay는 원본 모양을 그대로 쓰는 대신 칸 수가 고정이다. html은 내용에 따라 모양이 바뀐다.
- 거래내역·명세 같은 **표의 행 수를 문서마다 늘리고 줄일** 수 있다.
- 내용이 넘치면 **여러 쪽으로 나뉜다.** 생성기의 `docgen/paginate.js`가 이미 하는 일이다. 표는 줄 단위로 자르고 머리글 줄을 다음 쪽에 반복하며, 쪽 번호와 "다음 쪽에 계속"을 넣는다(최대 12쪽).
- 글꼴·선·여백을 샘플마다 바꿔 같은 서식도 조금씩 다르게 나온다.

**만드는 방법 세 가지**

| 방법 | 하는 일 | origin |
|---|---|---|
| 이미지에서 만들기 | 서식 이미지(빈 서식, 또는 가져오기에서 고른 견본)를 CLI 분석기에 보내 html 템플릿과 서식 정보를 받는다(7.3 `html` 작업). 받은 결과를 아래 편집기에서 고친다 | `analyzer` |
| 복제 | 기존 html 서식을 복제해 템플릿만 고친다. 생성 함수는 부모 것을 그대로 쓰므로 키와 정답 구조가 같다 | `copy` |
| 직접 고치기 | 편집기에서 위 두 가지로 만든 템플릿을 사람이 고친다 | 그대로 |

**값은 서식 정보 파일(`form.json`)이 정한다.** 이미지에서 만든 서식에는 Python 생성 함수가 없으므로, 값을 무엇으로 채울지를 파일에 선언한다.

```json
{
  "name": "거래내역확인서", "group": "finance", "origin": "analyzer", "source_image": "input/page_1.png",
  "fields": {
    "customer.name": {"label": "성명", "type": "text", "source": "profile.person.name"},
    "account.number": {"label": "계좌번호", "type": "text", "source": "profile.account.number"},
    "issue_date": {"label": "발급일", "type": "date", "source": "rule:date"}
  },
  "lists": {
    "rows": {"min": 3, "max": 60, "fields": {
      "date": {"type": "date", "source": "rule:date_seq"},
      "amount": {"type": "amount", "source": "rule:amount"},
      "memo": {"type": "text", "source": "rule:choice", "choices": ["급여", "이체", "카드대금"]}}}
  },
  "paginate": true
}
```

- 템플릿은 `f("customer.name")`으로 값을 넣고, 반복 행은 `{% for r in d.rows %}`로 그린다. `lists.rows`의 `min`~`max` 사이에서 문서마다 행 수를 고르므로, `max`가 크면 자동으로 여러 쪽이 된다.
- 값 출처 규칙(`profile.*`, `rule:*`)은 overlay와 같다(4.2, 신규 `docgen/sources.py`). 계산이 얽힌 값(잔액 흐름, 세액)은 개발자가 생성 함수를 붙인다. 그 전까지는 단순 규칙 값으로 나온다.
- 복제한 서식의 `form.json`은 부모 서식 ID와, 새로 더한 항목만 적는다.

**편집기 화면**

```
┌ 거래내역확인서 (analyzer) ─ seed 0 ─ 행 수 [자동|최소|최대] ─ [다시 렌더링] [저장] [분석기에 다시 고쳐] ┐
│ ┌ 템플릿 (template.html.j2) ─────┐ ┌ 미리보기 ─────────────────────────┐ │
│ │ <table class="rows">           │ │  렌더링 결과  [원본 겹쳐 보기 ◐]   │ │
│ │ {% for r in d.rows %}          │ │  쪽 1/3  ← →                       │ │
│ │  <tr><td>{{ f("rows."~loop... │ │  (박스 층: 값·항목명·체크·도장)     │ │
│ ├ 서식 정보 (form.json) ─────────┤ │                                    │ │
│ │ 항목 표: 키·항목명·타입·값 출처 │ │  검사: 표시 안 된 값 0, 쪽 넘침 없음 │ │
│ └────────────────────────────────┘ └────────────────────────────────────┘ │
└──────────────────────────────────────────────────────────────────────────────┘
```

- 고치면 곧바로 다시 렌더링한다(미리보기 함수, 장당 1초 안팎). **원본 이미지를 반투명하게 겹쳐** 칸 위치·선·글자 크기가 얼마나 같은지 본다.
- 행 수를 최소·최대로 바꿔 보며 표가 늘어날 때 쪽이 제대로 나뉘는지 확인한다.
- 미리보기의 박스를 누르면 템플릿에서 그 `f("키")` 줄로, 항목 표에서 그 키로 간다.
- 저장하기 전에 `docgen check`와 같은 검사를 한다: `form.json`에 선언했는데 템플릿에 안 나오는 키, 템플릿에 있는데 선언 안 된 키, 쪽 넘침, 렌더링 오류.
- 직접 고치다가 막히면 "분석기에 다시 고쳐"로 의견을 적어 CLI에 다시 맡긴다. 지금 템플릿과 의견이 함께 간다(7.3).

**구현 (8단계)** — `docgen/htmlform.py`, `studio/api_html.py`, `studio/static/js/htmled.js`

- 서식 폴더: `docgen/templates/copies/<ID>/`(공개), 실서류 그림에서 만든 것은 `private_forms_dir/<ID>/`. 안에 `template.html.j2`, `form.json`, (분석기면) `source.png`.
  생성기는 처음 `load_all()` 때 이 폴더들을 등록한다(코드 서식 ID 와 겹치면 코드 서식이 이긴다). 템플릿 이름은 `@form/<ID>` 이고 `render.env()` 의 로더가 서식 폴더(또는 저장 전 초안)에서 읽는다.
- 값: 부모가 있으면(복제) 부모 생성 함수 → `fields` 로 더하거나 덮기 → `lists` 마다 행 수 `min~max`. 행마다 `rule:<종류>` 값은 새로 뽑는다. 데이터 난수는 서식 ID 로 정해지므로 복제본은 부모와 키 구조는 같고 값은 다르다.
- 미리보기: `Previewer.render(…, draft={"template", "form"}, rows="min"|"max")`. 라벨에 `checks`(선언했는데 안 나온 키, 템플릿에 있는데 값이 없는 키, 쪽 넘침)를 붙인다. 저장 때는 Jinja 문법·form.json 형식만 막고, 키 검사는 경고만 한다.
- 명령줄 `python -m docgen.preview <서식ID>|--dir <폴더> [--rows max] --out <폴더>`: 쪽 그림·라벨을 쓰고 쪽 수·항목 수·검사를 JSON 한 줄로 낸다. 분석기 CLI 가 작업 폴더 안에서 쓰고, studio 도 결과 검사에 쓴다.
- 확인한 것 (2026-10-20): 거래내역 html 서식이 행 최소 1쪽 · 최대 3쪽(머리글 반복, 쪽 번호)으로 나뉘고, 미리보기 박스를 누르면 템플릿의 그 키(반복 행은 `"rows." ~` 줄)로 간다. 재직증명서를 복제해 항목을 더해 생성된다.

| `workspace_dir` | studio가 만든 데이터셋, 데이터셋 등록부(`registry.json`), 채점 결과. 기본 `studio_workspace/`(git 제외). 1부·2부가 만든 폴더는 옮기지 않고 등록부에 경로만 적는다 (9.1) |
| `import_dir` | 가져올 문서 이미지 뭉치를 두는 폴더 (8절). 실서류가 들어온다. studio는 읽기만 한다 |
| `real_data_dir` | 실서류 검수 결과: 라벨 검수(S5), OCR 검수(S11), 실서류 업무 묶음(S13) |
| `private_forms_dir` | **실서류에서 만든 템플릿.** 값을 지운 배경이라도 실서류에서 나온 것은 공개 저장소에 넣지 않는다. 생성기는 이 경로가 설정돼 있으면 여기 서식도 등록한다 |

### 4.5 overlay 수정 파일 예 (`docgen/forms/overrides/hf169.json`)

```json
{
  "items": [
    {"match": {"page": 0, "label": "직장주소"},
     "rect": [120.5, 233.0, 470.0, 245.0], "note": "안내 문구와 겹쳐 칸을 줄임"},
    {"match": {"page": 0, "key": "는기관"}, "drop": true, "note": "기재란이 아닌 문장 조각"},
    {"match": {"page": 0, "label": "성명"},
     "key": "customer.name", "type": "text", "source": "profile.person.name"}
  ],
  "add": [
    {"kind": "text", "page": 1, "label": "비고", "rect": [80, 600, 500, 620],
     "key": "remark", "type": "text", "source": "rule:free_text"}
  ]
}
```

`match`는 자동 추출 결과에서 고칠 영역을 고르는 조건이다. 다시 추출해 영역 순서가 바뀌어도 쪽과 항목명으로 같은 영역을 찾는다. 못 찾은 수정은 UI가 "깨진 수정"으로 보여 준다.

### 4.6 서식 목록표와 검수 (`docgen/catalog.json`)

```json
{
  "hf169": {"reviewed": {"by": "suhyun", "at": "2026-10-21"}, "split": "train", "note": ""},
  "employment_certificate": {"reviewed": null, "split": "test_only", "note": ""}
}
```

- **검수 완료는 사람이 버튼을 눌러 정한다.** 누른 사람과 날짜를 남긴다.
- 누를 때 자동 검사 결과를 **경고로 보여 주되 막지는 않는다**: 한글 키가 남음, 값 영역이 안내 문구·다른 영역과 겹침, 값이 한 번도 안 채워지는 영역, 깨진 수정.
- 검수 후 그 서식의 파일이 바뀌면 검수 표시를 "수정 후 재검수 필요"로 바꾼다.
- `split`은 `train` / `test_only` / `unassigned`. `docgen.bench build`가 이 값을 읽어 평가 전용 서식은 학습 데이터에서 뺀다.

### 4.7 표시 요소: 손글씨, 체크박스, 도장, 서명, 정정

값 영역에 **무엇이 어떻게 그려지는지**는 값과 따로 다룬다. 지금은 확률과 모양이 코드 상수와 템플릿 매크로에 흩어져 있다.

| 요소 | 지금 만드는 곳 | 지금 설정 | 라벨에 남는 것 |
|---|---|---|---|
| 손글씨 / 인쇄체 | overlay: `realform.py` | 서류마다 손글씨 72%. 손글씨 글꼴 4종(`docgen/fonts/`), 인쇄체 5종. 글자마다 기울기·흔들림 | 손글씨 여부 (`ocr_field`의 `writing` 구분에 쓰임) |
| 체크박스 | overlay: `realform.py` / html: `render.py`의 `checkmark`, 템플릿 매크로 | V(손으로 그은 선)·■ 칠하기·○ | 보기마다 `checked`, □ 위치 `box_bbox` |
| 도장 | html: `_macros.html.j2`의 `seal`(나올 확률 `p`) / overlay: 서명 자리 | 원형·사각, 인감·직인·행원인 | `present`, `kind`, 위치 |
| 서명 | html: `_macros.html.j2`의 `sign` / overlay: 서명 자리 | 선으로 그린 낙서 모양. 서명란은 도장/서명/빈칸 중 하나 | `present`, 위치 (빈칸이어도 자리 위치) |
| 결재란 | overlay: `realform.py` | 처리된 서류 85%, 칸마다 85% 찍음. 원형 50%, 사각 20%, 서명 30% | `seal.staff.*`, `sign.staff.*`, `kind: 행원인` |
| 손글씨 정정 | html 고객 기재 서식 | 4~8% | 바른 값이 정답, `corrected_from`에 틀린 값 |

studio에서는 **"어느 칸에 무엇이 나올지"(확률)와 "어떻게 생겼는지"(모양)를 나눈다.**

**① 확률: 표시 설정 파일** (`docgen/marks.json`)

- 코드 상수를 이 파일로 옮긴다. 전체 기본값을 두고 서식마다 덮어쓴다(서식 정보나 overlay 수정 파일의 `marks` 항목). 예: 이 서식은 손글씨 100%, 이 서명란은 항상 빈칸.
- 영역 편집기에서 영역마다 고를 수도 있다. `text` 영역은 손글씨/인쇄체/서식 기본, `sign` 영역은 도장/서명/빈칸 비율.

**② 모양: 표시 요소 풀** (`docgen/assets/marks/`)

표시 요소마다 **모양 후보를 모아 둔 풀**을 두고, 생성기는 칸마다 풀에서 하나를 (가중치대로) 골라 그린다. 지금 코드가 그리는 모양은 풀의 기본 항목으로 등록한다.

| 풀 | 항목 하나 | 기본 항목 (지금 코드) | 추가하는 방법 |
|---|---|---|---|
| 체크 표시 | 투명 배경 이미지(PNG/SVG) | 손으로 그은 V·✓, ■ 칠하기, ○ | 이미지 올리기 |
| 서명 | 투명 배경 이미지 | 선으로 그린 낙서 생성기 | 이미지 올리기 |
| 도장 | **도장 틀**: 모양(원·사각·타원), 테두리 두께·겹선, 글꼴, 글자 배치(1~4줄, 세로), 인주 색, 번짐·빠짐 | 원형·사각 (인감, 직인, 행원인) | 틀 파일(JSON)에 추가. 글자가 고정인 도장(확인, 검인, 접수)은 이미지로도 |
| 손글씨 글꼴 | 글꼴 파일 | 4종 (`docgen/fonts/`) | `docgen/fonts/`에 넣기 (OFL 등 사용 가능한 글꼴) |
| 인쇄체 글꼴 | 글꼴 이름 | 5종 | 목록에 추가 |

- 화면에서 서명·체크를 그리는 기능과 도장 틀 편집기는 두지 않는다(11판에서 뺌). 화면에서는 항목 보기, 이미지 올리기, 가중치·켜기, 샘플 서식에 적용해 보기만 한다.
- **도장은 이미지보다 틀이 기본이다.** 인감·직인의 글자는 서류의 값(고객 성명, 회사명)과 맞아야 하므로 렌더링할 때 틀에 글자를 채운다.
- **쓸 때마다 조금씩 바꾼다.** 크기, 회전, 잉크 색, 농도, 위치 흔들림을 항목마다 정한 범위 안에서 바꾼다. 같은 서명 이미지가 똑같이 반복되지 않게 한다.
- 항목마다 이름, 종류(라벨의 `kind`: 인감·직인·행원인 …), 출처(기본/그림/업로드), 가중치, 켜기·끄기를 둔다.
- **실서류에서 잘라 온 서명·도장은 개인정보다.** 저장소 풀에 넣지 않고 `private_forms_dir` 아래 내부 전용 풀에만 둔다.
- **라벨에 쓴 항목을 남긴다.** 칸마다 쓴 풀 항목과 글꼴을 `render` 항목으로 기록한다(지금 정답에 없는 정보). 손글씨만, 특정 도장 모양만 따로 채점하거나, 풀에 새로 넣은 모양이 성능에 주는 영향을 볼 때 쓴다.
- 지금 손글씨는 글꼴 4종이라 필체 다양성이 낮다(DOCGEN.md 알려진 한계). 글꼴과 서명 풀을 늘리는 것이 가장 쉬운 개선이다.

### 4.8 생성 예시

서식을 고치거나 추가하려면 **그 서식으로 실제 만들어지는 예시**를 여러 장 봐야 한다.

- **예시 묶음:** 서식마다 고정 seed 여러 개(기본 8개)로 만든 예시. 변형(내용 많음, 특수 상황)과 촬영 조건(원본, 스캔, 촬영, 팩스)을 켜고 끌 수 있다.
- **겹쳐 보기 층:** 값 박스, 항목명 박스, 체크·도장·서명, 손글씨 영역을 층별로 켜고 끈다. 박스를 누르면 그 항목의 키·값이 나오고, "이 영역 고치기"로 영역 편집기의 같은 영역으로 간다.
- **문제 표시:** 예시를 보다가 문제가 있는 곳에 표시와 메모를 남긴다(겹침, 잘림, 어색한 값). 표시는 서식의 할 일 목록이 된다.
- **수정 전후 비교:** 저장하기 전에 같은 seed로 수정 전·후 예시를 나란히 보여 준다. 바뀐 키·값 목록도 함께 보여 준다.
- 예시는 미리보기 저장소(`studio_cache/`, git 제외)에 두고, 서식 파일이 바뀌면 다시 만든다.

## 5. 키 규칙

### 5.1 지금 상태

| 서식 | 키를 정하는 곳 | 예 | 현황 |
|---|---|---|---|
| html 70종 | 생성 함수가 돌려주는 dict 경로 | `employee.name`, `company.corp_reg_no`, `rows.3.amount` | 모두 영어 |
| overlay 406종 | `docgen/realform.py`의 `KEY_RULES`가 자주 나오는 항목명(성명, 주소, 계좌번호 등 약 30가지)을 영어 키로 바꾸고, 나머지는 **항목명을 그대로 키로** 쓴다 | 영어: `customer.name`, `employer.address`, `company.corp_no` / 한글: `매수비율`, `기업부담금_목록.0.상품명`, `는기관` | 글자 칸 6,715개 중 4,766개(71%)가 한글 키 |

영어 키도 두 벌이다. 예를 들어 직장 회사명을 html 서식(재직증명서)은 `company.name`, overlay 규칙은 `employer.name`으로 쓰고, 법인등록번호를 html 서식은 `company.corp_reg_no`, overlay 규칙은 `company.corp_no`로 쓴다. 학습 데이터로 내보낼 때만 일부 동의어(`corp_no`→`corp_reg_no` 등)를 바꾼다.

### 5.2 목표

- **모든 키는 영어 표준 키다.** 형식은 지금 html 서식과 같다: snake_case, `역할.속성` (`applicant.name`, `loan.amount`), 반복 행은 `목록.번호.칸` (`products.0.name`).
- **표준 키 사전**(`docgen/keys.json`)을 하나 둔다.
  - 역할 목록: `customer`, `applicant`, `agent`, `employee`, `employer`, `company`, `loan`, `account` …
  - 속성 목록: `name`, `rrn`, `birth`, `address`, `phone`, `biz_no`, `corp_reg_no` …
  - 동의어와 한글 항목명 예시
  - html 서식에서 이미 쓰는 키를 모아 초안을 만들고, 두 벌인 이름은 하나로 정한다.
- overlay 영역에 키를 정할 때 UI가 사전에서 고르게 한다. 사전에 없는 서식 고유 항목은 영어 키를 새로 짓는다. 분석기가 이름을 제안하고 사람이 확정한다.
- 한글 키는 자동 추출 직후의 임시 상태로만 남는다. 검수 경고에 뜬다.

### 5.3 영향

- overlay 키를 바꾸면 기존 학습 데이터·평가 세트와 키가 달라진다. 바꾼 뒤에는 평가 세트 버전(`docgen/bench/build.py`의 `VERSION`)을 올리고, 이전 버전과 점수를 비교하지 않는다.
- 406종을 한 번에 바꾸지 않는다. 업무 시나리오에 쓰이는 서식, 실서류에 많은 서식부터 바꾼다.

| 데이터셋 | 등록부의 모든 데이터셋 목록(벤치마크 종류, 출처, 정답 종류, 버전, 고정 여부, 문항 수, 실서류 여부). 새로 만들기(OCR / 은행 업무 × 합성 / 이미지 묶음 / 결과 폴더), 기존 폴더 등록, 빌드 진행, 학습 설정 내보내기(9.9). 데이터셋 하나를 열면 맨 위에 설명서, 아래에 과제별 문항 보기(이미지, 질문, 정답 박스) (9절) | S8, S10 |
| 평가 | 데이터셋에 붙은 모델 답(`predictions/*.jsonl`)과 점수 목록, 답 파일 붙이기·채점, 문항마다 정답과 모델 답 나란히 보기(박스 겹쳐 보기, 틀린 것 먼저), 모델·버전 비교표, 합성·실서류 비교표, 사내 OCR 기준·검수 정답 기준 비교 (9.8) | S12 |
| 시나리오·묶음 | 시나리오 목록·편집, 묶음 목록, 묶음 상세(서류 전부, 고객 프로필, 문항), 대조·심사·구비 문항 보기, 직접 묶음 만들기 (9.5) | S8 |
| 설정 | 분석기 목록·연결 확인, 브라우저 경로, 실서류 경로 | 공통 |

## 7. 분석기 연결

### 7.1 두 방식만 지원한다

| 방식 | 무엇이든 붙는 조건 | 예 |
|---|---|---|
| `openai` | OpenAI 호환 `chat/completions` API | vLLM에 띄운 Qwen, 사내 LLM 게이트웨이, 상용 API |
| `cli` | 지시문 파일과 작업 폴더를 받아 실행되고 결과를 파일로 쓰는 명령 | Claude Code, Codex, VS Code 확장에 들어 있는 다른 에이전트 CLI, 사내 CLI |

특정 도구 이름을 코드에 넣지 않는다. CLI는 **명령 틀**로 등록한다. VS Code 확장으로 설치된 CLI는 확장 폴더 안의 실행 파일 위치를 찾는 규칙(`discover`)으로 등록하므로, 확장이 업데이트돼 경로가 바뀌어도 그대로 쓴다.

### 7.2 설정 (`studio/config.json`, 예시는 `config.example.json`)

```json
{
  "browser": "C:/Program Files/Google/Chrome/Application/chrome.exe",
  "ocr": {"callable": "internal_ocr_adapter:ocr_from_file", "base_url": "http://<사내 OCR 서버>:30107", "path": "/ocr", "revision": "<OCR 버전>"},
  "import_dir": "D:/studio_import",
  "real_data_dir": null,
  "private_forms_dir": null,
  "providers": {
    "qwen-server": {
      "kind": "openai", "base_url": "http://<서버>:8000/v1", "model": "qwen3.5-9b",
      "api_key_env": "INTERNAL_MODEL_API_KEY", "external": false
    },
    "claude": {
      "kind": "cli",
      "discover": "~/.vscode/extensions/anthropic.claude-code-*/resources/native-binary/claude*",
      "args": ["-p", "{task_text}", "--output-format", "stream-json"],
      "external": true
    },
    "codex": {
      "kind": "cli",
      "discover": "~/.vscode/extensions/openai.chatgpt-*/bin/*/codex*",
      "args": ["exec", "--json", "--sandbox", "workspace-write", "-C", "{job_dir}", "-i", "{image}", "{task_text}"],
      "external": true
    }
  }
}
```

- `args` 안의 `{job_dir}`, `{image}`, `{task_file}`, `{task_text}`는 실행할 때 채운다. 새 CLI는 이 틀만 적으면 붙는다.
- `discover` 대신 `cmd`에 실행 파일 경로를 직접 줘도 된다. `discover`에 맞는 것이 여러 개면 가장 최근 것을 쓴다.
- UI 설정 화면에 "연결 확인" 버튼을 둔다. `openai`는 모델 목록을 묻고, `cli`는 `--version`을 실행한다.
- **`external`은 도구 이름이 아니라 연결 대상으로 정한다.** 같은 Codex·Claude Code라도 내부망에서 사내 게이트웨이나 vLLM에 연결해 쓰면 `external: false`로 등록한다.

2026-10-20 이 PC 확인: VS Code 확장 안의 `claude.exe`(2.1.294)와 `codex.exe`(0.162)가 실행된다(버전만 확인, 실제 요청은 보내지 않음). 내부망에 어떤 CLI가 있는지는 아직 모른다.

### 7.3 맡기는 일과 작업 폴더

| 작업 | 입력 | 출력 | 맞는 방식 |
|---|---|---|---|
| `layout` 값 영역 제안 | 서식 이미지, 표준 키 사전, (있으면) 사내 OCR 결과 | `layout.json` (4.2 형식) | `openai` 또는 `cli` |
| `html` 템플릿 작성 | 서식 이미지, `docgen/manual/TEMPLATE_GUIDE.md`, 비슷한 기존 서식 1~2개(반복 표·여러 쪽 예 포함), 표준 키 사전, `form.json` 형식(4.3). 다시 고칠 때는 지금 템플릿과 사람 의견 | `template.html.j2` + `form.json` | `cli` (작성 → 렌더링 → 원본과 비교 → 수정을 스스로 반복. 렌더링은 작업 폴더 안에서 `python -m docgen.preview`로) |
| `autolabel` 실서류 오토 라벨 | 실서류 이미지, 서식 ID, 그 서식의 키 목록 | `labels` 형식 JSON | `openai` + 사내 OCR, `external: false`만 |

모든 분석기는 같은 폴더 구조로 일한다. 분석기를 바꿔도 UI는 바뀌지 않는다.

```
<workspace_dir>/analyzer/<작업ID>/
  job.json          작업 종류(html·layout), 분석기, 연결 대상(external), 대상 서식, 그림 출처, 보낸 파일 목록
  input/            원본 이미지(source.png 또는 page_<쪽>.png), 참고 파일 (가이드, 예시 템플릿, 매크로, 키 사전, 지난 결과)
  TASK.md           지시문 (studio/analyzer_tasks/<종류>.md 틀에서 생성)
  output/           분석기가 써야 하는 결과 파일 (html: template.html.j2 + form.json, layout: layout.json)
  check/            studio 가 결과를 렌더링해 본 것 (행 최소·최대)
  result.json       결과 검사 (형식, 렌더링, 경고)
  review.json       사람 의견과 승인
```
실행 로그는 ⑧ 작업의 일반 작업 로그(`<workspace_dir>/jobs/<작업>/log.txt`)에 남는다.

- `openai`: UI 서버가 이미지와 지시문을 보내고 받은 JSON을 `output/`에 쓴다.
- `cli`: 작업 폴더를 작업 디렉터리로 해서 실행한다. 쓰기는 작업 폴더 안으로만 한다(각 CLI의 샌드박스·허용 도구 설정을 `args`에 둔다).
- 결과가 나오면 UI가 형식 검사와 렌더링을 하고, 통과한 것만 검토 화면에 올린다. 승인하면 4.4의 자리로 복사해 등록한다. 등록한 서식은 검수 전 상태로 시작한다.
- "다시 고쳐" 의견은 `review.json`에 쌓이고 다음 실행의 `TASK.md`에 붙는다.

### 7.4 데이터 경계

- `external: true` 분석기는 실서류 작업(`autolabel`, 검수 화면, 실서류 데이터셋 추론)에서 고를 수 없다.
- 가져온 이미지 묶음(8절)은 기본으로 실서류로 보고 외부 분석기로 보낼 수 없다. 사용자가 묶음을 "공개 서식(빈 서식 모음)"으로 표시한 경우만 풀린다.
- 새 서식 화면에서 외부 분석기를 고르면 "공개 서식·빈 서식만 보낸다"는 확인을 받는다.
- 작업 폴더에 보낸 파일 목록이 남는다.

## 8. 가져오기

가져오기는 두 방식이다. 둘 다 **포맷·양식으로 묶어서** 보여 주는 것은 같다.

| 방식 | 사용자가 주는 것 | studio가 하는 일 | 목적 |
|---|---|---|---|
| **이미지 묶음** (8.1~8.5) | 문서 이미지 뭉치 | 사내 OCR로 읽기 → 묶기 | 포맷마다 템플릿으로 만들지 정한다. 그대로 **OCR 벤치마크**로도 만든다(9.2) |
| **결과 폴더** (8.6) | 이미 만든 OCR·추론 결과를 저장한 폴더 경로 ([RESULTS_FORMAT.md](RESULTS_FORMAT.md)) | 저장된 OCR로 묶기 (OCR 다시 안 함) | 추론 결과를 사람이 검수해 **실서류 정답**을 만들고 벤치마크 점수 계산에 쓴다. 템플릿으로도, OCR 벤치마크로도 보낼 수 있다 |

두 방식 모두 OCR 결과를 사람이 고칠 수 있다(OCR 검수, 8.7). 고친 OCR은 OCR 벤치마크의 검수 정답이 된다.

### 이미지 묶음

문서 이미지 뭉치(스캔, 사진, PDF)를 넣으면 studio가 **사내 OCR로 모두 읽고, 생김새가 같은 문서끼리 포맷·양식으로 묶는다.** 사용자는 포맷마다 견본을 보고 **템플릿으로 만들지 말지만 정한다.**

### 8.1 흐름

```
이미지 폴더 지정 또는 끌어다 놓기 (PDF 는 쪽마다 이미지로 바꿈)
   │
   ▼  OCR: ocr/internal_ocr_adapter.py 방식으로 사내 OCR 호출, 결과 캐시 (8.2)
   ▼  포맷·양식 묶기: masking_ui 지문 방식 (8.3)
   │
포맷 목록: 문서 수, 견본 썸네일, 양식 수, 가까운 기존 서식
   │  사람이 포맷·양식마다 정한다
   ├─▶ 템플릿으로: 견본 1장 고르기 → 배경 지우기(4.2) → 값 영역 지정 → 새 overlay(image) 서식
   │              필요하면 분석기에 값 영역 초안을 맡기거나, html 서식으로 만든다 (4.3, 7.3)
   ├─▶ 기존 서식과 같음: 그 서식의 실서류 예시로 연결 (실서류 라벨 작업 재료, S5)
   └─▶ 건너뛰기

묶음 전체 또는 고른 포맷 (위 결정과 따로)
   └─▶ OCR 벤치마크로: (필요하면 OCR 검수, 8.7) → 1부 scan·prepare → OCR 데이터셋 (9.2)
```

### 8.2 OCR — 1부 OCR 준비 단계(`ocr/bank_ocr`)를 그대로 쓴다

OCR을 읽고 부르는 일은 1부 OCR 학습의 준비 단계(`python -m bank_ocr scan` / `prepare`)에 이미 있다. studio는 `ocr/bank_ocr/data.py`를 **복사하지 않고 불러 쓴다**(표준 라이브러리와 PIL만 쓰므로 생성기 환경에서 import된다. 2026-10-20 확인). 두 곳의 OCR 처리가 늘 같게 된다.

| 일 | 1부 OCR 준비 단계 | studio |
|---|---|---|
| 페이지 이미지 찾기·문서 묶기 | `scan`: 이미지 폴더를 훑고, `document_regex`의 `(?P<document_id>…)`로 여러 쪽을 한 문서로 묶는다(또는 한 장 = 한 문서) | 같은 함수 |
| 저장된 OCR 찾기 | `--ocr-dir`: 이미지와 **같은 상대 경로 또는 같은 파일 이름 + `.json`** (`find_saved_ocr`) | 같은 함수 (결과 폴더 방식, 8.6) |
| OCR 부르기 | `ocr_callable`(기본 `internal_ocr_adapter:ocr_from_file`)이 원본 JSON을 돌려준다 | 같은 설정 키. 어댑터 파일이 쓰지 않는 `matplotlib`을 import하므로, import가 안 되는 환경이면 같은 요청(`{INTERNAL_OCR_BASE_URL}/ocr`, multipart `file`)을 직접 보낸다 |
| OCR JSON 해석 | `parse_ocr` + `mapping`(`items_path`, `success_key`, `text_key`, `confidence_key`, `box_key`, `box_format`, `points_key`). 사내 OCR 형식이 기본이고, 다른 OCR이면 `mapping`만 바꾼다 | 같은 함수·같은 `mapping` |
| 이미지 정규화 | `canonical_image`: EXIF 회전을 적용한 RGB. EXIF 회전이 있는 이미지는 저장된 OCR을 쓰지 않는다(좌표가 어긋남) | 같은 규칙 |
| 캐시 | 키 = 픽셀 해시 + `ocr_callable` + `ocr_revision` → `<cache_dir>/ocr/<키>.json` | 같은 키 규칙. **studio의 OCR 캐시 경로를 1부의 `cache_dir`(예: `ocr/data/ocr-cache`)로 두면 1부에서 이미 돌린 OCR을 다시 부르지 않는다** |

- 결과는 단어 목록 `{text, bbox(픽셀), bbox_norm(0~1000), confidence, order, line_num}`이다(`parse_ocr` 출력 그대로). 포맷 묶기(8.3)는 이 목록을 쓴다.
- 1부와 마찬가지로 이 OCR 결과는 사람이 검수하지 않은 의사정답이다. 사람이 고치면 검수 정답이 된다(8.7).
- **사내 OCR은 내부망에만 있다.** 이 PC에서 OCR 설정이 없으면 가져오기는 OCR 단계에서 멈추고 안내한다. 시험용으로 생성 데이터를 넣는 `from-docgen`을 둔다. 생성 데이터는 글자·박스 정답이 있어서 OCR 결과 대신 쓸 수 있고, 서식 ID를 알아서 묶기가 맞는지도 잴 수 있다.

### 8.3 포맷 묶기 — masking_ui 방식을 옮겨 온다

[masking_ui](https://github.com/kimsh12191/masking_ui)(`app/clustering.py`, 확인한 커밋 `6f5bca6`)가 이미 같은 일을 한다. **지문·묶기 함수만 `studio/formats.py`로 옮겨 오고 masking_ui와의 의존은 끊는다.** 두 도구는 합치지 않고 따로 간다.

| masking_ui에서 | studio에서 |
|---|---|
| `geometry.py`의 줄 만들기·글자 정규화 (표준 라이브러리만 씀) | 필요한 함수만 옮긴다 |
| `clustering.py`가 전역 저장소(`DOCS`, `FORMATS`, `LOCK`)를 읽고 씀 | 문서 목록과 기존 포맷을 **인자로 받고 결과를 돌려주는** 함수로 바꾼다. 저장은 studio가 한다 |
| 설정(`CONFIG`)의 기준값 | 함수 인자 + studio 설정의 `cluster` 항목 |
| `rules.boilerplate_vocab` (서식 고정 문구 사전) | 필요한 만큼만 옮기거나 단순화한다 |
| 마스킹 관련 부분(마스크 조각, 1차 마스킹 비교) | 가져오지 않는다 |

- 옮긴 파일 머리에 출처(masking_ui 커밋 `6f5bca6`, 원래 파일·함수 이름)를 적는다. 이후 masking_ui가 바뀌어도 자동으로 따라가지 않는다.
- masking_ui의 묶기 시험 도구(`tools/bench_cluster.py`)처럼, docgen 생성 데이터로 "같은 서식끼리 묶이는가"를 재는 시험을 함께 만든다. 생성 데이터는 서식 ID를 알기 때문에 정답이 있다.

방법은 그대로 가져온다.

| 단위 | 뜻 | 방법 |
|---|---|---|
| **포맷** | 생김새가 비슷한 문서 묶음. 제목이 달라도(같은 회사 양식의 재직·경력증명서) 글자 구성이 비슷하면 한 포맷 | OCR 줄 글자의 2글자 조각과 대략적인 세로 위치로 지문을 만들고, 포맷 중심과 코사인 유사도로 배정. 숫자 조각과 한 문서에만 나오는 조각(값)은 뺀다 |
| **양식** | 포맷 안에서 표 배치·값 위치까지 같은 문서 | 글자 조각 + 가로·세로 위치로 다시 나눈다 |
| 이어지는 쪽 | 제목 없이 표만 이어지는 쪽 | 표 머리줄이 같은 포맷에 붙인다 |

- 템플릿은 **양식 단위**로 만든다 (양식 하나 = overlay 서식 하나가 기본).
- **가까운 기존 서식 찾기:** 생성기 서식의 견본 이미지에도 같은 OCR·지문을 만들어 두고, 포맷 중심과 가장 비슷한 기존 서식을 보여 준다. 이미 있는 서식이면 새로 만들지 않는다.
- 사람이 포맷을 합치거나 나누면 자동 묶기가 다시 바꾸지 않는다 (masking_ui와 같은 규칙).

### 8.4 가져온 묶음 저장

```
<import_dir>/<묶음>/                사용자가 넣은 원본 이미지·PDF (studio는 읽기만). 올린 파일은 <workspace>/uploads/<묶음>/
<workspace>/imports/<묶음>/
  batch.json                         이름, 출처(folder·upload·docgen), 실서류·공개 서식 표시, OCR 설정, 단계
  pages.jsonl                        쪽마다 {id, doc, source, page, image(OCR이 본 그림), width, height, sha, ocr(원본 응답 경로), fp(지문)}
  formats.json                       포맷 {id, name, pages, docs(문서→쪽), variants(양식), decision, similar} + fixed(사람이 고정한 쪽)
  pages/ · thumbs/                   PDF 쪽 그림, 화면용 미리보기
<OCR 캐시>/images/<픽셀 해시>.png      OCR이 본 그림 (EXIF 회전 적용, 1부와 같은 규칙)
<OCR 캐시>/ocr/<키>.json              OCR 원본 응답 (1부와 같은 키 규칙, 8.2. 기본 studio_cache/ocr, 1부 cache_dir 와 같이 써도 됨)
```

- 구현(7단계): 여러 쪽 문서(PDF, 생성 데이터)는 첫 쪽만 지문으로 묶고 뒷쪽은 그 문서 첫 쪽의 포맷·양식을 따른다. 포맷 = 문서 종류이고, 템플릿은 견본 문서 하나의 쪽 전부로 만든다.
- 사람의 합치기·떼기·이름·결정은 `fixed`(쪽 → `keep:<포맷>` / `split:<표>`)로 남아 다시 묶어도 유지된다.

- 가져온 이미지는 **기본으로 실서류로 본다.** 외부 분석기로 보낼 수 없고(7.4), 여기서 만든 서식은 `private_forms_dir`에 저장한다. 사용자가 묶음을 "공개 서식(빈 서식 모음)"으로 표시하면 이 제한이 풀린다.

### 8.5 템플릿으로 보낼 때

- **견본 고르기:** 양식 안에서 가장 깨끗한(기울기·흐림이 적은) 문서를 기본 견본으로 제안하고, 사람이 바꿀 수 있다.
- **값 지우기:** 4.2의 배경 지우기 도구를 쓴다. 아래 지울 후보와 값 영역 초안은 7단계 마지막에 만든다. 없어도 손으로 지우고 그려서 서식을 만들 수 있다. **지울 후보**는 같은 양식 문서들의 OCR을 겹쳐 문서마다 달라지는 글자(= 값)로 잡는다.
- **값 영역 초안:** 같은 양식 문서들에서 늘 같은 글자는 항목명·고정 문구, 문서마다 다른 글자는 값이다. 값 글자 덩어리의 위치를 모아 값 영역 초안으로, 그 왼쪽·위의 항목명을 `label` 초안으로 쓴다. 키는 표준 키 사전에서 고른다(5절).
- **보관 위치:** 실서류에서 만든 서식은 `private_forms_dir`(4.4)에 두고 공개 저장소에 넣지 않는다. 공개 서식·빈 서식에서 만든 것만 저장소의 `docgen/forms/images/`에 둔다.

**구현 (7단계)** — `studio/importer.py` `create_template`, `value_drafts`

- 서식 폴더 `img_<ID>/`: `page_<n>.png`(견본 쪽 그림, OCR이 본 그림 그대로), `layout.json`(쪽 크기 pt = px ÷ `BG_ZOOM`, 빈 `items`, 배경 글자 `texts` = 견본 OCR 단어(pt) — 합성 OCR 정답의 서식 글자), `overrides.json`(사람 수정. `img_*` 서식은 수정도 서식 폴더에 둬서 실서류 서식의 수정이 저장소로 나가지 않는다).
- 값 자리 초안: 같은 포맷 다른 문서(같은 양식 먼저, 12개까지)의 같은 쪽을 견본에 **아핀 정렬**(양쪽에 한 번씩만 나오는 같은 글자들의 중심으로 최소제곱, 어긋난 짝 30% 빼고 다시)한 뒤, 견본 단어가 다른 문서 **60% 이상**에서 같은 자리(가로 4%·세로 2%)에 같은 글자로 나오면 서식 글자, 아니면 값. 견본 글자가 25% 미만(또는 가장 비슷한 문서의 60% 미만) 겹치는 문서는 다른 서식으로 보고 뺀다(한 포맷에 섞인 재직·경력증명서). 기호만인 단어는 경계로 보지 않는다.
- 값 단어를 줄로 모아 왼쪽부터, 사이에 서식 글자가 없고 간격이 글자 높이 2배 안이면 한 자리로 묶는다. 자리마다 `erase`(주변색) + `add`(글자 칸, 항목명 = 같은 줄 왼쪽 서식 글자(띄어 쓴 "소 재 지"는 붙임), 없으면 바로 위). 키는 항목명으로 자동 추정되고(`realform.kind_of`), 사람이 영역 편집기에서 고친다.
- 생성 데이터 3종으로 확인(2026-10-20): 퇴직연금 신청서·소득금액증명·재직증명서에서 성명·주민번호·주소·회사·금액·날짜가 값 자리로 잡히고, 몇 개의 서식 글자가 값으로 잘못 잡힌다(사람이 지운다).
- 주변색 지우기는 사각형 바깥 테두리 픽셀 중 밝기 95% 자리 색을 쓴다(테두리가 표 선에 걸쳐도 종이색).
- **검수 전 가져온 서식은 데이터셋에 들어가지 않는다:** 레시피의 `"all"`·그룹 선택(`docgen.bench build`, `docgen.ocr_set`)은 `imported` 그룹 서식 중 검수 완료한 것만 고른다. ID를 직접 적으면 시험용으로 들어간다.

### 8.6 결과 폴더 가져오기 — OCR·추론 결과가 이미 있을 때

내부 파이프라인이나 모델로 **이미 OCR과 추론을 돌려 저장해 둔 결과**를 쓰는 방식이다. 사용자는 폴더 경로만 준다. 폴더 모양은 [RESULTS_FORMAT.md](RESULTS_FORMAT.md)로 정한다.
- 이미지와 OCR은 **1부 OCR 준비 단계의 `scan --ocr-dir` 규칙 그대로**다(8.2). 1부에 쓰던 이미지·OCR 폴더를 옮기지 않고 경로만 적으면 된다.
- 추론 결과는 평가 세트 `kie`·`marks` 답과 같은 모양이다(9.3).

```
결과 폴더 경로 입력  (studio는 읽기만 한다)
   │
   ▼  형식 검사 → 저장된 OCR로 포맷·양식 묶기 (OCR 다시 안 함, 없는 문서만 OCR)
   │
포맷 목록 → 포맷 하나 열기
   │
   ▼  ① 키 대응 (포맷마다 한 번): 모델이 낸 키·항목명 → 표준 키 사전(5절). 포맷 안 모든 문서에 적용
   ▼  ② 문서별 검수: 추론 결과를 영역 편집기의 "라벨 모드"로 고친다
   │       값 고치기, 박스 고치기, 빠진 항목 추가, 틀린 항목 삭제, "확인" 누르기
   │       같은 포맷 문서를 이어서 보므로 같은 자리를 반복해서 보게 된다 (masking_ui 방식)
   ▼  ③ 검수 완료 문서 = 실서류 정답 (real_data_dir 에 저장)
   │
   ├─▶ 실서류 평가 세트로 (9.7): 벤치마크 점수 계산
   └─▶ 템플릿으로 (8.5): 이 포맷을 생성기 서식으로
```

**검수 화면 (라벨 모드)**

- 항목마다 상태를 남긴다: `자동`(추론 그대로) / `수정`(사람이 고침) / `확인`(그대로 맞다고 확인) / `추가` / `삭제`. 원래 추론 값은 지우지 않고 함께 보관한다.
- **같은 자리 모아 보기:** 한 문서에서 고친 항목과 같은 자리(같은 양식, 같은 키)를 다른 문서들에서 모아 한 화면에 보여 준다. 같은 실수를 한 번에 고친다.
- **의심 먼저 보기:** 같은 양식 문서들은 대부분 같은 키를 같은 자리에 낸다. 다른 문서에는 있는데 이 문서에 빠진 키, 박스가 유난히 다른 자리에 있는 항목, OCR 글자와 값이 안 맞는 항목을 먼저 띄운다.
- 문서 단위 상태: `미검수` / `검수 중` / `완료`. 포맷 화면에서 진행률을 본다.

**검수만으로 바로 나오는 숫자:** 원래 추론과 검수 결과를 비교하면 그 추론을 낸 모델(`meta.model`)의 실서류 점수가 바로 나온다(값·위치·값+위치, 9.3과 같은 채점). 사람이 얼마나 고쳤는지가 곧 그 모델의 오류다.

**데이터 경계:** 결과 폴더는 기본으로 실서류로 본다(`meta.real_data`). 외부 분석기로 보낼 수 없고, 검수 결과는 저장소가 아니라 `real_data_dir`에 쓴다.

### 8.7 OCR 검수 — 사내 OCR을 검수 정답으로

1부 OCR 벤치마크의 정답은 사내 OCR 결과 그대로라서, 점수는 "사내 OCR과 얼마나 같은지"다. 사내 OCR이 틀린 곳에서 모델이 맞혀도 감점된다. **사람이 OCR을 고치면 이 한계가 사라진다.** 이미지 묶음(8.1)과 결과 폴더(8.6) 어느 쪽에서든 쓴다.

**화면** (영역 편집기의 OCR 모드)

- 쪽 이미지 위에 OCR 단어 박스를 겹쳐 보여 준다. 낮은 신뢰도부터 색으로 구분한다.
- 박스를 누르면 글자를 고친다. 박스를 옮기거나 크기를 바꾸고, 빠진 글자 덩어리는 새 박스를 그려 더하고, 잘못 잡은 박스는 지운다. 잘못 쪼개진 박스는 합치고, 붙은 박스는 나눈다.
- **확인 순서:** 신뢰도 낮은 단어, 같은 양식 다른 문서와 글자가 다른 고정 문구(사내 OCR 오독일 가능성이 높다), 숫자가 섞인 값 순서로 먼저 띄운다.
- 항목마다 상태를 남긴다: `자동` / `수정` / `추가` / `삭제`. 쪽 전체에 `확인`을 누르면 그 쪽은 검수 정답이 된다.
- 단축키로 다음 의심 단어로 넘어간다. 1~2쪽만 고쳐도 되도록, 쪽 단위로 저장한다.

**저장**

```
<real_data_dir>/ocr_reviewed/<묶음 또는 결과 폴더 이름>/
  <쪽 id (/ → __, # → _)>.json  고친 OCR. 사내 OCR 응답 형식 그대로 ({"success": "Y", "data": {"basicData": [...]}})
  review.jsonl                  저장할 때마다 한 줄 {page, status: in_progress|done, by, at, stats} (마지막 줄이 그 쪽 상태)
```

- 구현(7단계, `studio/ocr_review.py`): `stats` = 사내 OCR 글자 오류율(읽는 순서로 이은 글, 검수본 기준), 박스 F1(IoU 0.5), 고친·더한·뺀 단어 수. 고친 단어와 확인(done)한 쪽의 모든 단어는 신뢰도 1로 저장한다.
- 1부 설정에 `reference_type`을 더했다(기본 `ocr_pseudo_unreviewed`, 기존 출력 그대로). 검수본 세트는 `human_reviewed`, 합성 세트는 `synthetic_exact`로 만들어 1부 `DONE.json`·문항·채점 보고(`interpretation`)에 정답 종류가 바로 적힌다. 검수본 세트는 신뢰도 필터를 0으로 둔다.

- **사내 OCR 형식 그대로 저장한다.** 그래서 1부 `scan --ocr-dir <ocr_reviewed 폴더>`가 고친 OCR을 바로 읽는다. 1부 코드를 바꿀 필요가 없다.
- 원래 OCR은 캐시에 그대로 있다. 원래 OCR과 고친 OCR의 차이가 곧 **사내 OCR의 오류**다. 쪽마다 사내 OCR의 CER·박스 F1을 바로 낸다.
- OCR 벤치마크를 만들 때 정답을 고른다: `의사정답`(사내 OCR) / `검수 정답`(확인한 쪽만). 검수 정답 세트는 확인한 쪽만 들어간다.
- 검수 정답이 있으면 같은 모델 답을 두 정답으로 채점해 나란히 보여 준다(9.8). 사내 OCR 기준 점수가 실제 정확도를 얼마나 낮게, 또는 높게 보는지 알 수 있다.

### 9.1 데이터셋 등록부

데이터셋을 만드는 코드는 지금처럼 `docgen.bench`(은행 업무), `ocr/bank_ocr`(OCR), `bank/bank_task`(2부 준비·채점)에 둔다. studio는 생성·준비 명령을 **백그라운드 프로세스로 실행**하고, 완료한 결과 폴더를 등록부에 자동으로 올린다. 같은 레시피를 명령줄(`python -m docgen.bench build --recipe …`, `python -m bank_ocr prepare --config …`)로도 돌릴 수 있다. 서버에서 큰 데이터셋을 명령줄로 만든 경우에는 폴더를 등록한다. 과제를 추가하거나 바꾸는 일(좌표 등)은 그 코드에서 한다. studio는 과제를 레시피에서 고르고 문항을 보여 준다.

**등록부** (`<workspace_dir>/registry.json`): 데이터셋마다 한 줄. 폴더는 옮기지 않고 경로만 적는다.

```json
{
  "ocr-synth-v1": {
    "track": "ocr", "source": "synthetic", "gt": "exact", "real_data": false,
    "path": "D:/studio_workspace/datasets/ocr-synth-v1", "format": "bank_ocr/prepared",
    "recipe": "docgen/recipes/ocr-synth-v1.json", "version": "1.3", "frozen": true,
    "created": "2026-10-28", "counts": {"documents": 400, "benchmark_tasks": 5120}
  },
  "ocr-real-2026-10": {
    "track": "ocr", "source": "results", "gt": "reviewed", "real_data": true,
    "path": "/share/data/prepared-v2", "format": "bank_ocr/prepared", "registered": true,
    "runs": ["/share/runs/exp1"]
  },
  "bank-synth-1.2": {
    "track": "bank", "source": "synthetic", "gt": "exact", "real_data": false,
    "path": "/share/bench", "format": "docgen.bench", "prepared": "/share/data/bank-prepared", "registered": true
  }
}
```

| 항목 | 뜻 |
|---|---|
| `track` | `ocr` / `bank` |
| `source` | `synthetic` / `images`(이미지 묶음) / `results`(결과 폴더) |
| `gt` | `exact`(생성 정답) / `pseudo`(사내 OCR·추론 그대로) / `reviewed`(사람 검수) |
| `format` | `bank_ocr/prepared`(1부 `prepare` 결과), `docgen.bench`(은행 업무 문항 원본), `bank_task/prepared`(2부 `prepare` 결과) |
| `registered` | studio가 만들지 않고 경로만 등록한 폴더. studio는 읽기만 한다 |
| `runs` | 이 데이터셋을 푼 모델 답·점수가 있는 폴더 (1부·2부 파이프라인의 `runs/<실험>/`). 9.8 |
| `frozen` | 고정. 그 뒤로 덮어쓰지 않는다 |

- **폴더 등록:** 경로를 주면 안의 파일로 형식을 알아낸다. `DONE.json`+`pages.jsonl`은 1부 `prepare` 결과, `benchmark_items.jsonl`은 2부 `prepare` 결과, `meta.json`에 `version`이 있으면 `docgen.bench` 결과다.
- **버전 정보:** studio가 만든 데이터셋은 폴더 안 `dataset.json`에 레시피, 생성기 커밋, 평가 세트 `VERSION`, 서식 파일 해시, 과제별 문항 수, 출처(이미지 묶음·결과 폴더 이름, 검수 상태)를 남긴다.
- **데이터셋 설명서:** 데이터셋마다 설명서 한 장을 둔다. 연구 결과를 보고하거나 다른 사람에게 데이터셋을 넘길 때 그대로 쓴다.
  - 자동으로 채우는 칸: 벤치마크 종류, 출처, 정답 종류, 만든 방법(레시피, 생성기 커밋, 평가 세트 `VERSION`, OCR 버전), 구성(과제별 문항 수, 서식·시나리오·촬영 조건·포맷 분포, 쪽 수), 검수 현황(검수자, 확인한 문서·쪽 비율), 이 데이터셋을 쓴 학습(9.9)과 점수 요약(9.8)
  - 사람이 쓰는 칸: 목적, 쓰면 안 되는 곳, 알려진 한계(예: "실서류 대조 문항은 불일치가 적다", "의사정답이라 사내 OCR 기준 점수다")
  - 저장: studio가 만든 데이터셋은 폴더 안 `DATASET.md`, 등록만 한 폴더는 `workspace_dir/cards/<ID>.md` (등록한 폴더에는 쓰지 않는다). 화면에서는 데이터셋을 열면 맨 위에 보인다
  - 고정한 데이터셋은 자동 칸을 다시 채우지 않는다. 점수 요약과 쓴 학습 목록만 늘어난다
- **실서류 데이터셋:** 등록부 줄에 `real_data: true`가 붙는다. 외부 분석기로 보낼 수 없고, 저장소에 넣지 않는다. 등록부 자체가 `workspace_dir`에 있어 git에 들어가지 않는다.

| studio가 하는 일 | 내용 |
|---|---|
| 레시피 | 합성 데이터셋: 벤치마크 종류, 과제, 서식(목록표의 배정·검수 상태로 거르기), 시나리오, 서식당·시나리오당 수, 촬영 조건 비율, 변형 비율, `test`/`train`을 JSON 하나로 (`docgen/recipes/<이름>.json`). 실서류 데이터셋: 출처 폴더, 포맷, 정답 종류(검수 완료만 / 의사정답 포함), 과제 |
| 빌드 | 레시피로 `docgen.bench build`·`bank_ocr prepare`·`bank_task prepare`를 백그라운드 작업으로 실행. 진행·오류 표시 |
| 문항 보기 | 과제별로 문항을 넘겨 보며 이미지·질문·정답(좌표면 박스로)을 함께 본다. 서식·조건·사례별 거르기 |
| 비교 | 두 버전의 문항 수·구성 차이 |

#### 9.1.1 ⑥ 새로 만들기 → 완료 후 자동 등록 (구현: 2026-10-20)

**⑥에서 만들기를 누르면 같은 화면에 머물고, 생성·등록이 끝난 데이터셋이 아래 목록에 자동으로 나타난다.** 로그 확인을 위해 작업 이름을 누를 때만 ⑧로 이동한다. Studio가 만든 결과를 사용자가 다시 폴더 경로로 등록하게 하지 않는다.

| 단계 | 화면과 저장 동작 |
|---|---|
| 생성 요청 | 레시피·결과 이름·프로세스 수를 검증하고 백그라운드 작업 시작. 요청 중 만들기 버튼 중복 누름 방지 |
| 생성 중 | ⑥ `데이터셋 생성 현황`에 상태·진행·작업 로그 링크 표시. 페이지가 열려 있고 진행/끊긴 작업이 있을 때 약 2초마다 확인 |
| 등록 중 | 생성 프로세스가 성공하면 등록 콜백 실행. 등록이 끝나기 전에는 작업을 완료로 표시하지 않음 |
| 등록 완료 | `registry.json`에 한 번 등록하고 작업 `result.dataset`에 ID 저장. 아래 목록만 갱신해 `새로 등록됨` 표시와 결과 링크 제공. 레시피·결과 이름·수동 폴더 등록 입력은 유지 |
| 생성·등록 실패 | 오류와 작업 링크 표시. 미완성 결과를 완료 데이터셋으로 올리지 않음. 생성 성공 뒤 등록만 실패했다면 다음 목록 조회 때 완료 결과를 확인해 등록 재시도 |

대상은 은행 업무 `build_bank`, 합성 OCR과 가져온 이미지의 OCR 세트 `build_ocr`다. 은행 업무는 결과 폴더 자체, OCR은 `prepared/`를 등록한다. 기존처럼 출처·정답 종류·실서류 여부·레시피·버전 정보를 유지하며, 수동 폴더 등록과 외부 명령줄 생성도 계속 지원한다.

**재시작 시 완료 처리 복구**

- 각 생성 작업의 `info.dataset`에 `{path, name, meta}` 등록 정보를 저장한다. 완료 콜백과 복구가 공통 `studio/build_registration.py`의 `register_output`을 사용해 같은 폴더를 중복 등록하지 않는다.
- 서버가 재시작되면 기존 실행 작업은 `interrupted`가 된다. `GET /api/datasets` 또는 `GET /api/builds`에서 해당 생성 작업의 완료 파일을 확인한다. 이전 작업은 `info.out`과 생성 당시 `dataset.json`/`ocr_set.json`의 스냅샷으로 복구한다. 현재 편집된 레시피를 생성 당시 설명으로 오인하지 않는다.
- 은행 업무는 정상 JSON인 `meta.json`·`dataset.json`의 문항 수가 같고 각 `tasks/*.jsonl`의 실제 줄 수가 맞아야 한다. OCR은 1부 prepare가 마지막으로 쓰는 `prepared/DONE.json`과 `pages.jsonl`이 있어야 한다.
- 자동 복구 범위는 작업 기록에 있는 `workspace_dir/datasets/` 아래 출력이다. 임의의 외부 폴더를 탐색해 등록하지 않는다. 생성이 계속 도는 작업, 생성 자체가 실패한 작업, 취소한 작업은 자동 완료 처리하지 않는다.
- 복구되면 작업의 `status:done`, `stage:registered`, `result.dataset`, `recovered:true`, `recovered_at`을 기록한다. 복구된 작업의 표시 종료 시각은 완료 파일을 확인해 복구한 시각이다. 이미 등록된 같은 경로의 이름·고정 상태를 덮어쓰지 않으며, 사용자가 나중에 등록을 지운 완료 작업도 자동 재등록하지 않는다.
- `job.json` 갱신은 임시 파일을 만든 뒤 교체해 조회 중 부분 JSON을 읽지 않게 한다. 화면 갱신은 `dataset-builds.js`가 담당하고, 해당 화면을 떠나면 갱신을 중단한다. 네트워크 오류 시 상태를 표시하고 화면 안에서 재시도한다.

검증 항목: 은행/OCR 등록 정보 보존, 완료 후 한 번 등록, 재시작 누락 복구, 미완성·취소·실패 제외, 중복·고정 상태 유지, 등록 콜백 완료 전 진행 상태 유지. 실제 화면에서는 만들기를 눌러 ⑥에 머무는지, 완료 후 목록이 자동 추가되고 다른 입력 값이 보존되는지 확인한다.

2026-10-20 확인: 관련 회귀 테스트 89개 통과. 사용자 등록부와 분리한 작업 공간에서 실제 은행 업무 데이터셋을 브라우저로 생성해 같은 화면 유지·자동 등록·입력 보존을 확인했다. 기존 `bank-bench-2026-10-20`의 완료 파일·문항 수를 확인하고 누락된 등록도 복구했다.

### 9.2 OCR 벤치마크 — 세 출처 모두 1부 형식으로 만든다

OCR 벤치마크는 **1부 `bank_ocr prepare`가 만드는 8과제를 그대로 쓴다**(`crop_ocr`, `bbox_ocr`, `grounding`, `region_ocr`, `spotting`, `relation`, `marked_ocr`, `marked_box`). 출처에 따라 다른 것은 **이미지와 OCR JSON(정답)을 어디서 가져오는지**뿐이다. 그 뒤는 1부 코드가 똑같이 처리한다.

```
이미지 + OCR JSON(사내 OCR 응답 형식)
   │  1부 scan: 이미지 목록 manifest (document_regex 또는 한 장 = 한 문서, --ocr-dir)
   ▼  1부 prepare: 크기 맞추기, 깨끗한 사본 + 노이즈 사본, 8과제 문항, 문서 단위 train/val/benchmark 나누기
OCR 데이터셋 (benchmark_tasks.jsonl, train_sft.jsonl …) → 등록부
```

| 출처 | 이미지 | OCR JSON (정답) | 정답 종류 |
|---|---|---|---|
| 합성 | `docgen generate`의 쪽 이미지 (촬영 조건 포함) | **생성 라벨에서 만든 사내 OCR 형식 JSON** (`docgen/ocr_export.py`) | `exact` |
| 이미지 묶음 (8.1) | 가져온 이미지 | 사내 OCR 캐시(8.2) 또는 검수본(8.7) | `pseudo` / `reviewed` |
| 결과 폴더 (8.6) | 결과 폴더의 이미지 | 저장된 OCR 또는 검수본 | `pseudo` / `reviewed` |

**합성 OCR 정답**

- 생성 라벨의 글자·박스를 **사내 OCR 응답 형식**(`success`, `data.basicData`, `bounding.vertices`)으로 바꿔 쪽 이미지와 같은 이름으로 쓴다. 지금 `guide/examples/labels_to_ocr.py`가 하는 일을 생성기 안(`docgen/ocr_export.py`)으로 옮기고, guide 예시도 이것을 부르게 한다.
- **쪽 전체 글자가 정답에 있어야 한다.** `spotting`·`relation`·`region_ocr`는 그 쪽(또는 영역)의 글자 전부가 정답이다. 생성기는 지금 값 칸과 항목명 칸의 박스만 기록하므로, 안내문·표 머리글 같은 서식 고정 문구를 모델이 맞게 읽어도 오답이 된다. 그래서 **렌더링할 때 모든 글자 덩어리의 박스를 함께 잰다**(`docgen/image.py`, html 서식은 브라우저 DOM에서, overlay(pdf) 서식은 PDF 글자 층에서, overlay(image) 서식은 견본의 OCR 결과에서 지운 곳을 뺀 것으로). 그전까지 합성 OCR 세트는 전체가 필요 없는 과제(`crop_ocr`, `bbox_ocr`, `grounding`, `marked_*`)만 쓴다.
- **글자 덩어리 단위를 사내 OCR에 맞춘다.** 사내 OCR이 한 항목을 단어로 내는지 줄로 내는지에 따라 `spotting` 정답의 박스 크기가 달라진다. 내부망의 실제 사내 OCR 결과를 보고 정한다(12절).
- 촬영 조건(스캔, 촬영, 팩스)을 넣은 이미지는 박스를 같은 변환으로 옮긴다(`docgen`의 증강 좌표 변환을 그대로 쓴다). 1부 `prepare`의 노이즈 사본은 그 위에 따로 더해진다.
- 합성 OCR 학습 데이터도 같은 길로 만든다. 레시피의 `split`만 `train`으로 둔다. 1부 `prepare`가 같은 픽셀이 train과 benchmark에 함께 들어가지 않는지 검사한다.

**1부 코드에 필요한 변경** (`ocr/bank_ocr/pipeline.py`): 지금 `prepare`는 train과 benchmark가 둘 다 있어야 돈다. 평가 전용 데이터셋을 만들 수 있도록 `benchmark_only` 설정을 더한다(기본은 꺼짐, 지금 동작 그대로).

**`docgen.bench`의 OCR 과제** (`ocr_field`, `ocr_page`): 지금 은행 업무 세트 안에 있다. 기존 세트와 점수를 이어 보기 위해 그대로 두되, 새 OCR 평가는 위의 1부 형식으로 한다. 9판까지 있던 `ocr_spot`(신규) 계획은 1부 `spotting`으로 대신한다.

### 9.3 은행 업무 벤치마크의 좌표 — OCR 단계 형식을 그대로 쓰고, 문서 이해 과제는 모두 좌표를 함께 답한다

1부 OCR 학습의 좌표 학습이 잘 됐으므로, 은행 업무 평가 세트(`docgen.bench`)도 **같은 좌표 형식**을 쓴다. 기준 코드는 `ocr/bank_ocr/tasks.py`(질문·답 형식), `data.py`(`normalize_box`), `metrics.py`(채점)다.

**좌표 형식 (OCR 단계와 같음)**

- 박스는 `bbox_2d: [x1, y1, x2, y2]`, **그 쪽 이미지 기준 0~1000 정수** (Qwen-VL 방식). 질문에 "좌표는 이미지 기준 0~1000입니다"를 넣는다.
- 픽셀 → 0~1000 변환은 `normalize_box`와 같은 규칙: 반올림으로 폭·높이가 0이 되면 내림·올림으로 넓히고, 1000을 넘지 않게 한다.
- 정답은 라벨 그대로 **픽셀로 저장**하고, 문항을 만들 때 0~1000으로 바꾼다. 다른 좌표 형식의 모델을 잴 때만 `run`에서 바꾼다.
- 여러 쪽 서류는 항목마다 `page`(1부터, 이미지 순서)를 함께 답한다. OCR 단계는 이미지 한 장 단위라 `page`가 없다. 이 차이만 더한다.

**과제별 답 형식**

| 영역 | 과제 | 답 | 좌표 |
|---|---|---|---|
| OCR | `ocr_field` 값 칸 잘라낸 이미지 → 글자 (기존 세트 호환, 9.2 끝) | 글자 | 없음 (잘라낸 칸이 곧 위치) |
| OCR | `ocr_page` 전체 받아쓰기 | 글자 | 없음 |
| 문서 이해 | `classify` 서류명 | 서류명 | 없음 |
| 문서 이해 | **`kie`** 항목 목록 → 값 | `[{"key": "loan.amount", "value": "56,000,000", "bbox_2d": [...], "page": 1}]`. 빈 칸은 `"value": null`, 박스 없음 | **있음 (바뀜)** |
| 문서 이해 | **`marks`** 체크·도장·서명 | 체크박스 `{"key", "value": "변동", "bbox_2d": 체크된 □}` · 복수 선택은 체크된 보기마다 한 줄 · 도장·서명 `{"key", "value": true/false, "bbox_2d": 찍힌 자리}` (`false`면 박스 없음) | **있음 (바뀜)** |
| 은행 업무 | `doc_check`, `cross_check`, `review` | 지금과 같음 | 없음 (9.5 끝) |

- **좌표 과제를 따로 두지 않고 `kie`·`marks`의 답 자체를 좌표 포함으로 바꾼다.** 같은 답에서 점수를 세 가지로 낸다.
  - 값 점수: 지금의 F1·정확도. 박스는 보지 않는다. 좌표를 못 내는 모델도 잴 수 있고, 이전 버전 점수와 뜻이 같다.
  - 위치 점수: IoU 0.5 기준 F1.
  - 값+위치 점수: 박스가 맞고(IoU ≥ 0.5) 값도 맞은 항목의 F1. 주 지표로 쓴다.
- **채점은 OCR 단계와 같다.** 예측과 정답을 IoU가 큰 순서로 하나씩 짝짓는다(`metrics.match`). GRPO 보상이 필요하면 OCR 단계처럼 박스 점수 `min(1, IoU/0.8)`을 쓴다.
- `ocr/`은 따로 설치하는 프로젝트이므로 `match`·`iou`·`normalize_box`를 `docgen/bench/metrics.py`로 옮겨 쓴다. 옮긴 함수에 출처를 적고, 두 쪽이 같은 결과를 내는지 시험을 둔다.
- **학습 레코드도 같은 형식으로 맞춘다.** 지금 `docgen/swift.py`의 `grounding`·`marks` 답은 `{"checkboxes": [...], "seals": [...], "signatures": [...]}`처럼 평가 문항과 모양이 다르다. 학습과 평가의 답 형식을 하나로 해야 평가 점수가 학습 효과를 그대로 보여 준다.
- `kie`·`marks` 답 형식이 바뀌므로 평가 세트 버전을 올린다. 이전 버전과는 값 점수만 비교한다.

#### 9.3.1 서식·시나리오의 question / answer 계약과 실제 예시 (구현: 2026-10-20)

화면의 **question은 실제 문항 레코드의 `prompt`**다. `answer`는 데이터 정답, `eval`은 채점에 필요한 타입·허용 오차·서류명 등이다.
각 과제의 계약은 `docgen/bench/contracts.py`에서 표시하고, 질문 원본은 `docgen/bench/prompts.py`의 상수를 직접 참조한다.
계약 표시와 예시 조회는 읽기 전용이며, 질문·답 형식이나 기존 문항을 수정하지 않는다.

| 과제 | question에 들어가는 내용 | 저장되는 answer | 모델 출력 / eval |
|---|---|---|---|
| `classify` | 서류의 정식 명칭 요청 | 서류명 문자열 | 서류명 한 줄 |
| `ocr_field` | 잘라낸 값 칸의 글자 요청 | 문자열 | 문자열 그대로. 입력은 해당 칸의 crop 이미지 |
| `ocr_page` | 이미지의 전체 글자 요청 | 채점할 값 문자열 목록 | 모델은 줄바꿈한 텍스트. `answer` 배열을 그대로 JSON으로 출력하는 과제가 아님 |
| `kie` | 키·항목명 목록과 값/위치 출력 규칙 | `[{"key":"name", "value":"홍길동", "bbox_2d":[100,200,300,230], "page":1}]` | 같은 JSON 목록. `eval.fields`에 타입·정규화 값. 빈 항목은 `value:null`, 위치 생략 |
| `marks` | 체크 보기·도장·서명 항목과 출력 규칙 | 체크된 보기마다 문자열, 도장·서명은 boolean인 JSON 목록 | 위치 포함. 미체크는 null, 없는 도장·서명은 false. `eval.types`에 항목 타입 |
| `doc_check` | 고객·업무명·필수 서류명 목록, 빠짐/불필요/타인 서류 분류 요청 | `{"missing":[], "not_required":[], "not_customer":[]}` | 같은 JSON 객체. `eval.required`·`names`는 서류명 대응용 |
| `cross_check` | 고객·업무명·서류 수·이미지 수, 불일치 판단 기준 | `{"consistent":true, "issues":[]}` 또는 문제 서류·항목·실제값·기대값 목록 | 같은 JSON 객체. `alt_documents`는 짝 서류도 인정하는 채점 보조 정보이며 필수 모델 답이 아님 |
| `review` | 업무명·이미지 수 + 각 규칙의 실제 질문(단위·계산식·반올림·예/아니오 지시 포함) | 숫자 또는 `"예"`/`"아니오"` | `eval.answer_type`(`number`/`yesno`)과 `eval.tol`을 사용 |

`kie`·`marks`의 `bbox_2d`는 그 쪽 이미지 기준 0~1000 정수, `page`는 1부터다. 공통 JSON Schema와 형식 예시는 실제 고객 정답과 구분해 표시한다.

**① 서식 → 문항 Q/A**

- 과제 선택으로 공통 question 템플릿, answer JSON Schema와 설명을 확인한다. 브라우저 렌더링이 없어도 공통 계약은 볼 수 있다.
- seed·변형·촬영 조건, 값 칸 OCR 문항 수, 최대 추출/표시 항목 수를 정해 `실제 문항 예시 만들기`를 누른다.
- 미리보기에서 생성한 이미지·필드·원본 HTML의 visible 키를 `Builder.single`에 넘긴다. 질문·항목 선택·좌표·값 칸 자르기·정답·채점을 따로 구현하지 않는다.
- 각 문항에 입력 이미지, 질문 전문 `prompt`, 데이터 정답 `answer`, `oracle_output`이 만드는 모델 출력 예시, `eval`, 문항 레코드 JSON을 보여 준다. 해당 고객에서 문항이 안 나오면 그 상태를 표시한다. 조건을 바꾸면 이전 예시는 무효화한다.
- `POST /api/forms/{id}/questions`, `GET /api/question-formats`. 미리보기 및 OCR crop은 `studio_cache/preview/` 아래에만 저장한다. 실제 데이터셋에는 추가하지 않는다.

**③ 시나리오 → 예시 고객으로 실행 → 각 작업의 Q/A 포맷·예시**

- 추출의 간단한 결과 문자열과 **실제 KIE answer 목록**을 구분한다. 비교·심사도 `P_REVIEW`로 감싼 전체 질문, 실제 답, 숫자/예·아니오 채점 조건을 보여 준다.
- 구비 검사는 빠짐 없는 원본 예시, 대조 사례는 원본 정상판의 Q/A다. 사례에 부가 심사 질의가 있으면 해당 `review` 예시도 함께 표시한다. 변조 후보의 값과 원본 이미지를 섞어 실제 변조 문항인 것처럼 보여 주지 않는다.
- 꺼진 작업이나 적용 불가 작업도 공통 형식은 열 수 있고, 현재 고객의 실제 예시가 없다는 점을 표시한다. 최종 변조·빠짐·타인 서류 문항은 생성 후 ⑥의 문항 보기에서 확인한다.
- 서식·시나리오 공통 화면은 `studio/static/js/questions.js`, 서식 문항은 `studio/questions.py`, 시나리오 원본 Q/A는 `studio/scenario_processing.py`에서 구성한다.

검증: 서식 Q/A와 `Builder.single`의 prompt·answer·eval·항목 선택이 일치하고, crop 파일과 모든 예시의 기존 채점기 정답 점수가 정상인지 확인한다. OCR의 데이터 정답/모델 출력 차이와 시나리오의 KIE 배열·심사 전체 프롬프트도 검사한다. 관련 자동 테스트는 2026-10-20 기준 58개 통과.

### 9.4 은행 업무: 묶음 단위로 관리한다

은행 업무 과제는 서류 하나가 아니라 **업무 묶음**(한 고객이 한 업무로 낸 서류 전부)에서 나온다.

```
시나리오 (예: 전세자금대출 = 신분증 + 등본 + 임대차계약서 + 등기부 + …)
  └ 묶음 (고객 1명, seed 1개) — 서류마다 서식으로 렌더링, 같은 고객 프로필
       ├ doc_check    : 필수 서류 일부 빼기, 타인 서류·불필요 서류 끼우기
       ├ cross_check  : 사례(14종) 적용 → 변조판(값 하나 바꿔 다시 렌더링) / 정상판
       ├ review       : 선택한 규칙(LTV, 만 나이, 유효기간 …) 또는 직접 지정한 필드 비교
       └ kie          : 직접 지정한 문서·항목의 값과 근거 위치 추출
```

| 관리 대상 | 지금 | studio에서 |
|---|---|---|
| 시나리오 구성 | `docgen/scenarios.json` → `SCENARIOS`·`SCENARIO_EXTRA` | ③에서 필수 서류·프로필 값을 편집하고 같은 고객의 서류 이미지, 확대·쪽 넘김, 다른 고객을 확인한다. 기존 시나리오 순서는 유지한다 |
| 시나리오 처리 설정 | 같은 파일의 시나리오별 `processing` → `SCENARIO_PROCESSING` | ③에서 구비 검사·대조·심사를 켜고 끄고, 사례·심사 규칙과 직접 만든 추출·필드 비교를 저장한다. 미지정 시 기존 동작 유지 |
| 불일치 사례 14종 | `docgen/bench/cases.py` (Python 함수) | 알고리즘은 코드에 둔다. ③에서 시나리오별 적용 여부·원본 근거·변조 후보를 확인하고, 레시피에서 사례별 변조 비율을 정한다 |
| 심사·계산 규칙 12종 | `docgen/bench/rules.py`의 `RULES` 11종 + 별도 `doc_valid` | ③에서 선택하고 예시 고객의 원본으로 질문·계산값·근거를 확인한다. 실제 빌드의 유효기간 문항은 기존대로 발급일을 옮긴 사본도 생성한다 |
| 묶음 기록 | `bundles.jsonl` | 묶음 ID·시나리오·고객 seed·서류별 이미지/라벨·변조 내역·문항 ID와 **적용한 처리 설정, 직접 작업의 결과 및 건너뛴 이유**를 남긴다 |

### 9.5 묶음 관리

묶음은 서식처럼 **하나의 관리 대상**이다. 서식이 서류 한 장을 만드는 틀이라면, 시나리오는 묶음을 만드는 틀이다.

**묶음 구성 확률은 레시피, 무엇을 처리할지는 시나리오에 저장한다.** `build.py`의 기본값에 레시피를 덮어쓰며, ③의 처리 설정은 그 시나리오를 쓰는 다음 빌드부터 적용한다.

| 규칙 | 지금 값 (`docgen/bench/build.py`) | 레시피 항목 |
|---|---|---|
| 빠진 서류 수 | 0 / 1 / 2건 = 30 / 50 / 20% | `bundle.missing` |
| 타인 서류로 바꾸기 | 30% | `bundle.other_customer` |
| 불필요 서류 끼우기 | 35% | `bundle.extra_doc` |
| 대조 사례 변조 | 사례마다 50% (`format`은 항상 정상) | `cases.<사례>.tamper` |
| 촬영 조건 | 원본 50, 스캔 20, 촬영 15, 팩스 15% | `conditions` |
| 시나리오당 묶음 수 | `--bundles` (기본 4) | `bundles: {"default": 4, "<시나리오ID>": 5}` |

**화면**

| 화면 | 내용 |
|---|---|
| 시나리오 목록 | 시나리오마다 필수 서류, 쓰는 서식의 검수 상태, 적용 가능한 사례·규칙, 만든 묶음 수 |
| 시나리오 편집 | 필수 서류 넣기·빼기, 함께 내는 서류, 새 시나리오. 프로필에 넣는 값(예: 대출 종류) |
| 시나리오 이미지 보기 | 펼친 시나리오만 같은 고객 seed와 시나리오 프로필 값으로 생성. 문서별 첫 쪽과 총 쪽 수, 누르면 확대·모든 쪽·이전/다음 서류. 고객을 바꾸면 구성 전체를 다시 생성 |
| 이 묶음에서 할 일 | 구비 검사·대조 사례·기본 심사 켜기/끄기, 사례 14종·심사/계산 12종 선택, 문서와 필드를 고르는 추출·비교 편집기 |
| 예시 고객으로 실행 | 편집 중인 설정을 저장하지 않고 원본 라벨로 실행. 추출값·비교 결과·심사 질문/계산값, 대조 사례의 적용 가능 여부와 변조 후보, 적용 불가 사유. 근거를 누르면 문서의 해당 쪽·위치 강조 |
| 묶음 목록 | 데이터셋 버전 안의 묶음. 시나리오·고객·서류 수·쪽 수·촬영 조건·문항 수·문제 표시로 거르기 |
| 묶음 상세 | 서류를 모두 펼쳐 보기. **고객 프로필 보기**(성명, 주민번호, 주소, 직장, 소득, 부동산 등 서류끼리 맞아야 하는 값과 그 값이 각 서류의 어디에 있는지). 이 묶음에서 나온 문항 |
| 대조 문항 보기 | 변조판과 원본을 나란히, 바뀐 칸을 두 서류에서 모두 강조. 정상 문항은 "표기만 다름" 칸 표시 |
| 심사 문항 보기 | 정답 계산식과 쓰인 값의 위치 |
| 구비 문항 보기 | 필수 서류 목록 대비 낸 서류·빠진 서류·타인 서류·불필요 서류 |

**하는 일**

- **문제 표시:** 묶음이나 문항에 문제(서류끼리 값이 안 맞는데 정상 문항, 변조가 화면에 안 보임 등)를 표시하고 메모를 남긴다. 표시한 문항은 다음 버전에서 빼거나 고친다.
- **다시 만들기:** 묶음 하나를 같은 seed로 다시 만들어(서식을 고친 뒤) 전후를 비교한다. 고정한 버전은 바뀌지 않는다.
- **직접 묶음 만들기:** 시나리오와 고객 seed를 고르고, 뺄 서류·바꿀 서류·적용할 사례를 직접 지정해 특정 상황의 문항을 만든다. 손으로 만든 묶음은 레시피에 목록으로 남아 다시 만들 수 있다.
- **고객 일관성 검사:** 묶음 안 서류들에서 같아야 하는 값(성명, 주민번호, 주소, 금액)이 실제로 같은지 자동으로 보고, 다르면 경고한다. 변조판은 바꾼 칸만 달라야 한다.
- 여러 쪽 문서 연구(`mpx`, master 브랜치)도 같은 업무 묶음을 쓰므로 `bundles.jsonl` 형식을 함께 쓰게 한다.

#### 9.5.1 ③ 처리 설정과 실제 문항 생성 (구현: 2026-10-20)

사용 흐름은 **서류 구성 → 이미지 확인 → 할 일 설정 → 예시 고객으로 실행 → 근거 확인 → 저장 → ⑥에서 데이터셋 생성**이다.
③의 실행은 생성된 정답 라벨을 사용하는 설계 확인이다. OCR·모델 추론을 호출하지 않으며, 완성된 데이터셋의 모델 답·채점은 기존 ⑥·⑦에서 한다.

`docgen/scenarios.json`의 각 시나리오에 선택적으로 다음을 저장한다.

```json
"processing": {
  "doc_check": true,
  "cross_check": true,
  "review": true,
  "case_ids": ["typo", "other_person"],
  "rule_ids": ["age", "doc_valid"],
  "operations": [
    {"id": "customer_name", "kind": "extract", "name": "고객 성명 추출",
     "left": {"doc": "resident_id_card", "key": "name"}},
    {"id": "same_employee", "kind": "compare", "name": "신분증·재직증명서 성명 비교",
     "left": {"doc": "resident_id_card", "key": "name"}, "operator": "equal",
     "right": {"doc": "employment_certificate", "key": "employee.name"}}
  ]
}
```

- `processing`이 없으면 구비·대조·심사를 모두 켠 기존 방식이다. `case_ids`·`rule_ids`의 `null`은 전체 후보, `[]`는 선택 없음이다. 새 추출·비교 작업은 기본으로 추가하지 않는다.
- 대조 사례는 **시나리오 선택과 레시피 선택을 모두 통과**해야 만든다. 변조 비율·빠짐·타인·불필요 서류 비율·촬영 조건·고객 수는 기존 레시피가 정한다. 직접 묶음의 `cases`도 이 조건 안에서 추가로 제한한다.
- `review`는 기본 규칙과 대조 사례의 부가 예/아니오 심사 질의를 제어한다. `rule_ids`는 기본 규칙만 선택하며, 대조 사례 질의는 그 사례 선택에 따른다. 직접 추가한 추출·비교 작업은 각 작업의 `enabled`로 따로 제어한다.
- 추출은 한 문서의 텍스트·숫자·날짜 필드와 근거를 지정한다. 비교는 두 필드와 `equal`·`not_equal`·`lte`·`gte`·`lt`·`gt`를 지정한다. 숫자는 정규화 수치, 날짜는 ISO 날짜로 비교하고, 나머지는 공백을 제외한 전체 문자열을 비교한다. 가려진 값은 추측하지 않고 적용 불가로 표시한다. 대소 비교에 텍스트를 넣거나 값·근거 위치가 없으면 문항을 건너뛰고 이유를 남긴다.
- 추출은 기존 `kie`의 값+위치 형식, 필드 비교는 기존 `review`의 예/아니오 형식으로 생성한다. 기존 채점기·학습 형식을 사용한다. 작업 ID는 같은 시나리오 안에서 고정하며 문항 ID의 `operation_<ID>`에 들어간다.
- `docgen/bench/processing.py`가 저장 검증과 추출·비교 계산의 공통 구현이다. `studio/scenario_processing.py`가 렌더링 캐시를 이용해 대조 후보·심사 결과와 출처를 모으고, `POST /api/scenarios/run`으로 화면에 돌려준다. 처리 화면은 `scenario-processing.js`, 이미지·근거 확대는 `scenario-preview.js`에 둔다.
- 화면의 구비 검사는 빠짐 없는 원본 구성, 대조 사례는 **문항 생성 후보**를 보여 준다. 실제 변조 이미지와 최종 문항은 빌드에서 확인한다. 적용 가능 후보라도 재렌더링에 실패하면 빌드가 그 문항을 만들지 않을 수 있다. 원본에서 계산한 유효기간 결과도 빌드의 발급일 변경 사본 결과와 다를 수 있다.
- 문서 구성·프로필·고객 seed·처리 설정이 바뀌면 이전 실행 결과를 지워 오래된 결과로 오인하지 않게 한다. 새 설정은 다음 빌드에 반영하며, 이미 생성한 데이터셋의 이미지·문항·점수는 바꾸지 않는다. `bundles.jsonl`에는 `processing` 설정과 `processing_results`(작업별 결과·출처·건너뛴 사유)를 남긴다.

검증: 같은 고객·시나리오 설정을 서류 전체에 적용, 추출 좌표와 기존 채점기 만점, 수치·날짜·문자열 비교, 가림·값/근거 없음 처리, 저장/재로딩, 실제 `Builder.bundle`의 선택 적용 및 문항/묶음 기록을 자동 검사한다. 화면에서는 설정·실행·근거 확대·쪽 이동·설정 변경 시 결과 무효화를 확인한다.

2026-10-20 확인: 관련 자동 테스트 55개 통과. 실제 계좌개설 서류 7종으로 성명 추출·문서 간 성명 비교·만 나이 문항 3개를 생성하고, 기존 채점기에 정답을 입력했을 때 모두 만점인 것을 확인했다.

**은행 업무 과제의 좌표:** 대조 문항에서 불일치 근거의 위치(`bbox_2d`, `page`, 어느 서류)를 답하게 하는 것은 9.3과 같은 형식으로 나중에 붙일 수 있다. `bundles.jsonl`에 바뀐 칸의 위치가 남기 때문이다. 이번 범위에서는 선택으로 둔다.

### 9.6 수정이 데이터셋에 반영되는 방식

**studio에서 고친 것은 파일로 저장되고, 생성기가 그 파일을 읽으므로 다음 빌드부터 반영된다.** 평가 세트와 학습 데이터는 같은 생성기로 만들기 때문에 둘 다에 반영된다.

| 사용자가 고친 것 | 저장되는 파일 | 반영되는 곳 |
|---|---|---|
| overlay 영역(위치·키·타입·값 출처), 배경 지우기 | `docgen/forms/overrides/<ID>.json` | 그 서식이 나오는 모든 과제(OCR, 문서 이해, 은행 업무 묶음)의 이미지와 정답 |
| html 서식 (복제·분석기) | `docgen/templates/copies/<ID>/` | 위와 같음 (새 서식으로 추가) |
| 템플릿으로 보낸 새 서식 | `docgen/forms/images/<ID>/` 또는 `private_forms_dir` | 위와 같음. 실서류에서 만든 서식은 내부망 빌드에서만 |
| 표시 설정·표시 요소 풀 | `docgen/marks.json`, `docgen/assets/marks/` | 체크·도장·서명·손글씨가 들어가는 모든 이미지 |
| 표준 키 사전·키 대응 | `docgen/keys.json` | 정답 키, 질문에 넣는 항목 목록 |
| 검수 상태·학습/평가 배정 | `docgen/catalog.json` | 레시피의 서식 거르기(검수 완료만, 평가 전용 서식은 학습에서 뺌) |
| 시나리오 구성·처리 설정 | `docgen/scenarios.json` (`docs`, `extra`, `processing`) | 다음 빌드의 은행 업무 묶음과 선택한 구비·대조·심사, 직접 지정한 추출·비교 문항 |
| 레시피 | `docgen/recipes/<이름>.json` | 그 레시피로 만드는 데이터셋 |
| 실서류 검수 결과 | `real_data_dir` | **합성 생성에는 들어가지 않는다.** 실서류 평가 세트(9.7)로 쓴다 |

지켜야 할 것:

- **이미 고정한 데이터셋 버전은 바뀌지 않는다.** 서식을 고친 뒤 새로 빌드하면 새 버전이 되고, 버전 정보(`dataset.json`)에 서식 파일 해시가 남아 무엇이 달라졌는지 비교할 수 있다.
- 생성 결과가 바뀌는 수정은 평가 세트 `VERSION`을 올린다(10절). 이전 버전과 점수를 그대로 비교하지 않는다.
- 학습 데이터도 같은 생성기로 만들므로, 서식을 고치면 그 뒤에 만든 학습 데이터에도 들어간다. 학습을 다시 할지는 사용자가 정한다(기존 학습 데이터는 그대로 남는다).
- 서식 상세에 "이 서식이 들어간 데이터셋 버전"과 "마지막 빌드 이후 바뀌었는지"를 보여 준다.
- 레시피는 검수 완료 서식만 쓰도록 거를 수 있다(평가 세트 기본값).
- html 기본 서식(`origin: builtin`)의 생성 함수·템플릿을 직접 고치는 것은 코드 수정이라 studio가 하지 않는다. 고친 코드도 생성기가 읽으므로 반영은 같다.

### 9.7 실서류 평가 세트

**현재 구현과 목표 구분 (2026-10-20):** 이미지·PDF OCR 가져오기·검수에 더해 **생성기 공통 v1 라벨 폴더 검사 → 정답 미리보기·확인 → 은행 업무/OCR 문항 생성 → ⑥ 자동 등록**을 구현했다(9.7.2). 실제 라벨과 `bundles.jsonl`로 구비·직접 추출/비교·계산 문항을 만들 수 있다. 임의 모델 결과 폴더 매핑·항목 라벨 편집기·화면에서 실제 문서를 직접 묶는 UI는 아직 미구현이다. 아래 목표 중 그 부분과 자동 묶음 후보 제안은 추후 범위다. ③ 자체의 예시 실행은 합성 고객 기준이며 실제 라벨은 ④에서 반입한다. 사용 순서는 [DATA_IMPORT.md](DATA_IMPORT.md)에 명시한다.

#### 사용자 데이터 준비와 진입 흐름

- **OCR:** 문서별 이미지 또는 PDF를 준비한다. 현재 이미지 한 파일은 문서 하나, PDF 한 파일은 여러 쪽 문서 하나다. 이미지 하위 폴더를 자동으로 여러 쪽 문서로 묶지는 않는다. 현재 UI는 ④ 가져오기 → ⑤ OCR 검수·확인 → ④ OCR 벤치마크로 → ⑥ 자동 등록이다.
- **추출:** 정답은 [LABEL_FORMAT.md](LABEL_FORMAT.md)의 생성기 공통 v1으로 받는다. `labels/<id>.json`에 `id`, `doc_type`, `doc_name`, `images`, `pages`, `fields`를 고정하고 서식 키도 생성기의 것을 따른다. 원본은 `page` 0부터·`bbox` 이미지 픽셀이다. 문항 생성 시에만 모델 답의 `page` 1부터·`bbox_2d` 0~1000으로 변환한다. 기존 OCR·모델 추론 결과의 임의 매핑은 [RESULTS_FORMAT.md](RESULTS_FORMAT.md)의 보조 경로다. 모델 결과는 검수 전 정답 후보로 표시한다.
- **새 합성 시나리오:** ④ 템플릿 만들기 → ① 영역·키·값 출처·배경 지우기·검수 → ③ 필수 서식·처리 설정·예시 실행·저장 → ⑥ 레시피 생성. 이 경로는 실제 고객의 원본 서류를 그대로 평가 세트로 등록하는 것과 구분한다.
- **실제 업무 묶음:** 이름이 아닌 접수 건별 `bundle_id`와 문서 ID 목록을 준비하고 시나리오에 연결한다. `bundles.jsonl`이 있으면 읽고, 없으면 문서를 직접 배정할 수 있어야 한다. 포맷 묶기와 업무 묶기는 화면 설명과 동작에서 구분한다.
- **문항·정답:** 기존 과제는 검수한 라벨·문서 구성·규칙에서 생성한다. 특수 업무는 질문, 답 자료형·예시, 입력 키·단위·기준일, 판정/계산식, 근거 위치를 정의해야 한다. 현재 Q/A는 계약·생성 예시 조회이며 자유 질문 템플릿 편집은 미구현이다.
- **목표 UI:** ④에서 OCR/라벨 있는 데이터/업무 묶음 목적과 입력 방식 선택 → 표준 형식·문서·쪽·키 검사 → ⑤ 목적별 검수 → 실서류 묶음에서 문서 배정·시나리오 선택·처리 실행 → Q/A·근거 확인 → ⑥ 생성·자동 등록. 표준 라벨에 임의 키 매핑을 요구하지 않는다. 현재 지원하지 않는 단계를 완료된 것처럼 안내하지 않는다.

#### 9.7.1 생성 라벨과 외부 정답의 공통 입력 규격 v1 (확정: 2026-10-20)

- `docgen generate --png`의 원본 문서 라벨 구조를 표준으로 고정한다. 필수 항목과 17종 필드 타입은 [document.schema.json](static/label-format/v1/document.schema.json), OCR은 [ocr.schema.json](static/label-format/v1/ocr.schema.json), 반입 메타는 [meta.schema.json](static/label-format/v1/meta.schema.json), 문서 연결 목록은 [bundle.schema.json](static/label-format/v1/bundle.schema.json)으로 제공한다. 향후 v1의 의미를 바꾸는 변경은 새 버전으로 낸다.
- ④에는 규격·예제 다운로드와 표준 라벨 폴더 검사·미리보기·확인·문항 생성을 제공한다(9.7.2). 합성 이미지와 원본 생성 필드로 만든 예제 ZIP을 포함한다. 원본 라벨 편집 UI는 아직 없다.
- 원본 `value`는 문서 표시 문자열 또는 `null`, `norm`은 생성기의 정규화 값이다. 체크박스는 `options[].checked`, 도장·서명은 `present`를 사용한다. 모델 답의 boolean `value`를 원본 라벨에 혼용하지 않는다. 미라벨링은 항목 생략, `null`은 실제 빈 칸 정답으로 구분한다.
- 별도 질문/정답 파일을 사용자에게 문서마다 요구하지 않는다. 기존 생성기와 같은 과제 계약·질문·좌표 변환으로 문항을 만든다. 항목 라벨만으로 고정 인쇄 글자를 포함한 쪽 전체 OCR 정답을 만들지는 않는다.
- Schema 및 이미지 실재·실제 크기·쪽 수·좌표 범위·문서 ID 중복·묶음 참조·서식별 키를 검사한다. 정답 출처와 검수 상태를 확인하고, 이미 가진 정답을 OCR·모델 예측으로 덮어쓰지 않는다.

#### 9.7.2 라벨 폴더 경로 → 검사·확인 → 생성·자동 등록 (구현: 2026-10-20)

- **UI:** ④ `라벨 있는 데이터`에 폴더 경로 입력 → `폴더 검사` → 오류/확인 사항과 문서·쪽별 이미지/정답 박스 확인 → 이름·은행 업무/OCR·평가/학습·과제 선택 → 확인란 체크 → `데이터셋 만들고 등록`. ⑥으로 이동해 기존 생성 현황과 자동 등록을 사용한다. ZIP은 먼저 압축을 푼다.
- **API:** `POST /api/labeled-imports/check {path}`는 검사 결과와 유효한 경우 토큰을 반환한다. `GET /api/labeled-imports/{token}/image?doc=&page=`는 검사한 문서의 쪽만 제공한다. `POST /api/labeled-imports/{token}/build {name,track,split,tasks,confirmed}`는 검사 후 원본 변경을 다시 확인하고 생성 작업을 시작한다.
- **검사:** `meta.json`의 `format:docgen-labels/1`, 정답 종류·실서류 여부, 문서 라벨 Schema, 파일명/문서 ID, 이미지 연결·실제 크기·EXIF·프레임, 필드 타입·중복 키·쪽·좌표, OCR 규격·좌표, 묶음 문서·시나리오 참조를 검사한다. `import_dir` 제한과 루트 밖 경로/심볼릭 링크를 적용하며 원본에는 쓰지 않는다. 미등록 서식은 오류, 서식 사전에 없는 새 키는 확인 사항이다. 오류·확인 사항은 각각 최대 200건 표시한다.
- **원본 보존:** 검사 결과·파일 해시·처리 설정을 `workspace_dir/labeled_imports/<token>/check.json`에 저장한다. 생성 시 `input/`에 원본을 복사하며 해시를 재확인한다. 원본 변경 시 재검사를 요구한다. 소스 라벨의 `norm`이 없으면 생성기 정규화로 계산하되 원본은 수정하지 않는다.
- **은행 업무:** 렌더러를 띄우지 않고 `Builder.single`로 `classify`, `kie`, `marks`, `ocr_field`를 만든다. 선택 과제만 내보내며 값 칸만으로 쪽 전체 OCR 문항을 만들지 않는다. `meta.json`, `dataset.json`, `tasks/*.jsonl`, `bundles.jsonl`, 원본 복사본을 저장한다. 학습용은 `swift/all.jsonl`도 저장한다.
- **실제 묶음:** `bundles.jsonl`의 문서 ID로 연결하고 검사 시점의 ③ 처리 설정을 고정한다. 직접 추출/비교와 기존 계산·유효기간 규칙을 실제 값에 적용한다. 구비 문항은 명의 확인한 `not_customer` 목록이 있어야 한다(없으면 생략). 같은 서식이 여러 건인 묶음은 현재 오류로 처리한다. 부족한 입력·근거는 생략 사유를 기록한다. 합성 변조 대조 사례·임의 고객 프로필·seed 재생성은 적용하지 않는다.
- **OCR:** 모든 쪽에 저장 OCR이 있고 `ocr_scope:full_page`인 경우만 1부 `prepare`를 실행한다. 모든 manifest 행에 `ocr_json`이 있으므로 OCR 호출이 없다. `reference_type`은 exact→synthetic_exact, reviewed→human_reviewed, pseudo→ocr_pseudo_unreviewed로 보존한다. 평가 전용/학습을 지원하며 학습은 문서 2건 이상을 문서 단위로 분리한다.
- **등록:** 기존 `build_bank`/`build_ocr` 작업·완료 콜백을 재사용한다. `info.dataset`에 출처 results·정답 종류·실서류 여부를 기록해 재시작 복구·중복 방지를 유지한다. 완료 파일을 마지막에 쓴다. 문항이 하나도 없거나 검증·생성에 실패하면 등록하지 않는다.

검증: 관련 회귀 114개 통과. 잘못된 라벨·쪽·좌표·문서 참조 차단, 검사 후 원본 변경 감지, 원본 보존, 실제 Q/A 좌표 변환, 가린 값 계산 제외, 저장 OCR 재사용, 작업 완료 후 자동 등록을 확인했다. 사용자 등록부와 분리한 브라우저 검증에서 예제 폴더 → 검사·정답 미리보기 → 문항 10개 생성 → ⑥ 자동 등록 → 실제 업무 묶음 원본·구비 결과 표시까지 확인했다.

#### 실서류 평가 세트 목표

실서류에서 검수를 마친 것으로 평가 세트를 만든다. **내부망에서만 만들고 쓴다.** 합성 평가 세트와 **같은 과제·같은 답 형식·같은 채점**을 쓴다. 그래서 같은 모델의 합성 점수와 실서류 점수를 나란히 놓을 수 있다.

| 벤치마크 | 재료 | 과제 | 정답 |
|---|---|---|---|
| OCR | 이미지 묶음·결과 폴더의 OCR (8.7) | 1부 8과제 (9.2) | `pseudo`(사내 OCR) 또는 `reviewed`(OCR 검수에서 확인한 쪽만) |
| 은행 업무, 서류 한 장 | 결과 폴더 라벨 검수 (8.6) | `kie`, `marks`, `classify` | 검수한 항목 (값 + 위치), 검수 때 정한 서식 ID·서류명 |
| 은행 업무, 여러 서류 | 실서류 업무 묶음 (아래) | `doc_check`, `cross_check`, `review` | 규칙 코드가 계산하고 사람이 확인한 답 |

**실서류 업무 묶음**

은행 업무의 여러 서류 과제는 한 고객이 한 업무로 낸 서류 전부(묶음)가 있어야 만든다. 합성은 생성기가 묶음을 만들지만, 실서류는 사람이 묶는다.

```
검수를 마친 실서류 문서들 (8.6)
   │
   ▼  ① 묶기: 결과 폴더의 bundles.jsonl 이 있으면 그대로 (RESULTS_FORMAT.md 6절)
   │         없으면 검수한 값(성명, 주민번호, 사업자번호)이 같은 문서끼리 묶음 후보를 제안 → 사람이 확정
   ▼  ② 시나리오 정하기 (docgen/scenarios.json 에서 고름. 예: 전세자금대출)
   ▼  ③ 정답 계산: 합성과 같은 규칙 코드
   │     doc_check  : 시나리오 필수 서류 대비 낸 서류·빠진 서류 (서류 분류로 자동), 타인 서류 (성명·주민번호 비교로 제안)
   │     cross_check: 서류끼리 같아야 하는 값(cases.py 의 대조 항목)을 비교해 일치·불일치 계산
   │     review     : rules.py 규칙(LTV, 만 나이, 유효기간 …)을 검수한 값으로 계산
   ▼  ④ 사람이 계산된 답을 확인·수정 (계산할 수 없는 판단만 직접 입력)
실서류 은행 업무 평가 세트 (docgen.bench 문항 형식)
```

- **실서류 이미지는 바꾸지 않는다.** 합성 대조 문항은 값을 바꾼 변조판을 다시 렌더링해 만들지만, 실서류로는 변조판을 만들지 않는다. 실서류 대조 문항은 실제 서류 그대로의 일치·불일치만 쓴다. 실서류는 대부분 일치하므로 불일치 문항은 적다. 이 차이는 비교표에 함께 적는다.
- 같은 규칙 코드를 쓰려면 `docgen.bench`의 문항 만들기를 **"묶음(서류별 라벨 목록) → 문항"** 함수로 떼어 낸다. 합성 묶음과 실서류 묶음이 이 함수를 같이 쓴다(10절).
- 묶음 검수 결과는 `real_data_dir/bundles/<이름>.jsonl`에 쓴다.

**공통**

- 데이터셋 화면에서 "새로 만들기 → 실서류"를 고르고, 출처 폴더(검수 완료 문서만)·포맷·과제·정답 종류를 고른다. 버전 고정도 합성과 같다.
- 결과 폴더를 만든 모델의 점수는 검수 전 추론과 검수 결과를 비교해 바로 나온다(8.6). 다른 모델은 같은 문항에 추론해 채점한다(9.8).
- **합성이 실서류를 대변하는지 확인하는 데 쓴다.** 같은 모델들의 합성 점수 순위와 실서류 점수 순위가 비슷한지, 포맷·과제별로 합성에서만 쉬운 곳이 어디인지 보여 주는 비교표를 평가 화면에 둔다.
- 실서류 평가 세트의 문항·이미지·정답은 저장소에 넣지 않는다. 버전 정보와 점수 요약만 남긴다.

### 9.8 결과 보기·채점·비교

등록부의 어느 데이터셋이든 **같은 화면에서 문항, 정답, 모델 답, 점수를 본다.** 지금은 1부 OCR viewer(`ocr/viewer/ocr_viewer.py`), 2부 은행 업무 viewer(`bank/viewer/bank_viewer.py`), 비교표 HTML(`reports/benchmark.html`)이 따로 있다.

**읽는 것** (모두 1부·2부 파이프라인이 이미 쓰는 파일, 읽기만 한다)

| 벤치마크 | 문항·정답 | 모델 답 | 점수 |
|---|---|---|---|
| OCR | `<prepared>/benchmark_tasks.jsonl`, `pages.jsonl`, `image_items.jsonl` | `<runs>/predictions/*.jsonl` | `<runs>/reports/*.json` |
| 은행 업무 | `<prepared>/benchmark_tasks.jsonl`, `benchmark_items.jsonl` (또는 `docgen.bench` 폴더) | `<runs>/predictions/*.jsonl` | `<runs>/reports/*.json` |

**하는 일**

| 일 | 내용 |
|---|---|
| 문항 보기 | 과제별로 넘겨 보며 이미지, 질문, 정답 박스를 겹쳐 본다. 서식·조건·과제·사례로 거르기 |
| 답 비교 | 문항마다 정답과 모델 답(여러 모델)을 나란히, 박스는 색을 달리해 겹쳐 본다. 문항 점수가 낮은 것부터 |
| 채점 | 답 파일을 붙이면 `bank_ocr.metrics`·`bank_task.score`(= `docgen.bench.evaluate`)를 불러 채점한다. 명령줄로 낸 점수와 같은 숫자다. 점수 파일은 `workspace_dir`에 쓴다 (등록한 폴더에는 쓰지 않는다) |
| 비교표 | 같은 데이터셋의 모델끼리, 같은 모델의 버전끼리, 합성·실서류끼리, 의사정답·검수 정답끼리. 과제별·서식별·촬영 조건별로 펼친다 |

- **추론은 studio에서 하지 않는다**(11판). 모델 답은 1부·2부 파이프라인의 평가 단계나 `bank_ocr predict`가 만든다. 기존 viewer는 서버에서 모델을 띄워 서류를 바로 물어보는 기능이 있어 그대로 둔다. studio는 저장된 결과를 보고 비교하는 쪽을 맡는다. 두 쪽이 같은 파일을 읽으므로 섞어 써도 된다.

### 9.9 학습으로 이어 쓰기

studio가 만든 데이터셋은 **1부·2부 학습 파이프라인이 그대로 읽는 폴더**다. 학습 코드는 바꾸지 않는다. studio는 학습 코드가 읽을 폴더와 설정 조각을 만들어 주고, 학습이 끝나면 결과를 다시 읽어 온다. 단계별 따라하기는 [TRAINING.md](TRAINING.md)에 둔다.

| 학습 | 파이프라인 | studio 데이터셋을 넣는 곳 | 학습이 끝난 뒤 |
|---|---|---|---|
| 1부 OCR | `ocr/run_pipeline.py` | `configs/pipeline.json`의 `data_config`가 가리키는 1부 설정의 `output_dir` = studio의 OCR 데이터셋 폴더. 폴더에 `DONE.json`이 있으면 파이프라인이 준비 단계를 건너뛴다(`stage_prepare`) | `runs/<실험>/`을 그 데이터셋의 `runs`에 붙인다 → ⑦ 평가 |
| 2부 은행 업무 | `bank/run_bank_pipeline.py` | `configs/bank_pipeline.json`의 `data.train`(은행 업무 학습 데이터셋, `docgen.bench --split train` 폴더 목록), `data.benchmark`(고정한 평가 세트), `data.replay.path`(1부 OCR 데이터셋의 `train_sft.jsonl`), `ocr_check.tasks`(1부 OCR 데이터셋의 `benchmark_tasks.jsonl`) | 같음 |

**화면: 데이터셋 → "학습 설정 내보내기"**

- 학습 종류(1부 / 2부)와 데이터셋을 고르면 위 칸을 채운 설정 조각(JSON)을 보여 주고 파일로 저장한다. 나머지 칸(모델 경로, GPU, SFT·GRPO 설정)은 기존 예시 파일(`configs/*.example.json`) 값을 그대로 둔다.
- 경로가 실제로 있는지, 평가 세트가 고정돼 있는지, 학습 데이터셋과 평가 세트가 같은 생성기 버전인지 검사해 경고한다.
- 실서류와 합성 OCR을 함께 학습하려면 두 데이터셋의 이미지 목록을 1부 `bank_ocr merge`로 합쳐 `prepare`를 한 번 돌린 새 데이터셋을 만든다(같은 이미지가 학습과 평가에 같이 들어가는지는 `prepare`가 검사한다).

**기록: 어떤 학습이 어떤 데이터를 썼는지**

- 내보낸 설정마다 등록부에 `trainings` 줄을 남긴다: 학습 이름, 파이프라인, 쓴 데이터셋 ID와 버전, 설정 파일 경로, 만든 날.
- 학습 결과 폴더(`runs/<실험>/`)를 붙이면 그 학습 줄과 연결된다. 그래서 ⑦ 평가의 점수마다 "이 모델은 어떤 데이터로 학습했는가"를 따라갈 수 있고, 데이터셋 설명서에 "이 데이터셋을 쓴 학습" 목록이 생긴다.
- **학습 시작과 진행:** studio는 docgen 컨테이너에 있고 학습 환경(GPU, ms-swift, vLLM)은 학습 컨테이너에 있으므로, studio가 학습을 직접 실행하지는 않는다.
  - "학습 설정 내보내기"는 설정 파일을 공유 폴더에 쓰고, **학습 컨테이너에서 실행할 명령 한 줄**을 보여 준다(복사 버튼). 경로는 `path_map`으로 학습 컨테이너 쪽 경로로 바꿔 쓴다.
  - 학습이 시작되면 파이프라인이 공유 폴더에 남기는 `state.json`과 로그를 읽어 단계별 진행(prepare → eval_base → sft → … → report)을 보여 준다.
  - 끝나면(`report` 단계 완료) 결과 폴더를 그 데이터셋에 자동으로 붙여 ⑦ 평가에 점수가 뜬다.
  - 버튼 한 번으로 학습을 시작하는 것(docgen 컨테이너 → 학습 컨테이너 원격 실행)은 이번 범위에 넣지 않는다.
- 이 PC의 studio는 서식 편집·미리보기용이다. 데이터셋을 만들고 학습에 넘기는 일은 내부망 docgen 컨테이너의 studio에서 한다.

## 10. 생성기·학습 코드 쪽 변경

UI만으로는 안 되고 생성기가 새 파일을 읽어야 한다. 최소한으로 바꾼다. `ocr/`은 기본 동작을 바꾸지 않고 설정을 더하는 것만 한다.

| 변경 | 위치 | 내용 |

## 11. 구현 단계

각 단계가 끝나면 그 자체로 쓸 수 있어야 한다. 모든 단계는 이 PC와 내부망 서버 양쪽에서 확인한다. 단계마다 브랜치 `claude/docgen-studio`에 커밋한다.

| 단계 | 범위 | 완료 기준 |
|---|---|---|
| 1. 보기·예시 | 서버 뼈대, 설정 파일, 목록, 서식 상세(즉석 렌더링, 키 표), 예시 묶음과 층별 겹쳐 보기, 미리보기 함수 | **끝남.** `python -m studio`로 띄워 476종을 거르고, 아무 서식이나 예시 8장을 층별로 겹쳐 본다 |
| 2. overlay 고치기·표시 요소 | 영역 편집기, 배경 지우기(흰색·주변색), 수정층, 표준 키 사전 초안, 서식 목록표(검수 버튼·배정), 표시 설정, 표시 요소 풀(기본 항목 등록, 이미지 올리기, 가중치), 문제 표시, 수정 전후 비교 | `hf169`의 겹침을 고쳐 저장하면 생성기가 고친 대로 만든다. 다시 추출해도 수정이 남는다. 배경 일부를 지우면 렌더링에 반영된다. 올린 서명 이미지가 풀에 들어가 생성 이미지에 나온다 |

| 7. 가져오기·OCR 검수 | 이미지 폴더·끌어다 놓기, PDF 쪽 나누기, 사내 OCR 호출·캐시, `from-docgen`, 포맷·양식 묶기, 포맷 목록과 결정, "템플릿으로"(견본 고르기, 마지막에 지울 후보·값 영역 초안), OCR 검수, 이미지 묶음 → OCR 세트 | **이 PC에서 끝남 (2026-10-20).** `from-docgen` 묶음(재직·경력·퇴직연금·소득금액, 문서 12건 19쪽)이 3포맷으로 묶이고(순도 0.8: 겉모습이 같은 재직·경력증명서가 한 포맷, 양식으로는 갈림), 견본으로 만든 서식에 값 자리 초안이 들어가 생성된다. OCR 검수로 고친 쪽만 모은 세트가 `human_reviewed`로 1부 prepare·등록된다. 남은 것: 내부망에서 실제 이미지 묶음으로 OCR → 묶기 확인. 원래 기준: 생성 데이터를 `from-docgen`으로 넣어 서식별로 맞게 묶인다(서식 ID 대비 묶기 정확도 보고). 견본 하나로 overlay(image) 서식을 만들어 생성한다. OCR JSON 일부를 일부러 틀리게 넣고 OCR 검수로 고친 뒤, 같은 모델 답을 의사정답·검수 정답으로 채점하면 틀린 만큼 차이가 난다. 내부망에서 실제 이미지 묶음으로 OCR → 묶기를 확인한다 |
| 8. html 서식 만들기 | 분석기 설정·연결 확인(`cli`·`openai`), 작업 폴더·작업 화면, `html` 작업(이미지 → html), `layout` 작업(overlay 값 영역 초안), html 편집기(원본 겹쳐 보기, 행 수 바꿔 보기, 저장 전 검사, 다시 고쳐), 복제, `form.json`(항목·반복 목록), 단순 값 규칙 | **이 PC에서 끝남 (2026-10-20, 시험용 CLI 분석기로).** 그림 올리기 → `cli` 작업 → 검사(행 최소 1쪽·최대 3쪽) → 승인 → html 편집기에서 고쳐 저장 → 다시 고쳐 → 승인하면 그 서식이 바뀜, `layout` 결과가 영역 편집기의 "추가" 칸으로, 외부 분석기에 실서류 그림은 막힘. 남은 것: 실제 CLI(내부망에 있는 것) 하나를 붙여 확인. 원래 기준: 거래내역 서식 이미지 하나를 CLI로 html 서식으로 만들고 편집기에서 고친다. 행 수에 따라 1쪽짜리와 3쪽짜리가 모두 생성되고, 쪽이 나뉘어도 정답 박스가 맞다. 재직증명서를 복제해 새 항목 하나를 넣어 생성한다. `cli` 분석기를 하나 이상 붙인다 |
| 9. 실서류 | 결과 폴더 가져오기(형식 검사, 저장된 OCR로 묶기), 키 대응, 라벨 검수(라벨 모드, 같은 자리 모아 보기, 의심 먼저 보기), 검수 전후 점수, 실서류 업무 묶음(묶기, 시나리오, 정답 계산·확인), 실서류 평가 세트(OCR, 서류 한 장, 여러 서류), 합성·실서류 비교표, `autolabel` | **이 PC에서 끝남 (2026-10-20).** 생성 데이터로 만든 결과 폴더(값 20%를 일부러 틀림, 키 둘은 다른 이름)를 검사·가져와 저장된 OCR로 묶고, 포맷의 서식을 정해 키 대응 → 문서마다 고쳐 확인 → 표준 라벨 v1 폴더(`real_data_dir/labels/<묶음>/`) → ④ 라벨 있는 데이터 검사 통과. 검수 전 점수는 평가 세트와 같은 채점기(`Builder.single` 로 만든 kie·marks 문항)로 낸다. 업무 묶음은 화면에서 정해 v1 `bundles.jsonl`(시나리오 필수, 서식마다 한 건). `autolabel`은 내부 openai 방식 분석기만(시험용 가짜 서버로 확인). 남은 것: 내부망에서 실제 결과 폴더로 포맷 하나 검수, 실제 모델 2개 점수. 원래 기준: 생성 데이터를 결과 폴더 형식으로 바꿔 넣고(정답 일부를 일부러 틀리게) 검수 → 검수 전 점수가 틀린 만큼 낮게 나온다. 생성 묶음의 서류들을 묶음 정보 없이 넣어도 묶음 후보가 맞게 나오고, 계산된 구비·대조·심사 답이 생성기 정답과 같다. 내부망에서 실제 결과 폴더로 포맷 하나를 검수해 실서류 평가 세트를 만들고 모델 2개 점수를 낸다 |

**멈춰서 확인받는 곳:** 2단계 영역 편집기 사용감과 영어 키 통일 목록, 5·6단계는 생성기 출력이 바뀌기 전에 바뀐 예시 한 벌. 생성 결과가 바뀌는 5·6단계는 평가 세트 `VERSION`을 한 번에 올린다(알려진 생성기 버그 수정도 이때 함께, 13절).

## 12. 정해야 할 것

| 항목 | 상태 |
|---|---|
| 서식 종류 | **정함.** `html`, `overlay` 두 가지. 출처는 `origin` 속성 |
| 키 | **정함.** 영어 표준 키가 기본. 표준 키 사전을 둔다 |
| 검수 완료 | **정함.** 사람이 누른다. 자동 검사는 경고만 한다 |
| 내부망 | **정함.** 같은 코드, 설정 파일만 다름. 분석기는 `openai`/`cli` 두 방식으로 무엇이든 붙인다 |
| 두 벌인 영어 키 통일 | 초안. 사전 `docgen/keys.json`(`docgen/scripts/build_keys.py`)의 `duplicates`에 이름 두 벌 5건과 제안을 적었다(예: 직장은 `employer.*`, 고객인 법인은 `company.*`). `corp_no`→`corp_reg_no`는 이미 통일됨. 나머지 이름 바꾸기는 생성 결과가 바뀌므로 평가 세트 버전을 올릴 때 사용자 확인 후 한다 |
| 내부망 분석기 | 미정. 내부망에서 쓸 수 있는 vLLM 주소와 CLI 종류 |
| 실서류 저장 위치 | 미정. 내부망 담당과 정한다. 저장소에는 넣지 않는다 |
| 사용자 수 | 처음에는 혼자. 여러 명이면 저장 때 파일 충돌 검사를 넣는다 |
| 내부망 배치 | **정함.** studio = 기존 docgen 도커 컨테이너(이미지 그대로, 패키지만 코드와 함께 반입), 접속 = SSH 터널, 학습 = 폴더를 공유하는 별도 학습 컨테이너. 학습은 studio가 설정과 명령을 내주고 진행·결과를 읽는다 (3절 원칙 6, 9.9) |
| OCR 읽기·부르기 | **정함.** `ocr/bank_ocr/data.py`(1부 OCR 준비 단계)를 불러 쓴다: `scan` 규칙, `find_saved_ocr`, `parse_ocr` + `mapping`, `ocr_callable`·`ocr_revision`, 같은 캐시 키 (8.2) |
| 가져오기 방식 | **정함.** 두 방식. ① 이미지 묶음 → 사내 OCR(`internal_ocr_adapter` 방식) → 묶기 → 템플릿으로 만들지 결정. ② 결과 폴더(이미 만든 OCR·추론 결과, [RESULTS_FORMAT.md](RESULTS_FORMAT.md)) → 묶기 → 검수 → 실서류 평가 세트 (8절, 9.7) |
| 수정 반영 | **정함.** 고친 것은 파일로 저장되고 다음 빌드부터 평가·학습 데이터 모두에 반영. 고정한 버전은 그대로. 실서류 검수 결과는 합성 생성에 들어가지 않고 실서류 평가 세트로만 쓴다 (9.6) |
| 배경 지우기 | **정함.** overlay 영역 편집기에서 사각형·OCR 단어·지울 후보를 흰색 또는 주변색으로 덮는다. 원본은 두고 지운 영역 목록만 저장 (4.2) |
| 표시 요소 | **정함.** 확률(`marks.json`)과 모양(풀)을 나눈다. 체크·서명은 이미지 풀, 도장은 틀이 기본. 화면에서 그리기·틀 편집기는 두지 않는다 (4.7) |
| 범위 줄임 (11판) | **정함.** 뺀 것: studio 안 모델 추론, 표시 요소 그리기·도장 틀 편집기, 분석기의 영역 하나 제안(`suggest`). 뒤로 미룬 것: 지울 후보·값 영역 초안(7단계 마지막). 넣지 않은 것: 데이터셋 사이 누수 검사, 검수 품질 관리(재검수 표본) |
| html 서식 | **정함.** CLI 분석기가 이미지를 보고 html로 만들고, 사람이 화면에서 템플릿을 고친다. 표 행 수·여러 쪽이 바뀌는 서류를 위해서다. 값은 `form.json`의 항목·반복 목록 선언으로 채운다 (4.3) |
| 학습 연결 | **정함.** 학습 코드는 바꾸지 않고, studio가 설정 조각을 내보내고 학습 결과 폴더를 다시 붙인다. 어떤 학습이 어떤 데이터셋 버전을 썼는지 등록부에 남긴다 (9.9) |
| 데이터셋 설명서 | **정함.** 데이터셋마다 자동 칸 + 사람이 쓰는 칸(목적, 한계)으로 된 설명서 (9.1) |
| masking_ui 묶기 코드 재사용 | **정함.** 지문·묶기 함수만 `studio/formats.py`로 옮기고 masking_ui 의존은 끊는다. 두 도구는 합치지 않는다 (8.3) |
| 서버 구성 | **정함.** FastAPI + uvicorn (3절 원칙 6) |
| 데이터셋 생성 코드 | **정함.** `docgen.bench`·`ocr/bank_ocr`·`bank/bank_task`에 두고 studio는 불러 쓴다. 명령줄로도 같은 레시피가 돈다 (9.1) |
| studio의 역할 | **정함.** 벤치마크 데이터 생성·관리기. 두 벤치마크(OCR, 은행 업무) × 세 출처(합성, 이미지 묶음, 결과 폴더)를 데이터셋 등록부 하나로, UI 한 곳에서 관리한다 (1절) |
| OCR 벤치마크 형식 | **정함.** 세 출처 모두 1부 `bank_ocr prepare` 형식·채점. `docgen.bench`의 `ocr_field`·`ocr_page`는 기존 세트 호환으로 남기고, 계획했던 `ocr_spot`은 1부 `spotting`으로 대신한다 (9.2) |
| OCR 검수 정답 | **정함.** 사내 OCR을 사람이 고친 것을 사내 OCR 응답 형식 그대로 저장해 1부 `scan --ocr-dir`로 읽는다 (8.7) |
| 실서류 업무 묶음 | **정함.** 사람이 묶고 시나리오를 정하면 정답은 규칙 코드가 계산하고 사람이 확인한다. 실서류로 변조판은 만들지 않는다 (9.7) |
| 글자 덩어리 단위 | 미정. 합성 OCR 정답의 한 항목을 단어로 할지 줄로 할지. 내부망의 실제 사내 OCR 결과를 보고 맞춘다 (9.2) |
| 좌표 형식 | **정함.** OCR 단계와 같은 `bbox_2d` 0~1000 정수, 여러 쪽이면 `page`(1부터). 정답은 픽셀로 저장 (9.3) |
| 문서 이해 답 | **정함.** `kie`·`marks`는 좌표를 함께 답한다. 값 점수는 따로 내서 이전 버전과 비교한다 (9.3) |
| 합성 OCR 정답 범위 | **정함.** 렌더링 때 서식 고정 문구까지 모든 글자 덩어리의 박스를 재서, 1부 `spotting`처럼 쪽 전체 글자를 정답으로 쓴다 (9.2) |
| 은행 업무 좌표 | 선택. 대조 문항의 불일치 근거 위치는 나중에 9.3 형식으로 붙인다 |
| 사례·규칙 편집 | 지금은 코드로 둔다(9.4). 단순한 사례(값 하나 바꾸기)는 나중에 데이터 파일로 뺄 수 있다 |

## 14. 제출 역할·HTML 값 영역·값 점검 (2026-10-21)

### 14.1 제출 역할과 실제 서식

`docgen/document_roles.json`이 제출 역할별 서식 ID 목록을 정한다. 예를 들어 대출신청서 역할에는 기존 HTML, `hana_official_049` HTML, `hf049` PDF 배경 서식이 들어간다. ③에서 역할마다 서식 하나를 고른다. 저장되는 `scenarios.json.docs`는 선택한 실제 ID 목록이므로 이미지·구비 검사·데이터셋 생성이 같은 선택을 사용한다. 같은 역할 두 개를 필수 서류로 넣으면 저장을 막는다. 기존 시나리오 선택은 자동 교체하지 않는다. 복제본은 부모 역할을 이어받고, 미등록 서식은 독립 역할이다.

발급신청서와 발급 증명서, 개인과 법인, 가입자 증명과 전체 가입이력처럼 범위가 다른 문서는 구분한다. 특정채무 보증·집합건축물 전유부 등 범위가 있는 대응본은 설명을 표시한다. **역할이 같아도 필드 키 호환을 뜻하지 않는다.** 교체한 서식을 참조하던 직접 추출·비교 작업은 끄고 항목 재선택 표시를 한다. 새 서식의 키를 골라 다시 켠다. 코드로 된 기본 대조·심사도 필요한 문서 ID와 키가 있을 때만 실행한다. 역할 이름만 보고 키를 추정하지 않는다.

### 14.2 HTML 글자 값 영역 편집

①의 **영역 편집**을 HTML에도 제공한다. 실제 생성 이미지 위에서 칸 선택·이동·모서리로 크기 조절·좌표 입력·다른 쪽으로 이동·새 값 칸 그리기·출력 제외·수정 취소를 할 수 있다. 항목명·값 출처(`profile.*`, `rule:*`)·고정 값·글자 크기도 고친다. 위치가 없는 항목도 목록에 표시하며, 이를 선택한 뒤 그리면 해당 키에 위치를 연결한다. 체크·도장·서명은 이 글자 편집 대상에서 제외하며 현재는 HTML 템플릿에서 편집한다. overlay는 기존 편집기를 사용한다.

- 공개 HTML 수정: `docgen/forms/html_regions/<ID>.json`. 내부 전용 HTML은 그 서식 폴더의 `regions.json`.
- 원본 템플릿을 보존하는 별도 수정층이다. 좌표는 페이지 왼쪽 위 기준 **CSS px**이며 overlay의 PDF pt와 다르다.
- `regions`는 `{key, occurrence?, page?, rect?, source?, label?, text?, choices?, font_size?, drop?}` 목록. `occurrence`는 같은 키의 출력 순서(0부터). 같은 키의 값 출처는 하나이며 위치는 출력마다 고칠 수 있다.
- `GET/PUT /api/forms/{id}/regions`. 저장 전 미리보기는 render API의 `draft.html_regions`를 사용하며 파일을 바꾸지 않는다. 저장은 이미지 렌더링으로 페이지·좌표를 확인한 뒤 처리한다.
- 값 수정은 `FieldRecorder`, 위치 수정은 페이지 나눔 후 이미지·라벨 수집 전에 적용한다. Studio·CLI·은행 업무·OCR 데이터 생성이 같은 경로를 쓴다. 새 값도 `f()`로 기록해 이미지와 정답·근거 좌표가 함께 바뀐다. 수정 파일과 공통 적용 코드는 미리보기 해시에 포함한다.
- 페이지 수·반복 행이 바뀌는 서식은 다른 고객 seed에서도 미리보기를 확인한다. 지정한 페이지가 없거나 좌표가 페이지 밖이면 오류로 알린다.

### 14.3 이미지 값 점검과 남은 범위

`python -m docgen.scripts.audit_form_values --out studio_cache/value_audit/final`은 모든 서식을 실제 이미지로 렌더링하고 각 쪽 이미지·모든 쪽 모음·필드 JSON·빈 텍스트 키·위치 누락·페이지 밖 값·쪽 넘침을 기록한다. 스냅샷은 `docgen/manual/form_value_audit.json`, 표는 `docgen/manual/FORM_VALUE_AUDIT.md`. ① 상세에서 해당 결과와 코드 변경 후 재검사 필요 여부를 표시한다. **자동 검사는 사람 검수 완료와 별개이며 인쇄된 모든 입력칸의 값 출처 연결을 보증하지 않는다.**

현재 seed 0 기준 545종·917쪽 검사에서 렌더링 실패·채운 값의 위치 누락·페이지 밖 값·쪽 넘침은 0건이다. 빈 텍스트 항목은 6,531개이며, 미사용 행·기재 대상이 아닌 칸·문장 조각·출처 미연결이 함께 들어 있다. 정부 HTML·일부 약정 등 주요 기재란만 연결한 서식은 설명을 표시한다. `hf407`은 본문 설명서이므로 고객 값을 임의로 만들지 않는다. 전체 수동 대조·미연결 칸 보완이 끝난 상태로 표시하지 않는다.

기본 생성은 알아낸 텍스트 칸을 무작위로 비우지 않고 반복 표를 최소 한 행 채운다. 예전 희소 채우기는 `Profile.extra.sparse_fields=true`로 사용한다. 금액 단위를 성명 규칙보다 우선하고 천원·만원·백만원·억원으로 표시값을 환산한다. 필드의 `unit`을 보존하며 숫자 `norm`은 원 단위다. `shared_copies=true`인 약정 보관본·고객 사본의 동일 값은 공유한다. HTML 값 선언은 `parent.<경로>`로 부모 생성값을 참조하며 `part`(날짜 숫자 순서)와 `format`(`number`, `yy`, `office_prefix`)으로 인쇄된 단위·접미사에 맞춘다. 합성 결과가 달라지므로 기존 평가 세트를 덮어쓰지 않고 새 버전으로 생성한다.

## 15. 서류 넣기 — 여러 장을 한 번에 넣어 서식·시나리오·데이터를 고친다 (2026-10-21, 설계)

### 15.1 왜 바꾸나

④ 가져오기·⑤ 검수·⑦ 평가에 목적이 다른 일 셋(새 서식 등록, 실서류 평가 세트, OCR 정답)이 섞여 있어 무엇부터 해야 하는지 알기 어렵다. 새 서식을 이미지에서 만들려면 ④ OCR → 묶기 → 템플릿으로 → (html이면) ⑧ 분석기까지 가야 한다. 실제로 들어오는 것은 **외환 문서 뭉치처럼 원본 이미지 여러 장 + (있으면) OCR + 추출 결과**다. 이것을 한 번에 넣고, studio가 만든 변경안을 **양식 단위로 일괄 승인**하는 흐름 하나로 바꾼다. 9단계까지의 부품(결과 폴더 형식, `formats.py` 묶기, `create_template`, `value_drafts`, 라벨 검수, 표준 라벨 v1)은 그대로 쓰고, 입구와 끝(무엇으로 반영하나)을 바꾼다.

### 15.2 넣는 폴더

```
<넣을 폴더>/
  images/<업무>/<건>/<서류>/p1.png …   PDF면 <서류>.pdf 하나. 쪽 순서 = 파일 이름 순서
  ocr/<같은 경로>/p1.json              (선택) 사내 OCR 응답 그대로 (1부 find_saved_ocr 규칙)
  pred/<업무>/<건>/<서류>.json          (선택) 추출 결과 (RESULTS_FORMAT.md 4절 items 형식)
  cases.csv                             (선택) 파일 경로 → 건·업무 목록 (접수 시스템에서 뽑은 것). 있으면 추정보다 우선
  meta.json                             (선택) 없으면 기본값 (real_data: true, 사내 OCR 형식)
```

- **업무** = 기존 시나리오 ID 또는 새 업무 이름. **건** = 고객 한 명의 신청 한 건. **서류** 이름은 자유이며 서류 종류는 studio가 묶어서 알아낸다.
- 단계가 빠져도 된다: `images/<건>/<서류>/…`, `images/<서류>/…`, `images/*.png` 모두 받는다. 깊이로 판단하지 않고 **문서 = 이미지가 직접 든 가장 안쪽 폴더(또는 PDF·이미지 한 장)**, 그 위 단계를 차례로 건·업무로 본다. 위 단계가 없으면 15.5의 추정을 쓴다.
- 추출 결과 `items`: `{key, value, bbox_2d?(0~1000), page?(1부터), label?, type?}`. 키는 모델 키 그대로 둔다(표준 키와의 대응은 양식 단위로 한 번).

### 15.3 화면: 한 화면, 위에서 아래로 3단계

메뉴: ① 서식 · ② 표시 요소 · ③ 시나리오 · **④ 서류 넣기** · ⑤ 데이터셋(평가는 "비교" 탭) · 작업 · 설정. 지금의 ⑤ 검수(라벨·OCR 검수)는 ④의 "실서류 정답 만들기"에서 들어가고, 기능은 그대로 둔다.

```
④ 서류 넣기                       [❶ 넣기] ─ [❷ 양식 정리] ─ [❸ 반영]
❶ 넣기   폴더 경로 [________] [검사]
  ✓ 업무 3 · 건 120 · 서류 860 · 쪽 1,420 · OCR 100% · 추출 결과 82%
  ⚠ 업무·건 구분 없음 → 추정합니다                          [묶기 시작]
❷ 양식 정리   양식 24개 · 많은 순
  [견본] 118장 · 판정: 기존 서식 loan_application 과 같음 (0.93)
         [기존 서식 ▾] [새 서식] [건너뛰기]   용도 ☑ 원본 데이터로
  [견본]  42장 · 판정: 새 서식  이름 [____] 역할 [▾]
         값 칸 초안 31 (추출 결과) · 지울 후보 +4 (OCR)  [지운 배경 보기] [영역 편집에서 다듬기]
         용도 ☑ 서식으로 ☑ 원본 데이터로
  [견본] 인보이스류 · 양식 61개 · 각 1~6장  (제각각이라 원본 데이터 권장)
  [선택한 판정대로 확정]
❸ 반영
  건·업무 추정   건 112 (확실 97 · 확인 필요 15) · 업무 mortgage 41 · 새 업무 후보 A 14 [이름]
  서식           ☑ 새 서식 5 (미검수 · 내부 전용 폴더)  ☑ 역할 후보 +1
  원본 데이터    ☑ 서류 1,240 · 건 180 → 학습 80% / 평가 20% (건 단위) · 정답: 추출값(의사정답)
  시나리오       ☑ mortgage: 필수 서류 + 재직증명서 (37/41건)  ☑ 새 시나리오 sme_loan
  [반영] → [① 새 서식] [③ 시나리오] [⑤ 데이터셋]
```

- 넣은 기록(묶음)과 판정은 남긴다. 같은 업무 서류를 더 넣으면 앞 판정이 이어져 **새로 나온 양식만** 고르면 된다.
- 반영 전에는 저장소·서식·시나리오 파일을 바꾸지 않는다. 반영은 변경안 목록 그대로이며 항목마다 끌 수 있다.

### 15.4 양식마다 쓰는 길 (겹쳐 고를 수 있음)

| 용도 | 하는 일 | 기본값 |
|---|---|---|
| 기존 서식과 같음 | 그 서식으로 판정만 기록 (원본 데이터의 `doc_type`, 시나리오 집계에 씀) | 지문이 기존 서식 렌더링과 가까울 때 |
| 서식으로 | 추출값 박스(+여백)와 OCR 지울 후보를 지운 견본 배경 + 박스를 값 칸으로 → overlay 서식 (미검수) | 장수 많고 고정 양식 |
| 원본 데이터로 | 원본 이미지 + 추출값 → 표준 라벨 v1 폴더 (`gt: pseudo`), 검수하면 `reviewed` | 항상 켬. 양식이 제각각(장수 적음)이면 이것만 |
| 건너뛰기 | 아무것도 하지 않음 | 장수 1~2 |

**서식으로 — 값 출처 연결:** 추출 키를 표준 키 사전(`docgen/keys.json`)의 동의어로 프로필 값에 잇는다. 못 이으면 여러 문서의 값에서 종류(날짜·금액·통화·영문 이름·계좌번호·코드)를 추정해 그 종류의 무작위 값으로 채운다. 외환 문서에 필요한 통화 코드·SWIFT·영문 주소 값 종류는 생성기에 새로 더한다.
**남은 개인정보:** 추출하지 않은 칸·서명·도장·메모가 배경에 남을 수 있다. 같은 양식끼리 달라지는 글자(`value_drafts`)를 지울 후보로 띄우고, 사람이 견본을 확인해 승인해야 서식이 된다. 승인 전·검수 전 서식은 데이터셋에 들어가지 않는다(8.5). 실서류 묶음의 서식은 `private_forms_dir`에만 쓴다.
**첫판에서 뺌:** 같은 양식 여러 장을 각각 지워 배경 여러 장으로 돌려 쓰기(다음 판).

**원본 데이터로 — 정답 등급과 용도:**

| 정답 | 학습 | 벤치마크 |
|---|---|---|
| 추출값 그대로 (`gt: pseudo`) | 됨 | 경고. 추출 결과를 낸 모델(`meta.model`)을 이 세트로 채점하면 막는다 |
| 검수한 값 (`gt: reviewed`) | 됨 | 됨 |

- 학습/평가는 **건 단위로** 나눈다(같은 고객이 양쪽에 들어가지 않게). 평가로 뺀 건의 원본은 서식 배경으로도 쓰지 않는다(기본값).
- 내보내기는 v1 폴더 두 개(`<real_data_dir>/labels/<묶음>-raw/train`·`test`)다. 각각 그대로 ④ 라벨 있는 데이터의 경로로 넣어 학습(train)·평가(test) 데이터셋을 만든다. 추출 결과에 없는 보기(체크하지 않은 보기)는 모르므로 체크 문항의 보기는 체크된 것뿐이다.
- 검수는 벤치마크로 쓸 부분만 9단계 라벨 검수로 한다.

### 15.5 건·업무 정하기와 시나리오 변경안

**기준은 사람이 고른다.** 원본에 건 단위 정보가 있으면 그것이 가장 정확하다. ❸ 첫 줄에서 건 기준과 업무 기준을 고르고, 후보마다 덮는 서류 비율과 건 수를 보여 준다(`intake_cases.bases`).

| 기준 | 건 | 업무 |
|---|---|---|
| 폴더 | 서류 위 단계(또는 `cases.csv`) | 그 위 단계 |
| 파일 이름 앞부분 | `20261021-00123_신분증.pdf` → `20261021-00123` (밑줄·띄어쓰기 앞, 둘 이상 서류가 같은 값일 때 후보) | — |
| 추출 키 | 추출 결과의 키 하나(예: 접수번호). 서류 30% 이상에 있고 값이 겹치는 키가 후보 | 값 종류가 20개 이하인 키(예: 업무구분). 값은 시나리오 ID·이름·업무 사전으로 찾고, 없으면 새 업무 이름 |
| 자동 | 고객 식별값으로 묶기(아래) | 서류 조합을 시나리오와 비교 |

- 기본값: 폴더 → 파일 이름 앞부분 → 키 사전에서 건 번호(`document.case_no`)·업무구분(`document.task`)에 이은 키 → 자동. 추출 키를 고르면 그 키 이름을 그 공통 키의 다른 이름으로 남겨 다음 묶음에서 먼저 골라진다.
- 기준 값이 같은 서류는 무조건 한 건이고, 기준 값이 없는 서류만 자동으로 붙인다(기준으로 묶인 건끼리는 합치지 않는다).

**자동 묶기(건 추정):** 서류마다 고객 식별값을 모은다. 추출 결과의 고객·법인 칸(키 사전으로 서식 키 → 당사자), OCR 글자의 주민번호·휴대전화, 다른 서류에서 알게 된 고객 이름, 항목명(성명·이름·고객명·예금주) 바로 옆 이름(한글 3자, 흔한 성).

| 근거 | 묶기 |
|---|---|
| 주민번호 13자리 · 휴대전화 · 고객 계좌번호 · 법인 사업자번호가 같음 | 확실. 같은 번호라 생년월일 충돌을 보지 않는다(미성년 자녀 계좌처럼 서류의 '고객'이 다른 사람인 건) |
| 주민번호 앞 7자리(생년월일·성별) + 이름이 함께 같음, 이름 둘이 함께 같음(법인명·대표자, 고객·가족) | 확실. 두 건의 고객 생년월일이 두 글자 이상 다르면 합치지 않는다(추출 오류 한 글자는 같은 사람) |
| 확실한 근거가 없는 서류가 이름 또는 생년월일만 같은 건 하나와 맞음 | 확인 필요로 붙임 |
| 이름이 건 2~3개에만 나오고 그중 고객 생년월일이 있는 건이 하나 이하 | 확인 필요로 합침. 동명이인은 둘 다 생년월일이 있어 막히고, 흔한 이름(건 4개 이상)은 합치지 않는다 |
| 근거 없음 | 서류 하나가 건 하나 (확인 필요) |

- 건마다 같은 이름이 나오는 다른 건(`same_name`)을 '합칠 후보'로 띄운다. 사람은 확인 필요인 서류만 보고 옮기기·합치기·업무 정하기·확인을 한다(`intake_cases.edit`).
- **업무 추정:** 건의 역할 조합과 시나리오 자리의 겹침(F1)이 0.5 이상인 시나리오 중 가장 큰 것. 안 맞는 건은 조합이 비슷한(Jaccard 0.5) 것끼리 "새 업무 후보 A, B …".

**시나리오 변경안**(`intake_plan.proposals`, 업무마다 건 비율로):

| 변경 | 조건 | 기본 |
|---|---|---|
| 필수 추가 | 시나리오에 없는 서류가 건 70% 이상 (건 둘 이상) | 켬 |
| 선택 추가 | 20~70% (건 둘 이상). 시나리오의 `optional`에 넣고 구비 검사에서는 필수가 아니다 | 켬 |
| 필수 → 선택 / 빼기 | 필수인데 20~70% / 20% 미만. 업무의 건이 5개 이상일 때만 | 끔 |
| 후보 서식 | 자리에 기준 서식 말고 같은 역할의 다른 서식이 나옴 → 샘플링 후보·가중치(나온 건 수) | 켬 |
| 대조 추가 | 같은 공통 키가 한 건의 두 서류에 70% 이상 함께 나옴 → 기준 서류(그 키가 가장 많은 자리) ↔ 다른 자리 '같다' 비교. 공통 키마다 한 줄 | 켬 |
| 새 시나리오 | 새 업무 후보가 건 3개 이상이고 필수 서류가 있을 때. 그보다 작으면 '어디에도 안 맞는 건'으로만 보인다 | 켬 |

- 원본 데이터로만 쓰는(서식으로를 끈) 새 양식은 서식이 되지 않으므로 시나리오 변경안에 넣지 않는다.
- 심사 규칙(금액 한도 등)은 데이터만으로 정할 수 없어 제안하지 않는다.

**반영**(`intake_plan.apply`): ① '서식으로'를 켠 새 양식을 overlay 서식으로 등록(견본 쪽 그림 + 지울 자리 = 추출값·남은 값 후보, 값 칸 = 추출값 위치, 키 = 이은 공통 키 또는 추출 키. 미검수라 영역 편집기 확인 전에는 데이터셋에 안 들어감. 실서류는 `private_forms_dir`) → ② 등록된 서식으로 변경안을 다시 계산해 고른 것을 시나리오에 저장(③ 저장과 같은 검사) → ③ 원본 데이터 내보내기(15.4). 반영 기록은 `batch.json`의 `applied`.

### 15.7 키 사전 화면 — 키·값 종류·값 출처·동의어를 한곳에서

**지금 흩어져 있는 것** (모두 코드나 자동 생성 파일이라 화면에서 고칠 수 없다):

| 무엇 | 어디 |
|---|---|
| 키 목록 1,915개 (항목명 예, 타입, 쓰는 서식 수) | `docgen/keys.json` — `build_keys.py`가 렌더링 결과로 자동 생성 |
| 키 동의어 (`dob`→`birth` …) | `docgen/schema.py` `LEAF_SYNONYMS` |
| 이름 두 벌 5건과 결정 | `keys.json` `duplicates` (결정은 다시 만들어도 유지) |
| 항목명 → 표준 키 (`성명|이름|예금주…` → `customer.name`) 32개 | `docgen/realform.py` `KEY_RULES` |
| 항목명 → 값 종류 (`통화`→currency, `외화금액`→fx_amount …) | `realform.py` `KIND_RULES` |
| 값 종류별 값 만들기 | `realform.py` `Values` (overlay), html 서식은 서식마다 생성 함수 |
| 값 재료 | 프로필(`docgen/entities.py`). 외국 거래 상대(`foreign`: 영문 이름·주소·국가·은행·SWIFT·계좌)는 이미 있으나 overlay 값 종류에는 연결되어 있지 않다 |

**바꿀 것:** 사람이 정하는 부분을 데이터 파일 `docgen/key_rules.json`으로 옮긴다(첫판은 지금 코드의 값을 그대로 옮겨 **생성 결과가 바뀌지 않게** 하고, 서식 표본을 렌더링해 옮기기 전후 값이 같은지 시험한다). `keys.json`은 지금처럼 자동 생성이고, 화면은 두 파일을 합쳐 보여 준다.

```json
{"keys": {"customer.name": {"meaning": "고객 성명", "kind": "person_name", "source": "profile.person.name",
                            "aliases": ["name", "applicant_name", "remitter.name"], "labels": ["성명", "이름", "예금주", "Name"]}},
 "kinds": {"swift": {"how": "source", "source": "profile.foreign.swift", "example": "BFTVVNVX"},
           "currency": {"how": "choices", "choices": {"USD": 3, "EUR": 1, "JPY": 1, "CNY": 1}},
           "hs_code": {"how": "pattern", "pattern": "####.##-####"}}}
```

- `aliases` = 모델·외부 추출 키 이름 (서류 넣기의 키 대응), `labels` = 서식의 항목명 (overlay 자동 키, 지금 `KEY_RULES`).
- 값 종류 방식은 셋: `source`(프로필 값), `choices`(목록·가중치), `pattern`(`#`숫자 `A`대문자 `a`소문자). 계산이 필요한 종류(주민번호 검증 자리, 날짜 앞뒤 관계 등)는 코드로 두고 화면에는 읽기만.

**메뉴:** ① 서식 다음에 **키 사전**을 둔다.

```
키 사전   키 1,915 · 사람이 정한 키 174 · 이름 두 벌 5 (미결 5) · 대기 23
[키] [값 종류] [대기 23] [이름 두 벌]
─ 키 탭 ────────────────────────────────────────────────────────────
 [검색____] [그룹▾] [값 종류▾] ☐ 값 출처 없음만      | customer.name
 키              항목명 예      값 종류    서식      | 뜻     [고객 성명        ]
 customer.name   성명·이름·예금주 person_name 312    | 값 종류 [person_name ▾] 값 출처 [profile.person.name ▾]
 remitter.swift  SWIFT CODE     (없음)       4  ⚠   | 예시 값: 박찬연 · 김민수 · 이서준  [seed 바꾸기]
 …                                                  | 동의어(추출 키) name · applicant_name [+]
                                                    | 항목명          성명 · 이름 · 예금주 [+]

─ 값 종류 탭 ─ 종류마다 방식·예시 10개, [새 종류] (이름, 방식 고르기, 미리보기)
─ 대기 탭 ── 서류 넣기에서 들어온 모르는 추출 키
 추출 키          항목명         예시 값            추정        제안
 remitter_swift   SWIFT CODE    BFTVVNVX·KOEXKRSE  swift(0.95)  [remitter.swift 새 키] [기존 키에 동의어] [무시]
 [제안대로 전부 승인]
─ 이름 두 벌 탭 ─ duplicates 의 결정 고르기 (바꾸면 평가 세트 버전을 올려야 한다는 안내)
```

- **대기 탭이 서류 넣기와 사전을 잇는다.** ❷ 양식 정리에서 사전에 없는 추출 키는 여기로 모인다. 제안은 키 이름 유사도 + 항목명 + 예시 값으로 추정한 값 종류로 만들고, 일괄 승인한다. 승인하면 같은 키를 쓰는 모든 양식 초안의 값 출처가 한 번에 채워진다.
- 저장은 다음 빌드부터 반영된다. 기존 키의 값 종류·출처를 바꾸면 그 키를 쓰는 서식 수와 "평가 세트 버전을 올려야 함"을 보여 주고, 고정한 데이터셋은 그대로 둔다(9.6).
- 외환 쪽에서 실제로 새로 만들 값 종류는 IBAN, HS 코드, 인코텀즈, 항구·선박명 정도다. 영문 이름·주소·국가·은행·SWIFT·계좌는 프로필의 `foreign`에 이미 있어 `source`로 잇기만 하면 된다.

**외부 문서:** 생성기에 없는 양식으로 "새 서식"·"새 업무"를 시험하려고 공개 문서(허용 라이선스: CC-BY·MIT·Apache 등)를 모아 라벨을 붙여 시험 폴더에 섞는다. 출처·라이선스·SHA-256을 함께 기록한다. 이 클라우드 환경에서는 파일 저장소(Hugging Face 파일 CDN, 정부 사이트)가 망 정책으로 막혀 있어(2026-10-21) 받을 수 있게 되면 넣는다.

## 16. 키 사전 — 업무명·문서명·키 (2026-10-21)

### 16.0 정리: 화면·문서에서 쓰는 말은 셋

프롬프트가 묻고 답하는 것은 **업무명 · 문서명 · 키**다(분류 문항의 정답 = 문서명, 추출·표시 문항 = 키와 그 이름표, 구비·대조·심사 = 업무명·문서명). 그 밖의 것(값 종류·다른 이름·나오는 문서·쓰는 업무)은 이 셋에 대한 설명이다.

| 말 | 갖는 것 |
|---|---|
| 업무명 | 이름 · 다른 이름(서류 넣기의 업무 폴더 이름) · 필요한 문서 · 서류끼리 대조할 공통 키 · (드물게) 이 업무에서만 뜻이 바뀌는 이름(buyer = 고객) |
| 문서명 | 이름(분류 정답) · 다른 이름(영문·줄임말) · 대분류 · 서식들 |
| 키 | 범위(공통 / 문서별) · 이름 · 값 종류 · 가짜 값 출처 · 다른 이름(외부 추출 키) |

**키의 범위**
- **공통 키** (`common.json`, 첫판 74개): 여러 문서에 나오고 서류끼리 대조·심사하는 값. 이름을 사전에서 정한다(`customer.name` 고객 성명, `foreign.swift` 외국 상대 SWIFT 코드 …).
- **문서별 키**: 서식의 키 그대로, 그 문서에서만 의미가 있다(12,592개). 관리하지 않는다.
- 문서별 키를 공통 키에 **잇기**(`links.json`: 이음 · 제안 · 끊음). 이은 칸은 서식이 달라도 공통 키로 묻고 답한다(생성 결과 반영은 평가 세트 버전을 올릴 때, K4). 자동 초안: 이음 999 · 제안 2,074. 여러 문서에 같은 칸이 나오면 **공통으로 올리기**(새 공통 키).
- 아래 16.1~16.3의 당사자·역할·속성·합치기는 **잇기 제안을 만드는 속 장치**다. 화면에는 나오지 않는다.

화면(키 사전): 키(공통 키 / 문서별 키, 잇기·끊기·공통으로 올리기) · 문서 · 업무 · 값 종류.

### 16.0a 처음 설계 (속 장치)

15.7의 키 사전(키·값 종류·동의어)을 넓힌다. 키가 서식마다 따로 붙어 있어 같은 뜻이 여러 이름으로 흩어져 있다(2026-10-21 집계: 필드 키 1,915개, 맨 앞 이름 569가지, 끝 이름 791가지, 영어 표준꼴이 아닌 키 319개, 도장 34·서명 20·체크 125). 서식·시나리오·분류 문항·서류 넣기가 모두 이 사전을 기준으로 삼게 한다.

### 16.1 네 사전과 계층

| 사전 | 계층 | 지금 재료 | 쓰는 곳 |
|---|---|---|---|
| 문서 분류 | 대분류 → 문서 종류 → 실제 서식(html·공식 대조 html·PDF 배경) | `registry.GROUPS`, `document_roles.json` | 분류 문항 정답 이름, 서류 넣기 양식 판정, 시나리오 서류 |
| 업무 | 업무 대분류 → 업무(시나리오) → 필수·선택 문서 종류 + 이 업무의 당사자 역할 | `scenarios.json` | 시나리오·묶음, 서류 넣기 업무 폴더 이름 |
| 필드 키 | **당사자 → 서류 속 역할 → 속성 → 세부·반복** | `keys.json`, `guide/fields/fields.json`, `key_rules.json` | 영역 편집·html 편집 키 고르기, 시나리오 대조·추출, 서류 넣기 키 대응 |
| 표시 요소 | 당사자 → 서류 속 역할 → 표시 종류(도장·서명·체크) + 체크 보기 목록 | `seal.*`·`sign.*` 키, 체크 키의 `options` | ② 표시 요소, 표시 문항 |

**당사자** (업무 문서에 나오는 사람·곳·것): 고객 본인 · 배우자·가족 · 대리인 · 직장 · 법인·사업자 · 거래 상대(국내) · 외국 거래 상대 · 은행·직원 · 발급기관 · 물건(부동산·차량·화물) · 거래(대출·계좌·송금·무역 조건) · 재무 수치 · 문서 자체(발급일·문서번호). 프로필(`entities.Profile`)의 값 위치를 당사자에 붙인다(고객 본인 = `person`, 외국 거래 상대 = `foreign` …).

**서류 속 역할 → 당사자:** `applicant`·`borrower`·`holder`·`debtor`… → 고객 본인. 기본값을 두고, 문서 종류나 업무에 따라 바꾼다(주택담보대출의 매매계약서 `buyer` = 고객 본인, `seller` = 거래 상대 / 해외송금의 `beneficiary` = 외국 거래 상대). 모르는 역할은 "미정"으로 두고 화면에서 정한다.

**속성:** 끝 이름(`name`, `rrn`, `address`, `swift` …). 뜻·값 종류는 속성에 한 번 정하면 모든 당사자가 물려받고, 값 출처는 당사자의 프로필 위치 + 속성으로 정해진다(`remitter.name` → 고객 본인.이름 → `person.name`). 전체 키 규칙(`key_rules.json`의 keys)이 있으면 그것이 우선이다.

### 16.2 합치기

- "A를 B로 합치기" = A는 B의 다른 이름으로 남는다. 지우지 않으므로 이전 라벨·추출 결과도 읽힌다. 네 사전 모두 같다(문서 종류 둘을 하나로, 역할 둘을 하나로, 속성 `account_no` → `account` …).
- **결정과 적용을 나눈다.** 결정(`accepted`)은 언제든 하고, 생성 라벨의 키 이름이 실제로 바뀌는 적용(`applied`)은 평가 세트 버전을 올릴 때 한 번에 한다. 적용 전에도 사전은 두 이름을 같은 것으로 풀어 주므로 시나리오 대조·서류 넣기·채점은 바로 혜택을 본다.
- 후보는 자동으로 만든다: 같은 당사자·같은 속성의 다른 이름, 끝 이름 동의어 꼴(`_no`, `_name`, 단수·복수), 같은 항목명, 영어 표준꼴이 아닌 키의 항목명이 표준 키 규칙에 맞는 것. 사람이 일괄 승인·거절한다.

### 16.3 파일 (`docgen/dictionary/`)

| 파일 | 내용 |
|---|---|
| `parties.json` | 당사자 {id: {name, desc, profile(프로필 위치)}} |
| `roles.json` | 서류 속 역할 {역할: {party, name, by: 자동/사람, by_doc_type: {문서 종류: party}, by_task: {업무: party}}} |
| `attributes.json` | 속성 {id: {name, kind, aliases}} |
| `doc_types.json` | 문서 분류 {groups: {id: name}, types: {id: {name, group, aliases, forms}}} |
| `tasks.json` | 업무 {groups: {id: name}, tasks: {id: {name, group, aliases, roles: {역할: party}}}} |
| `options.json` | 체크 보기 목록 {속성: {options, keys}} |
| `merges.json` | 합치기 {items: [{dict, from, into, reason, status: proposed·accepted·rejected, applied}]} |

- 첫판은 `python docgen/scripts/build_dictionary.py`가 지금 파일들로 **자동 초안**을 만든다. 다시 돌려도 사람이 정한 것(`by: 사람`, 합치기 결정)은 남는다.
- 첫판은 아무 생성 코드도 이 파일을 읽지 않는다 → **생성 결과가 바뀌지 않는다.** 쓰는 쪽 연결(16.5)은 따로 한다.
- 풀이 함수 `docgen/dictionary.py` `resolve(키, 문서 종류?, 업무?) → {party, role, attribute, sub, canonical}`.

### 16.3a 연결 (relations.json, 초안 만들 때마다 새로 계산)

```
업무 ──필수 서류──▶ 문서 종류 ──실제 서식──▶ 서식 ──키──▶ 필드 키 ──역할──▶ 당사자 ──▶ 당사자 키 (customer.name)
  └──이 업무의 역할 → 당사자 (buyer = 고객 본인)──────────────────────────────┘
```

- 업무마다 **둘 이상의 문서 종류에 나오는 사람·기관 당사자 키 = 대조 후보**(같은 값이어야 하는 칸). 해외송금: `foreign.name`·`foreign.address`(4종), `foreign.swift`(2종), `customer.name`… 문서·거래·재무·발급기관·미정 당사자와 반복 행은 뺀다.
- 화면: 업무 → 필수 문서 종류·대조 후보, 문서 종류 → 쓰는 업무·당사자 키, 당사자 키 → 나오는 문서 종류·업무.
- 키 목록(`keys.json`)은 서식 필드(`guide/fields/fields.json`)에서 다시 만든다(`build_keys.py`; 공식 대조 html 69종의 키가 빠져 있었음). 반복 행 `owners[].name` = `owners.*.name`.
- `official.*`(공식 대조 html)은 역할이 아니라 이름 묶음이다. 키마다 합치기 후보로 진짜 키를 찾는다(`official.debtor` → `debtor.name`, `official.address_copy` → `official.address`, 같은 항목명의 표준 키).
- **역할 없는 키**(bank, date, 취급점, 금액 … 2,689개, 주로 overlay 서식의 항목명 키)는 `roles.json`의 `single`에 당사자를 둔다. 첫판은 항목명 규칙의 값 종류로 추정하고(추정 2,183, 미정 1,332), 화면에서 골라 일괄로 정한다.

### 16.4 화면 (키 사전 메뉴)

탭: **문서 분류 · 업무 · 필드 키 · 표시 요소 · 값 종류 · 합치기 후보**. 계층은 나무로(당사자 → 역할 → 속성, 대분류 → 문서 종류 → 서식). 나무에서 고르면 오른쪽에서 이름·다른 이름·당사자·값 종류를 고친다. "미정" 역할과 합치기 후보는 개수를 탭에 띄우고 일괄 승인한다.

## 17. OCR·은행 업무 통합 — 과제 형식·채점·학습·보기 하나로 (2026-10-21)

### 17.1 왜

1부 OCR(`ocr/`)과 2부 은행 업무(`bank/`)는 만든 순서 때문에 나뉘었을 뿐이다. 둘 다 "이미지 + 질문 → 답 + 채점"이고 좌표 형식도 같으며(9.3), 2부 학습은 이미 1부 학습 실행기를 물려받고 OCR 데이터를 섞어(replay) 학습한다. 그런데 문항 형식·채점·GRPO 보상·학습 실행·viewer가 두 벌이고, studio는 `sys.path`를 고쳐 `bank_ocr`를 불러 쓴다. viewer 두 개와 따로 된 학습 명령은 쓰지 않으므로(2026-10-21 확인) 하나로 합친다.

### 17.2 자리

| 자리 | 들어가는 것 | 옛 위치 |
|---|---|---|
| `docgen/bench` (공용, 학습 컨테이너도 import) | 과제 형식 하나, 과제별 채점(OCR 8 + 은행 업무 8), GRPO 보상 하나, OCR 문항 만들기(`ocr_data`·`ocr_augment`·`ocr_tasks`·`ocr_prepare`·`ocr_metrics`) | `ocr/bank_ocr/{data,augment,tasks,pipeline,metrics}.py`, `bank/bank_task/score.py` |
| `studio` | 데이터 만들기 전부(합성·실서류·OCR 준비), 데이터셋·평가 화면 하나(옛 viewer 둘을 대신), 사내 OCR 어댑터 | `ocr/internal_ocr_adapter.py`, `ocr/viewer`, `bank/viewer` |
| `train/` (학습 컨테이너) | 학습 실행 하나(prepare → eval_base → sft → eval_sft → select → grpo → eval_grpo → report), 데이터셋 섞기(목록·비율, 이미지 토큰 예산, 문항 묶기, GRPO 보류 고객), 모델 답 내기, 보상 플러그인, 보고서, 설정 | `ocr/{run_pipeline,train,benchmark_report,bank_ocr_reward}.py`, `ocr/bank_ocr/{inference,settings,cli}.py`, `bank/{run_bank_pipeline,bank_task_reward}.py`, `bank/bank_task/{prepare,report,cli}.py`, 두 `configs/` |

`ocr/`·`bank/`는 옮긴 뒤 지운다. 데모(`ocr/demo.py`)·viewer·옛 문서는 옮기지 않는다.

### 17.3 과제 형식 하나 (`docgen-tasks/1`)

- 데이터셋 = 폴더: `meta.json` + `tasks/<과제>.jsonl` (+ 이미지). 지금 `docgen.bench` 폴더 형식 그대로이고, OCR 준비 결과도 이 형식으로 쓴다.
- 문항: `{id, task, images, prompt, answer, eval, meta}`. OCR 과제는 `answer` = 옛 `target`을 푼 것(`{"text"}` 또는 `{"boxes": [{bbox_2d, label}]}`), `meta`에 `document_id`·`page_id`·`view`·`view_ops`·`reference_type`·`confidence`·`size`·`context_image`·`split`.
- 쪼개기: 폴더의 `meta.split`(test·train), OCR 준비처럼 한 폴더에 섞이면 문항의 `meta.split`(train·val·benchmark)이 우선한다.
- 과제 묶음은 태그다: OCR(`crop_ocr`·`bbox_ocr`·`region_ocr`·`marked_ocr`·`grounding`·`spotting`·`relation`·`marked_box`·`ocr_field`·`ocr_page`), 문서 이해(`classify`·`kie`·`marks`), 업무 처리(`doc_check`·`cross_check`·`review`). 데이터셋의 `track`(ocr/bank)은 없앤다.

### 17.4 채점·보상

- `docgen.bench.evaluate.score_task(task, items, preds)`가 16과제 모두를 채점한다. OCR 과제는 옮긴 `ocr_metrics`를 그대로 불러 **옛 점수와 같은 숫자**를 낸다(대표 지표는 옛 `REPORT_METRICS`와 같음).
- `docgen.bench.evaluate.reward(task, completion, item)` 하나가 GRPO 보상이다(OCR은 옛 `bank_ocr.metrics.reward`, 업무는 옛 `bank_task.score.reward`와 같은 값). 플러그인은 `train/reward_plugin.py` 하나(`reward_funcs: ["docgen"]`).

### 17.5 순서와 완료 기준

| # | 범위 | 완료 기준 |
|---|---|---|
| U1 | 채점·보상 하나 (`ocr_metrics` 옮김, `evaluate`가 OCR 과제도) | 같은 OCR·업무 세트와 답을 옛 코드와 새 코드로 채점하면 과제별 지표·보상이 모두 같음 |
| U2 | OCR 준비를 `docgen/bench`로, 출력에 `docgen-tasks/1` 폴더, studio·docgen 의 `bank_ocr` import 와 `sys.path` 고치기 없앰, 사내 OCR 어댑터는 studio 로 | OCR 준비 결과(문항·쪼개기)가 옮기기 전과 같음, studio 테스트 통과 |
| U3 | studio 데이터셋·평가 하나 (track 없앰, 보기·채점·레시피·라벨 데이터 만들기 하나) | OCR·업무 문항을 한 데이터셋에 섞어 만들고 같은 화면에서 보고 채점 |
| U4 | `train/` 하나 (섞기·학습·답 내기·보상·보고서) | 섞기 결과가 옛 2부 prepare(+OCR replay)와 같은 문항 집합, 학습 실행 리허설(dry-run)·보상 플러그인 시험 통과 |
| U5 | `ocr/`·`bank/` 지우기, 문서(README·guide·TRAINING·docker·이 문서 9절) 고치기 | 저장소에 `bank_ocr`·`bank_task` 참조 없음, 전체 테스트 통과 |
