# 내가 가진 데이터 준비와 UI 사용 순서

현재 구현 기준: 2026-10-20. 설계상의 전체 흐름과 현재 쓸 수 있는 기능을 구분한다.

## 1. 먼저 목적을 고른다

| 목적 | 현재 지원 |
|---|---|
| 이미지·PDF의 글자와 박스를 OCR 정답으로 검수하고 데이터셋 만들기 | 지원 |
| 견본 이미지로 새 합성 서식을 만들고 새 시나리오에 넣기 | 지원 |
| 생성기 공통 라벨 폴더를 검사하고 문항·데이터셋 생성·등록 | 지원, ④ 라벨 있는 데이터 |
| 이미 저장한 OCR·추출 JSON을 결과 폴더로 가져오기 | 지원. ④ 결과 폴더에서 ([RESULTS_FORMAT.md](RESULTS_FORMAT.md)) |
| UI에서 성명·금액 같은 항목 정답을 새로 작성·수정하는 라벨 편집기 | 지원. ⑤ 라벨 검수 (추론 결과 또는 빈 라벨에서 시작, 확인하면 표준 라벨 v1 폴더로) |
| 라벨·묶음 목록으로 구비·직접 추출/비교·계산 문항 만들기 | 지원. ③ 처리 설정 사용. 임의 변조 대조 사례와 묶음 편집 UI는 미구현 |

④의 **포맷 묶기**는 같은 양식의 문서를 찾는 기능이다. 한 고객의 여러 종류 서류를 모으는 **업무 묶음**과 다르다. ③에서 새 시나리오를 저장해도 실제 고객 파일이 그 시나리오에 자동 배정되지 않는다.

## 2. 이미지·PDF 준비

다음은 예시 구조이며 현재 가져오기가 하위 폴더까지 찾는다.

```text
my-documents/
  case_001/
    id_card.png
    application.pdf
    income.pdf
  case_002/
    id_card.jpg
    application.pdf
```

- 이미지 파일 하나는 문서 하나, PDF 파일 하나는 문서 하나다. PDF는 여러 쪽을 유지해 읽는다.
- PNG/JPG/JPEG/TIF/TIFF/BMP/WEBP/PDF를 지원한다. 여러 장의 이미지 파일을 폴더에 넣어도 현재 UI가 자동으로 한 문서로 합치지는 않는다. 여러 쪽 문서는 PDF 한 파일로 준비한다.
- 문서가 다른데 파일 이름이 겹치면 고객/접수 건별 하위 폴더로 구분한다. 폴더명만으로 업무 묶음이 확정되지는 않는다.
- 같은 사람이 접수한 서로 다른 업무 건은 별도 접수 ID로 구분한다. 이름만으로 묶음 ID를 만들지 않는다.
- 현재 OCR 경로에는 question/answer 파일을 미리 만들 필요가 없다. OCR 결과를 검수하면 과제별 문항과 정답은 데이터셋 생성 단계에서 만든다.

## 3. 현재 UI에서 OCR 데이터셋 만들기

사전 설정은 `studio/config.json`에서 한다. [config.example.json](config.example.json)의 `ocr.callable`, `ocr.revision`, 필요한 경우 `ocr.base_url`을 실제 OCR 환경에 맞춘다. `ocr.cache_dir`, `workspace_dir`, `real_data_dir`은 저장 경로다. 실서류로 합성 서식도 만들려면 `private_forms_dir`을 설정한다. ⑨는 설정 조회 화면이다.

1. **④ 가져오기**에서 새 이름을 쓰고 **서버 폴더에서** 또는 **파일 올리기**를 고른다. 서버 폴더는 Studio 프로세스가 접근할 수 있는 경로여야 하며 `import_dir`이 있으면 그 아래만 허용한다. 서버/컨테이너에서 띄웠다면 브라우저 PC의 `C:\...` 경로를 그대로 읽을 수 없으므로 파일 올리기나 서버 공유 경로를 쓴다.
2. **실서류** 여부를 지정하고 **만들고 OCR·묶기** 또는 **올리고 OCR·묶기**를 누른다. 일반 이미지·PDF 가져오기는 설정한 OCR을 호출한다. 이미 계산한 결과는 같은 캐시 규칙에 맞을 때 재사용한다.
3. 묶기 결과를 보고 잘못 묶인 포맷을 합치거나 따로 뗀다. OCR 데이터셋만 필요하면 **템플릿 만들기**는 필요 없다.
4. **OCR 검수로** 이동한다. ⑤에서 글자·박스를 고치고 쪽마다 **확인 (검수 끝)**을 누른다. 저장만 한 쪽은 확인 완료가 아니다.
5. ④의 해당 가져오기 상세에서 **OCR 벤치마크로…**를 누른다. 대상 포맷, 정답, 용도, 이름을 선택해 생성한다.
6. 정답은 **OCR 검수본 (확인한 쪽만)** 또는 **사내 OCR 그대로 (일치도)**다. 후자는 OCR의 의사정답이며 사람이 확인한 실제 정답과 구분한다. 용도는 평가 전용/학습을 고른다.
7. 완료 후 **⑥ 데이터셋** 목록에 자동 등록된다. 문항·정답을 확인하고 학습 설정 내보내기나 평가로 이어 간다.

일반 가져오기(이미지·PDF 폴더)는 OCR 을 부른다. 이미 OCR·추론 결과가 있으면 **결과 폴더에서**로 가져온다(`meta.json`·`images/`·`ocr/`·`pred/`, [RESULTS_FORMAT.md](RESULTS_FORMAT.md)). 저장된 OCR 을 쓰고, 추론 결과는 ⑤ 라벨 검수에서 고친다. 명령줄 검사: `python -m studio.results check <폴더>`.

## 4. 내 서식으로 새 합성 시나리오 만들기

1. ④에서 포맷을 열고 견본 문서·서식 ID(`img_...`)·이름을 정해 **템플릿 만들기**를 누른다. 같은 양식에 값이 다른 문서 둘 이상이면 값 자리·지우기 초안을 제안한다. 한 문서만 있어도 직접 편집할 수 있다.
2. **① 서식 → 영역 편집**에서 값 영역과 배경 지우기를 확인한다. 항목의 키, 종류(글자/체크 등), 합성 값 출처를 정한다. 기존 견본의 값이 배경에 남아 새 고객의 값과 겹치지 않도록 수정 전후를 확인한다.
3. **미리보기**, **문항 Q/A**, **검수**에서 다른 고객 seed로 값과 정답이 함께 바뀌는지 확인한다. 서식을 검수 완료로 표시한다.
4. **③ 시나리오·묶음 → 새 시나리오**에서 ID·이름·필수 서식 ID를 지정한다. 필요한 추출/비교 작업의 서류와 키, 비교 연산을 정하고 예시 고객으로 실행한다. 기존 대조 사례·심사 규칙은 적용 가능한 것을 선택한다.
5. 결과·근거·Q/A를 확인하고 **저장**한다. **⑥ 새로 만들기 → 은행 업무** 레시피에서 서식/시나리오·수량·과제를 골라 생성한다. 완성 결과는 자동 등록된다.

이 경로는 원본 문서를 견본으로 **새 합성 고객의 서류**를 만드는 경로다. 실제 고객의 문서 내용과 묶음을 그대로 데이터셋으로 옮기는 기능은 아니다. 새 업무의 특수 계산·심사 규칙이나 새로운 question/answer 계약을 자유롭게 추가하는 UI도 아직 없다. 현재 직접 작업은 추출과 지원 비교 연산, 심사는 기존 규칙 선택 범위다.

## 5. 라벨 있는 데이터: 생성기의 원본 형식으로 고정

정답 입력 표준은 [LABEL_FORMAT.md](LABEL_FORMAT.md)의 **v1**이다. 생성 데이터와 같은 `labels/<id>.json`을 준비한다. 필수 정보는 `id`, `doc_type`, `doc_name`, `images`, `pages`, `fields`이며, `fields`에 항목별 `key`, `label`, `type`, `value`와 필요한 위치를 쓴다.

**원본 라벨은 `page` 0부터·`bbox` 이미지 픽셀이다.** 모델 정답의 `page` 1부터·`bbox_2d` 0~1000을 원본 라벨에 섞지 않는다. 항목 키는 생성기의 해당 서식 키를 그대로 사용한다. 같은 서식을 사용하는 데이터마다 별도 키 대응을 요구하지 않는다. `null`은 실제 빈 칸 정답이며, 라벨링하지 않은 항목은 생략한다.

④ 가져오기에서 **라벨 있는 데이터 준비 · 생성기 공통 규격 v1**을 펼치면 JSON Schema와 실제 합성 이미지·라벨 예제 ZIP을 다운로드할 수 있다. ZIP을 푼 뒤 **라벨 있는 데이터 → 폴더 경로 → 폴더 검사 → 이미지·정답 확인 → 과제/용도 선택 → 확인란 체크 → 데이터셋 만들고 등록**을 실행한다. ⑥에서 생성 진행을 보고 완료 후 자동으로 등록된 데이터셋을 연다. ZIP 직접 업로드는 지원하지 않는다.

필수 반입 메타 `meta.json`은 `format: "docgen-labels/1"`, `name`, `real_data`, `gt`를 지정한다. 쪽 전체 OCR 세트는 모든 쪽의 `ocr/*.json`과 `ocr_scope: "full_page"`가 있을 때만 선택할 수 있다. 기존 라벨과 저장된 OCR만 사용하며 OCR 서버를 다시 호출하지 않는다. 라벨 편집은 원본 JSON에서 하고 다시 검사한다.

원문 값·정규화 값·체크박스 보기·도장/서명 유무와 쪽 전체 OCR도 표준 규격을 따른다. 모델 추론 `pred/*.json`은 정답 표준과 별개인 보조 입력([RESULTS_FORMAT.md](RESULTS_FORMAT.md))이다. 사용자가 정답 데이터를 준비할 때는 모델의 임의 출력 구조 대신 생성기 공통 표준을 따른다.

## 6. 실서류 업무 묶음과 Q/A 준비

문서별 필드 정답 외에 **한 접수 건에 어떤 문서들이 제출됐는지**가 필요하다. 문서 ID는 표준 `labels/*.json`의 `id`와 일치해야 한다. 예를 들면 `bundles.jsonl` 한 줄은 다음과 같다.

```json
{"bundle_id":"case_001","scenario":"jeonse_loan","customer":"홍길동","documents":["case_001_id_card","case_001_application","case_001_lease"],"not_customer":[]}
```

- 서류 구비: 시나리오의 필수 서류와 실제 제출 목록을 비교한다. 명의를 확인한 뒤 `not_customer`에 타인 문서 ID 목록 또는 `[]`를 적는다. 없으면 명의 미확인으로 구비 문항을 생략한다. 없는 서류는 가짜 문서로 채우지 않는다.
- 항목 추출: 검수한 항목별 키·값·쪽·위치에서 정답을 만든다.
- 서류 대조: 비교할 두 서류·키·연산을 정한다. 예: 신청서 성명과 신분증 성명 일치. 실제 값과 근거에서 답을 계산하고 사람이 확인한다.
- 심사·계산: 입력 필드와 단위, 기준일, 계산식/판정 기준이 필요하다. 문서에서 확인할 수 없는 정보는 추정해 정답으로 확정하지 않는다.
- 표준 과제는 사용자가 모든 question/answer를 손으로 만들 필요 없이 검수된 라벨·문서 구성·규칙으로 생성하는 방향이다. 특수 질문은 질문 문구, 답 자료형·예시, 근거 항목, 계산·판정 기준을 별도로 정의해야 한다. 현재 Q/A 화면은 기존 과제 계약·생성 예시 조회용이며 질문 템플릿 편집기는 아니다.

현재 UI는 **④ 라벨 있는 데이터 → 폴더 검사·정답 미리보기·확인 → ⑥ 생성·자동 등록**이다. `bundles.jsonl`이 있으면 저장된 ③ 처리 설정과 기존 규칙으로 계산하고 생성된 업무 묶음에서 처리 결과·생략 사유를 확인한다. 항목 라벨 편집(⑤ 라벨 검수), 화면에서 묶음 정하기(⑤ 라벨 검수 › 업무 묶음), 모델 결과 키 매핑(키 대응)은 결과 폴더·가져온 묶음에서 쓴다. 확인한 문서·묶음은 표준 라벨 v1 폴더가 되어 이 경로의 입력이 된다. 실서류에서 합성 변조 사례나 임의 고객 프로필을 만들지 않는다.
